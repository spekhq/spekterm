## Context

探針以 CDP 連進**真正執行中的** app 驗收，這是本 repo 的核心紀律（不在產品程式碼裡塞測試分支、
不為驗收在 UI 上掛 `data-*`）。代價是它需要一個真的視窗：一輪 `test:e2e` 約十幾分鐘，期間使用者
無法操作自己的機器。

而 `probe:terminal` 有一條長期紅燈（「GPU 的渲染資源只給顯示中的終端」），CLAUDE.md 記載為既有的
產品缺陷。本 change 開始前的調查**推翻了那筆紀錄**，證據如下（全部實測）：

- webgl 路徑往 DOM 塞的 canvas 恰為 **2 顆**：`LinkRenderLayer`（class `xterm-link-layer`）與
  `WebglRenderer._canvas`（無 class）。兩顆都在 addon dispose 時被移除。
- 但單一終端就量到 **3 顆**。第三顆是 `<canvas width="40" height="27" style="display:none">`，
  parent 是 **`.xterm` 本身**（不是 `.xterm-screen`），且**反覆被移除又加回**。
- 攔截 DOM 插入 API 取得的堆疊：`TextureAtlas._drawToCache` → `getRasterizedGlyph` →
  `updateCell` → `_updateModel`。原始碼證實它是 `TextureAtlas._tmpCanvas` —— glyph 光柵化用的
  暫存 canvas，為了**繼承 font-feature-settings** 才必須掛進 DOM（`TextureAtlas.ts` 的註解自己
  說明了這一點）。
- 而 **atlas 由 `charAtlasCache` 跨終端共享**（`ownedBy` 陣列，同 font 設定的終端共用一份）——
  於是那**唯一的一顆** `_tmpCanvas` 會被 `append()` 搬到「最近一次光柵化 glyph 的那個終端」底下。
  DOM 節點只有一個 parent，所以總數恆為 3：**它從來沒有多出來過，只是換了個 parent。**

紅或綠因此只取決於一件與規格無關的事：切換之後，顯示中的終端**有沒有再光柵化過新字元**。沒有的話
`_tmpCanvas` 就停在隱藏的那個終端底下不動 —— 一個**穩定**的狀態，因此輪詢等不掉它。

**產品符合規格；錯的是判準。** 本 change 不改任何產品行為。

## Goals / Non-Goals

**Goals:**

- 探針預設不佔用使用者的實體螢幕、不與使用者搶鍵鼠焦點。
- 讓「持有程式化繪製的渲染資源」有一個**與規格意圖一致**的可觀察判準，並把它寫進 spec。
- 更正 CLAUDE.md 中把這條紅燈記為產品缺陷的敘述。

**Goals（實作期間追加）:**

- 收掉 `probe:terminal` 的兩個既有 flaky —— 一支間歇性紅的探針侵蝕的是「紅燈值得看」這件事本身，
  而那正是本 change 的主題（見 D7）。

**Non-Goals:**

- **不改任何產品程式碼。** 若實作期間發現產品確有缺陷，那是另一個 change。
  （追加的兩個 flaky 亦然：實測根因都在探針，不在產品。）
- **不宣稱建立了呈現正確性**（框線相接、粗細一致）。見 D4。
- 不追求「所有探針都能在無頭環境跑」以外的可攜性（Windows／macOS 的等價方案不在範圍內）。

## Decisions

### D1：以 `xvfb-run` 提供虛擬螢幕，不改探針連線的任何一環

**選擇**：在**啟動探針的那一層**包一層 `xvfb-run -a -s "-screen 0 <w>x<h>x24"`，探針本身
（CDP 連線、真滑鼠事件、行程清理）**一行都不改**。

**理由**：`DISPLAY` 是行程層的環境變數，Electron 會照著它把視窗畫到哪個 X server 上；
CDP 的 `Input.dispatchMouseEvent` 是注入 Chromium 的輸入管線，**與 X server 無關**。於是「換一個
螢幕」對探針而言是完全透明的 —— 實測 `probe:shell` 在虛擬螢幕上 17/17，一個字都沒改。

**替代方案與否決理由**：

- **`--headless`**：Electron 的 headless 與這些探針的前提衝突 —— 它們要量真實版面、送真滑鼠、
  驗視窗行為。而且 headless 下的渲染路徑與出貨路徑不同，違反「驗的正是被出貨的那份程式碼」。
- **Xephyr（可見的巢狀 X）**：解決不了「佔用螢幕」，只是把它縮小成一個視窗。
- **在探針內部自己起 Xvfb**：9 支探針各自重複一段行程管理，而 `xvfb-run` 已經處理了 display
  號碼配置與收屍。

### D2：虛擬螢幕上必須明確啟用軟體 GL，否則整條 GPU 路徑靜默地不被驗到

**選擇**：探針啟動 Electron 時傳入啟用軟體 GL 的旗標（實測 `--enable-unsafe-swiftshader`
`--use-angle=swiftshader`）。

**理由（實測）**：虛擬螢幕沒有 GPU，webgl context 取不到 → app **正確地**降級為 DOM renderer →
GPU 相關的三條斷言全紅。而那個紅是**環境**造成的，不是產品。若為此把那三條斷言刪掉或放寬，就等於
把 `terminal-gpu-renderer` 的整個交付從驗收中移除。加上旗標後同一段 66/66。

**這裡有一個必須明說的性質**：旗標讓 webgl **路徑**走得到（addon 載入、canvas 建立、資源釋放），
但畫素是 CPU 畫的。**驗得到生命週期，驗不到繪製正確性** —— 見 D4。

**替代方案與否決理由**：

- **只在虛擬螢幕上跳過 GPU 斷言**：那會讓「渲染資源只給顯示中的終端」這條**正確性要求**在預設
  路徑上零覆蓋，而它正是 webgl context 有並存上限（實測 16、超出時靜默回收）所要求的。
- **依 GPU 可用與否自動放寬斷言**：一條會自己變寬的斷言，在它最該說話的時候最安靜。

### D3：判準改為「這個終端當下走哪一條渲染路徑」，不是「底下有幾顆 canvas」

**選擇**：以**渲染路徑的可辨識產物**判定：

| 終端當下的渲染路徑 | 可觀察的憑據 |
|---|---|
| 程式化繪製（webgl） | 存在 `canvas.xterm-link-layer`；**不存在** `.xterm-rows` |
| 倚賴 glyph（DOM） | 存在 `.xterm-rows`；**不存在** `canvas.xterm-link-layer` |

**理由**：`xterm-link-layer` 是 webgl renderer **自己建立、自己在 dispose 時移除**的 render layer，
帶著穩定的 class，且**專屬於某一個終端**。`_tmpCanvas` 無 class、且會在終端之間遷移 —— 用「有沒有
canvas」當判準，就是把一個**共用的、會搬家的**東西當成了**per-terminal 的狀態**。

**兩條斷言都要有鑑別力**：不只斷言「隱藏的沒有」，也要斷言「顯示中的有」——
先前那條之所以能長期紅著而沒人發現是判準的問題，正是因為它只看隱藏的那一半。

**替代方案與否決理由**：

- **數 canvas 但排除 `_tmpCanvas`（例如以尺寸或 `display:none` 過濾）**：那是把判準綁在 xterm
  的內部實作細節上，且它會**靜默地**隨 xterm 版本失效（`session-restore` 已留下「別綁 claude 的
  內部佈局」的教訓，同型）。
- **讀 xterm 實例上的 renderer 型別**：探針碰不到那個物件（它活在模組閉包裡），而為了驗收把它
  掛到 `window` 上就是在產品程式碼裡塞測試鉤子 —— 本 repo 的紀律明文禁止。

### D4：軟體 GL 驗不到「畫得對不對」，這條限制寫進 spec 而非 CLAUDE.md

**選擇**：在 `terminal-sessions` 補上一條限制敘述：程式化繪製的**呈現正確性**（框線相接、粗細
一致）SHALL NOT 被視為可由自動化驗收建立。並保留**在實體螢幕上執行探針**的逃生口。

**理由**：`terminal-gpu-renderer` 的核心交付就是「表格不再破版」，而那是由 **dogfood 認定**的
（該 change 自己的紀錄：合成 fixture 重現失敗，最終由使用者實測通過）。改到虛擬螢幕之後，這件事
從「難以自動驗證」變成「**在預設路徑上不可能自動驗證**」—— 兩者的差別必須被記下來，否則下一個
change 會理所當然地以為「探針綠了 ＝ GPU 路徑是好的」。

**為什麼寫進 spec 而不是 CLAUDE.md**：CLAUDE.md 是給人讀的經驗；spec 是驗收的契約。**一條說
「這件事驗收證明不了」的敘述，屬於契約**。這與 `keyboard-navigation` 把「對話框抑制須以多種對話框
各驗一次」寫進 spec 是同一條理由。

### D5：逃生口是「顯式指定在實體螢幕上跑」，預設走虛擬螢幕

**選擇**：`test:e2e` 與各 `probe:*` 預設在虛擬螢幕上執行；提供一個明確的開關回到實體螢幕。

**理由**：預設要是「便宜到不會被繞過」的那一個 —— 這正是本 change 的出發點。而逃生口要存在，
因為 D4 的那一類問題只有真實驅動看得見，且**dogfood 之外還需要一條「我想親眼看它跑」的路**
（探針失敗時，看著它跑常常比讀 detail 快）。

### D7：兩個 flaky 都修「斷言問錯了問題」，不是加重試

兩條紅燈的表象都是「時好時壞」，直覺的處置是加重試或延長逾時。**兩條的實測根因都不是時間不夠：**

| flaky | 根因 | 處置 |
|---|---|---|
| 續寫入口的指示沒抵達 pty | stub 以 `exec sh -c 'tee \| "$SHELL" -i'` 收尾，而那個 `sh` 的 **stdin 是管線而非 tty**，撐不住 —— session 數秒內結束（**build 與 dev 皆然**，並非 dev 特有） | stub 改為 `exec cat >> <log>`：這一段只需要一個**讀 pty、寫檔、不會自己結束**的行程，不需要能執行命令的 shell |
| 「關掉 GPU 不遺失內容」 | 它緊接在「重新載入後仍可建立新 session」之後，顯示中的是一個**剛建立、幾乎空白**的 session —— 判準「複製回來的文字非空」其實只是在確認**非同步抵達**的 prompt 畫出來了沒 | 切 renderer 前先寫入一段已知標記（`echo GPUMARK_$((6*7))` —— **回顯裡不含答案**），判準改為「那一段特定內容還在不在」 |

**兩者都讓斷言變強，而不只是變穩**：前者從「賭 stub 還活著」變成「stub 必然活著」，後者從「有沒有
東西」變成「**那一段內容還在不在**」—— 後者才是 spec 說的「不遺失既有內容」。

**加重試會是錯的處置**：它會讓第一條在 stub 已死的情況下繼續重試（永遠等不到），也會讓第二條在
終端本來就沒有內容時反覆讀取一個空畫面 —— **把「斷言問錯了問題」偽裝成「機器比較慢」。**

> **追這兩條的方法本身是可複用的**：先問「它是不是每次都在同一個地方失敗」，再**把懷疑的中間狀態
> 變成獨立的斷言**（「按下前 pty 已存在」「切換前終端裡確實有已知內容」）。那兩條新斷言不只是診斷
> 用的鷹架 —— 它們留下來，下次同一個前提被破壞時會**直接指出是前提壞了**，而不是讓終點的斷言含糊
> 地紅一條。

### D6：`probe:identity` 與 `probe:native` 需個別確認，不假設它們一體適用

**選擇**：這兩支不與其他七支共用啟動路徑 —— `probe:identity` **刻意不傳 `--user-data-dir`**
（它要驗的正是 userData 實際解析出來的路徑），`probe:native` **自己就是一個 Electron 主行程**
（`electron scripts/probe-native.mjs`）。兩者都要各自實測，不得因為「其他七支過了」就推論。

**理由**：這正是 CLAUDE.md 已記載的一條紀律的實例 —— 那兩支的例外性質是有原因的，而批次套用
一個啟動包裝，最容易在這種例外上靜默地壞掉。

## Risks / Trade-offs

- **[軟體 GL 與真實驅動的行為不同，可能讓探針對某些回歸失明]** → 由 D4 的 spec 限制敘述 + D5 的
  實體螢幕逃生口承擔。**這是本 change 最實質的代價，不假裝它不存在。**
- **[`xvfb` 是系統套件，CI 或他人機器上可能沒有]** → 缺少時要**明確失敗並說明如何安裝**，
  SHALL NOT 靜默退回實體螢幕（那會讓「為什麼我的螢幕被佔用了」變成一個無從查起的問題）。
- **[虛擬螢幕的尺寸與使用者的實際螢幕不同，可能改變版面而影響對座標敏感的斷言]** → 尺寸要選得
  足夠大且**固定**（固定比「跟隨實體螢幕」更好：探針的行為不該隨執行機器而變）。CLAUDE.md 已記載
  分頁列寬度突變曾讓真滑鼠點空 —— 版面相關的失敗有前科，這條要在實作時實測整輪。
- **[改判準時可能把一條紅燈「改綠」而不是「改對」]** → 判準必須先在**已知的兩種狀態**上各驗一次
  （GPU 開 → 顯示中走程式化繪製；GPU 關 → 兩者都走 glyph 路徑），且要能重現先前那個誤判情境
  （`_tmpCanvas` 停在隱藏終端底下）而**仍然是綠的** —— 那才證明新判準真的把它排除了，而不是碰巧
  沒遇到。
