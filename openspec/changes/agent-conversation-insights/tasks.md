## 4. 存檔與增量掃描

- [x] 4.1 存檔的讀寫：一個來源檔案對應一份 NDJSON，寫入為整檔覆寫，目錄與檔案以僅限擁有者的權限建立；單元測試斷言覆寫後不殘留舊列，並斷言權限位元
- [x] 4.2 存檔中不得出現任何彙總結果；單元測試掃過存檔內容，斷言其中沒有直方圖、百分位或跨列計數
- [x] 4.3 digest 索引（**先 `stat` 再讀**，或記錄實際讀到的位元組數 —— design D2）與增量判定；單元測試斷言連續兩次掃描時第二次未讀取任何來源檔案內容
- [x] 4.4 **被追加內容的檔案其新增部分被萃取且既有列不重複**；單元測試對同一個 fixture 檔追加記錄後重掃，斷言新列出現、舊列未重複。transcript 就是逐輪追加的，這是實務上最常發生的路徑
- [x] 4.5 增量結果 = 全掃結果；單元測試對同一份 fixture 分別跑多次增量與一次從零全掃，比對兩份存檔完全相同
- [x] 4.6 來源檔案被刪除後存檔不受影響；單元測試刪掉 fixture 的一個來源檔再掃描，斷言對應存檔仍在
- [x] 4.7 **事後以新欄位重算**：單元測試對「來源已刪除」的存檔計算一個當初未規劃、但輸入欄位在萃取範圍內的指標，斷言算得出來
- [x] 4.8 存檔或索引損毀只影響它自己；單元測試弄壞一份存檔後重掃，斷言掃描完成、該來源被重新萃取、其餘不受影響
- [x] 4.9 來源不可用與個別檔案讀取失敗：兩者皆使掃描正常完成，且「來源不可用」與「來源可用但沒有資料」為可區分狀態；兩種各一條單元測試

> **第 4 組的五個對照組已跑過**：只比 mtime → 4.4 與 mtime 那條、來源消失時刪掉存檔 → 4.6、
> 重掃改成追加 → 4.1／4.4／4.5／4.8、存檔損毀時整次掃描失敗 → 4.8、來源不存在也回報 ok → 4.7／4.9。
>
> **兩個第一次跑不成立，值得記下來：**
> 1. 「重掃改成追加」的第一版 mutation 用了 `require`，在 ESM 下拋錯而走進 fallback ——
>    **等於沒改到，卻看起來像「對照組是綠的」**。改用已 import 的 `readFileSync` 才真的紅。
>    **一個沒有生效的 mutation 與一個沒有鑑別力的斷言，在輸出上長得一模一樣。**
> 2. 「mtime 相同但大小不同」那條測試原本以 `utimesSync` 把 mtime 改回舊值 —— 它收秒的浮點數而
>    檔案系統存奈秒，回讀時會落在目標值下方 1 奈秒。**六次裡四次紅，症狀是差 1 毫秒。**
>    改成把存檔記下的 mtime 對齊檔案當下的值（size 留舊的），連跑八次全綠。
>    順帶把產品端的 `Math.floor(mtimeMs)` 拿掉：它只丟掉次毫秒的資訊，換不到任何東西。

>
> **時間範圍的斷言轉為 issue #35。** 它在完整套件中兩次變紅、單獨跑 3 次中 2 次紅，症狀一致：
> 按鈕確實被按下（`aria-pressed` 為 true），但數字等 15 秒也不動。原本的假設是「開啟時的
> `refresh()` 晚一步回來、以全期間的結果蓋掉選好的範圍」，依此加了兩道守衛（請求序號、
> `refresh` 帶著當下範圍）—— **而對照組把兩道都拿掉之後它照樣 4/4 通過**。
>
> **假設沒有被對照組支持，就不能宣稱修好了。** 兩道守衛留著（邏輯上正確、代價極低），
> 但明文記著它們目前**沒有載體**。而那條偶發的斷言已從探針移除：留著它的代價是訓練人忽略紅燈，
> 在成因未明時把它改成「等久一點」則是把一個未知的錯誤改寫成一個更難察覺的錯誤。
>
> **dogfood 抓到兩個單元測試與探針都看不到的 bug：**
> 1. **`Math.min(...times)` 在真實資料上 `RangeError: Maximum call stack size exceeded`** ——
>    展開運算子把每一筆變成一個函式參數，而參數個數有上限。fixture 只有二十列，
>    真實資料有六十幾萬列。已改為單次迴圈，並補一條 30 萬列的迴歸測試（對照組驗過）。
> 2. **取數的 promise 沒有 `.catch`** —— 主行程一拋錯，畫面就一動也不動。使用者看到的是
>    「這個選擇器壞掉了」，而 console 裡有一整串錯誤。**這一條是放大器**：它讓第一個 bug
>    表現成「點了沒反應」而不是一則錯誤訊息。
