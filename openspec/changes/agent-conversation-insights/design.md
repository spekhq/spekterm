## Context

動機見 `proposal.md` §Why。這裡只記錄形塑作法的既有約束與實測事實。

**既有約束（本 repo）：**

- **主行程一死，所有 pty 陪葬。** `watcher-error-reporting` 已經為此付過一次代價
  （`branch-service` 沒掛 error handler）。任何長時間、吃 CPU 的新工作都不能跑在主行程裡。
- **renderer 沒有絕對路徑的詞彙。** 邊界檢查一律在主行程；推給 renderer 的只能是彙總結果。
- **`@theme` 的 token、`aria-label` 同時是 probe 的選擇器、UI 文案一律來自字典** —— 三道守衛照舊。
- **dev 的 userData 是 `~/.config/spekterm-dev`，與產物分家。** 存檔因此在兩邊各存一份，
  dogfood 看到的歷史比正式版短。這是既有機制的必然結果，不是缺陷。

**實測事實（2026-09-04，本機）：**

| | |
|---|---|
| 來源規模 | 44 個專案目錄、488 個 `.jsonl`、31 萬行、1.5 GB |
| 全掃耗時 | **約 24 秒**（Python 單執行緒；Node 同數量級） |
| 記錄類型 | **21 種**，其中 19 種要丟掉 |
| 保留期 | 最舊 2026-08-03，剛好 30 天 —— **來源每天在被刪** |
| 主 session ÷ subagent | 237 ÷ 251（subagent 各有獨立檔案，在 `<session>/subagents/`） |
| 使用者訊息 | `role: user` 的文字區塊 5,579 個，**真正是使用者輸入的只有 3,839（69%）** |

## Goals / Non-Goals

**Goals：**

- 掃描與聚合**都不在主行程執行**，且掃描崩潰不影響任何 pty。
- 存檔的正確性可被反向驗證：把增量結果與全掃結果對起來。
- 三條「禁止句」requirement 各有一個**能造出反例的 fixture** —— 沒有反例的驗收等於沒驗。

**Non-Goals：**

- **不做即時**。不 tail、不 watcher、不定時輪詢。這是回顧型的功能。
- **不做跨機同步、不做匯出格式的相容承諾。** 存檔是本機的、給自己看的。
- **不做對話的全文檢視器**。存檔含使用者輸入的內文，但畫面上只呈現彙總結果與「高頻的極短訊息」
  （`conversation-insights` 已明文限制）。存檔**不含** agent 的回覆、工具輸出或檔案內容。

## Decisions

### D1. 掃描與聚合跑在 `utilityProcess`，不是主行程、也不是 worker_threads

24 秒的 `JSON.parse` 在主行程裡等於 24 秒的 IPC 停擺 —— pty 的輸出、side panel 的請求、
所有東西一起卡住。

三個候選：

| | 主行程直接跑 | `worker_threads` | **`utilityProcess`** |
|---|---|---|---|
| 阻塞主行程 | **會** | 不會 | 不會 |
| 崩潰的後果 | 主行程死 → **所有 pty 陪葬** | 同一個行程，OOM 仍可能拖垮主行程 | **獨立行程，主行程存活** |
| Electron 支援 | — | 可用 | 43 原生提供 |

選 `utilityProcess`。**決定性的理由是崩潰隔離而不是效能** —— 這個模組要解析的是一份會隨版本
改變的內部格式，它出事的機率高於 repo 裡其他任何東西，而它出事時使用者正在跑的 agent 不該
跟著死。`worker_threads` 擋得住阻塞但擋不住這一條。

代價：多一個要收屍的行程（比照既有 pty 的生命週期紀律，三條路徑都要不留孤兒）。

### D2. 存檔的單位是「一個來源檔案一份」，不是一份大檔

增量的單位是來源檔案（判定鍵：路徑 + 大小 + mtime）。**讓存檔的單位與增量的單位相同**，
於是「重掃某個檔案」＝「覆寫對應的那一份」，而 spec 要求的「增量結果 SHALL 與全掃相同」
在結構上成立，不必靠測試去釘。

其他候選與它們的問題：

- **單一 append-only NDJSON**：重掃一個被改寫過的來源檔案時，舊的列還在裡面 —— 只能靠
  「寫入時去重」補救，而那是一個沒有結構保證的不變式。
- **按月分檔**：一個 session 會跨月，於是「重掃一個檔案」要動到兩個月份檔。

來源檔案被刪除時，**我們的那一份原地不動** —— 這正是本能力存在的理由，而以來源檔案為單位
讓它變成「什麼都不做」而不是「記得不要刪」。

格式為 NDJSON、短鍵。實測列大小：使用者訊息 60 bytes、工具 69、用量 84。

**digest 的順序是承重的：先 `stat` 再讀，或把「實際讀到的位元組數」存進 digest。**
反過來（先讀、後 `stat`）會記下一個比實際讀到的還大的 size；該檔案若之後剛好不再成長
（session 就此結束），那一段列**永遠補不回來**，而來源 30 天後就被刪了。
窗口很窄，但它丟掉的東西不可逆。

### D3. 用量列照 spec 存成一則訊息一列，接受它佔掉存檔的三分之二

實測換算（以 32 天的真實資料外推一年）：

| 內容 | 一年 | 佔比 |
|---|---|---|
| 使用者訊息列（欄位） | 3 MB | 2% |
| **使用者訊息的內文** | **4 MB** | **3%** |
| 工具呼叫列 | 43 MB | 30% |
| 用量列 | **95 MB** | **65%** |
| 合計 | **145 MB** | |

**訊息內文幾乎是免費的**（4 MB／年）—— 這個 change 最重要的目的之一，代價是存檔的 3%。
> 探索階段一度估成 61 MB／年，因為當時的長度平均值被 `isMeta` 的內容污染成 1,119
> （真實值 53）。**同一個誤判連帶讓一個容量決策差了 15 倍。**

真正貴的是用量列：它的數量是使用者訊息列的 26 倍，而它在本 change 的呈現裡**一張圖都沒用到**。
把它彙總成「每 session 每日一列」可以省下約 90 MB／年。

**仍然選擇不彙總。** 理由是一致性：`conversation-archive` 的第一條 requirement 就是
「不得只保存彙總結果，因為彙總不可逆」。在同一份 design 裡對一個**目前完全沒在用**的欄位
破例彙總，等於預先決定了「將來只能問這幾個關於成本的問題」—— 而那正是這個 change 想避免的
失敗模式。145 MB／年，對照來源本身 30 天就 1.5 GB，不構成問題。

### D4. 專案的識別用來源目錄名，顯示名稱用「與該目錄名相符的那個 `cwd`」的 basename

**實測踩雷：`cwd` 在 session 中途會變。** 本 change 自己的 session 紀錄裡有四個不同的 `cwd`
（含 `/tmp/.../scratchpad`）—— 直覺作法 `basename(cwd)` 會把這個專案標成 **「scratchpad」**，
而畫面上看起來完全正常。

正確的作法利用來源目錄名的生成規則（cwd 的每個非英數字元換成 `-`）：**在該 session 出現過的
所有 `cwd` 之中，取其編碼後等於來源目錄名的那一個** —— 那就是 session 起始的專案根，
其 basename 即顯示名稱。

- 送往 renderer 的是 **`{ id, label }`**：`id` 為來源目錄名的雜湊（不可逆），`label` 為 basename。
  **`cwd` 與來源目錄名都不離開主行程／utility process** —— 來源目錄名本身就是一個換過字元的
  絕對路徑，直接送出去等於送出路徑。
- basename 撞名時（不同根之下同名的 repo）以父層 basename 消歧。
- **編碼非單射**：`/a/foo-bar` 與 `/a/foo/bar` 都編碼成 `-a-foo-bar`。同一 session 兩者都出現過
  時，取**最早出現的那一個**（session 起始的 cwd 才是目錄名的來源）。
- 找不到相符的 `cwd`（來源只剩無 `cwd` 的記錄）時，退回「無法命名」而非猜一個 —— 比照
  `SpecInfo.path` 那條：少一個名字，好過給一個錯的。

### D5. 工具呼叫涵蓋 subagent 的檔案，使用者訊息不涵蓋

subagent 的 transcript 是獨立檔案（本機 251 個，多於主 session 的 237 個）。兩類資料的歸屬
方向相反：

- **使用者訊息**：subagent 的 `role: user` 記錄是 orchestrator 寫給它的指令，**不是使用者打的**。
  計入會讓每一個以「我講了幾句」為分母的指標失真。**排除。**
- **工具呼叫**：subagent 跑的 Bash 就是這次工作真的跑掉的 Bash。**計入**，且歸屬於同一個專案。

這件事必須被寫下來，因為兩種選擇都算得出數字，而「Bash 佔 75%」在兩種定義下是不同的量。
`conversation-insights` 的視圖 SHALL 讓這個口徑對使用者可見（比照「每個視圖標示其來源欄位」）。

### D6. 觸發時機：app 啟動後延遲一次，開 overlay 時再一次

**只在開 overlay 時掃是不夠的，而且它的失效方式正好摧毀本 change 的前提** —— 使用者若 31 天
沒開過 overlay，那一個月的來源已經被清掉了，而存檔裡永遠不會有它。

因此：

1. **app 啟動後延遲觸發一次增量掃描**（不與啟動搶資源；在 utility process 裡，不影響互動）。
   這一趟是本能力的保命動作，與使用者有沒有要看無關。
2. **開啟 overlay 時再觸發一次**，讓剛剛的對話也算進去。
3. **不做 watcher、不做定時輪詢。** 來源每天只有數個檔案在動，而這是回顧型功能。

同時只允許一次掃描在跑；重複觸發時回報「進行中」而不是排隊。

### D7. 聚合在 utility process 完成，renderer 只收得到最終數字

renderer 收到的是一份數十 KB 的彙總結果（本 change 的探索階段實測：其中八張圖的資料為 52 KB），
其中沒有任何列、沒有任何路徑。這同時滿足 spec 的兩條（不外洩路徑、renderer 不接觸列級資料），
且讓 overlay 的渲染不需要任何解析工作。

**已知的成長極限：** 中位數與百分位無法由已彙總的桶正確合併，因此聚合必須讀過全部的列。
以目前的體積（12 MB／32 天）不成問題；存檔累積到數百 MB 之後這一趟會變慢。
不預先最佳化 —— 記錄在此，等它真的變慢再處理（屆時的作法是為「不會再變的過去日期」建立
一層可合併的中間結果，而中位數改由細桶近似）。

### D8. 圖表自繪，一律 DOM／CSS，SVG 只用在真的需要的地方

不引入圖表函式庫。十一張圖裡有十張是長條、熱圖或比例條 —— DOM + CSS grid 即可，
且**沒有 SVG 的 viewBox 溢出問題**（標籤跑出畫框是 SVG 圖表最常見的靜默錯誤）。

> **不要把 `measure:bundle` 當成這件事的守衛。** 實際讀過 `scripts/measure-bundle.mjs`：
> 它的失敗條件只有三個（分類之和 ≠ 總計、產物出現語言服務 worker、語言資產少於兩個 lazy
> chunk），**沒有任何體積預算**。一個圖表函式庫會被歸進「other」而照樣 exit 0。
> 這件事的守衛是**依賴清單**，不是體積報告。

字級一律引用 `--text-*` token（`typography.test.mjs` 擋寫死字級）；顏色一律走既有主題 token。

### D9. 測試接縫是 `CLAUDE_CONFIG_DIR`，而它的解析必須走 `user-env`

**已實測（2026-09-05）**：設定 `CLAUDE_CONFIG_DIR` 後，`projects/` 與其中的 transcript
**確實一併搬到新位置**（連認證失敗的那一趟都照樣寫出 `<新位置>/projects/<slug>/<uuid>.jsonl`）。
接縫成立 —— probe 可以把它指向一份 fixture，**不需要在產品程式碼裡加任何測試分支，
也不需要在 UI 上掛 `data-*`**。

**但對真實使用者，只讀 `process.env` 是行不通的。** `user-env.ts` 的分界是承重的：使用者互動
shell 的環境只有 `PATH` 併進 `process.env`，其餘由 `getUserEnv()` 持有。使用者在 `.zshrc` 裡設的
`CLAUDE_CONFIG_DIR`，主行程與它 fork 的掃描行程**都看不到** —— 於是掃一個空目錄、呈現
「來源不可用」，而他的資料就在旁邊。**這個失效完全靜默。**

因此來源根的解析順序是 **`getUserEnv()` → `process.env` → `~/.claude`**。
probe 那條路徑仍然成立，因為 probe 是把變數設在被測 app 自己的行程環境上。

### D10. 三條「禁止句」requirement 各自需要一個能造出反例的 fixture

`conversation-insights` 有三條 requirement 的形式是「不得用 X」。**它們的載體必須是：把實作換成
被禁止的那個算法時，斷言會變紅。** 否則就是三盞假綠 —— 而這正是本 repo 重演過五次的失敗模式。

| requirement | fixture 必須具備 | 換成錯算法時的差異 |
|---|---|---|
| 不得以平均數呈現 | 一批短訊息 + 一則極長訊息 | 中位數與平均數相差一個數量級 |
| 使用者訊息的判定用結構旗標 | 一則帶 `isMeta`、內文很長的記錄 | 訊息數與長度平均值同時改變 |
| 不得以 session 首尾差定義工作段 | 一個 session，其記錄分佈於相隔數小時的兩個時段 | 一段長 vs 兩段短 |
| skill 不得自訊息開頭的斜線取得 | 一次 Skill 工具呼叫，其對應訊息**不以斜線開頭** | 計為 1 vs 計為 0 |
| 中斷以 `interruptedMessageId` 判定 | 一則內文像中斷、但不帶該欄位的訊息 | 計為中斷 vs 計為一般訊息 |
| 純通知不產生列 | 一則通篇只有 `<task-notification>` 的記錄 | 多出一列空內文訊息 vs 不產生列 |
| 時間軸以本機時區呈現 | 一則本機時間 23:30（UTC 為前一日）的訊息 | 落在 23 時 vs 落在 15 時 |

> **對照組本身也要被驗。** 本 repo 的紀錄是：清償覆蓋缺口時，「有載體」的第一版裡**三條有兩條
> 仍是假綠**。做完 fixture 之後要真的把實作改壞一次，確認它紅。

### D11. 使用者訊息的判定用來源的結構旗標，不用文字樣式比對

`conversation-archive` 已把這條寫成 requirement；這裡記錄它的來歷與實作後果。

**參考實作（BAT）用的是文字樣式比對**：三個 pattern（`<task-notification>`、
`<local-command-caveat>`、中斷標記）。對本機真實資料實測的結果：

| | 抓到 |
|---|---|
| 文字樣式比對（三個 pattern） | **53** 筆 |
| `isMeta: true` 旗標 | **965** 筆 |

漏掉的 912 筆全部是使用者從未輸入的東西：skill 被展開的完整內文（單是
`Base directory for this skill` 就 350 筆）、其他 agent session 送來的訊息（190 筆）、
圖片佔位、harness 的追問。它們讓每一個數字都偏掉：

| | 文字比對 | `isMeta` |
|---|---|---|
| 使用者訊息數 | 4,777 | **3,839**（高估 24%） |
| 長度中位數 | 33 | **23** |
| 長度平均 | 1,119 | **53** |
| 最長 | 922,812 | **3,784** |

**這正是本 repo「結構優於格式假設」那條紀律的又一個實例** —— 文字樣式是一份追不完的清單
（每加一種 skill、每加一個 harness 功能就多一種），而旗標是來源自己標的。

實作後果：萃取必須讀**記錄的頂層欄位**（`isMeta` / `isCompactSummary`），
不能只看 `message.content`。這件事很容易漏，因為分類邏輯天然會寫成「吃一個 content block」。

### D12. 語言特徵於讀取時計算，掃描階段只存原文

「我的語氣」的分類規則（什麼算問句、什麼算祈使）**一定會改**。在萃取階段就算成計數的話，
改規則只對之後的資料生效，而過去那段的來源已經被刪除 —— 永遠無法以新規則重算。

因此掃描階段不做任何語言判斷，聚合階段才套規則。代價是每次聚合要對全部訊息跑一次正規表示式：
3,839 則、內文合計 0.35 MB（32 天），可忽略；即使累積十年也只有數十 MB 的文字。

分類規則本身要能呈現給使用者（spec 已要求），**且每一類要附實際的例句** —— 因此規則的定義、
它的說明文字、以及取例句的條件要放在一起，不能散落在程式碼裡。

> **例句不是裝飾，它是唯一能發現規則寫錯的東西。** 以真實資料試作時，第一版規則有兩個 bug，
> 而兩個都是「數字看起來完全正常」：
>
> | bug | 症狀 | 真實影響 |
> |---|---|---|
> | 正規表示式用了 multiline 旗標 | `^…$` 錨定的是**行**而不是整則訊息，於是一則長訊息裡有一行寫「好」就被判成「純確認放行」 | 該類別混進大量長訊息 |
> | 修正詞表放了單字「別」 | 「分**別**是客廳次臥」「分**別**做什麼」全部命中 | 該類別從真實的 98 膨脹到 247，**2.5 倍** |
>
> 兩個都是把句子印出來的當下就看見的，而從長條圖上看不出任何異狀。

### D13. 語氣分類的規則表放進字典，不放在原始碼的字串字面值裡

`copy-language.test.mjs` 走 AST 掃 `src/**` 所有非測試檔，**字串與模板字面值不得含 CJK**。
而語氣分類必然要比對中文（「嗎」「吧」「請」「幫我」「不對」）。

三個選項裡選第三個：

| | 問題 |
|---|---|
| 寫成字面值 | **直接違反守衛**，`npm test` 紅 |
| 寫成 `\uXXXX` escape | 過得了守衛，但規則表變成沒有人讀得懂的東西 |
| **放進 `en.json`** | `.json` 不在守衛的定義域；而規則的**說明文字**本來就要呈現給使用者（spec 已要求），兩者放在一起 |

**這件事要在動工前決定**，否則會在第 5 組快結束時才炸，而那時規則表已經寫滿了。

### D14. 掃描行程回傳錯誤碼，文案在主行程或 renderer 組

掃描行程是第四個 realm（主行程／preload／renderer 之外）。本 repo 的 i18n **於模組載入時初始化**，
而**未初始化的 `t()` 不拋錯，它回傳 `undefined`** —— 畫面上就是一片空白。

與其在第四個 realm 再接一份字典（多一個「誰先載入」的不確定），掃描行程一律回傳**結構化的錯誤碼**，
文案由主行程或 renderer 依既有的字典組。這同時讓 spec 那條「錯誤訊息不得含絕對路徑」變得容易滿足
—— 錯誤碼裡沒有路徑可放。

### D15. 掃描行程是 main 建置的第二個進入點，且必須驗到打包後

`electron.vite.config.ts` 的 `main` 段目前沒有 `rollupOptions.input`，而 `utilityProcess.fork`
需要 `out/` 裡真的有那支檔案。**失效方式是最壞的那種**：dev 可能因為路徑巧合而正常，
打包後 `MODULE_NOT_FOUND` —— 而 `test:e2e` 的九支**都不含** `probe:package`。

因此：新增建置進入點，並在收尾時以 `PROBE_PACKAGE_APPIMAGE` 重用產物跑一次 `probe:package`。
若 `utilityProcess.fork` 無法直接 fork asar 內的檔案，比照 node-pty 加進 `asarUnpack`
（**未實測，動工時第一件事就是驗這個**）。

### D16. 新的 IPC 開一個自己的 namespace，不掛在 `fs` 之下

`filesystem-access` 有一條 scenario **逐一列舉**了 `window.workspace.fs` 上允許存在的成員，
多一個就違反它，且有探針斷言。preload 本來就是分 namespace 的（`fs` / `openspec` / `folders` /
`app` / `shell` / `clipboard` / `settings` / `terminal` / `panel`），開一個新的即可。

寫在這裡是因為「掃描器讀檔案」很容易讓人直覺往 `fs` 裡放，而那是這個 change 唯一會弄紅
`filesystem-access` 的方式。

## Risks / Trade-offs

- **`isMeta` 是內部旗標，可能改名或消失。** → 掃描時 SHALL 統計「被判定為非使用者輸入的比例」，
  該比例若在某次版本更新後驟降為 0，即為旗標失效的訊號。**這比事後從圖表上看出異常早得多**
  —— 圖表上它只會表現為「使用者最近話變多了」。
- **來源是內部格式，會漂移。** → 白名單處理記錄類型（spec 已要求），未知類型忽略而不報錯；
  存檔的寫入永遠是「整檔覆寫」，**格式漂移只會讓新資料變少，不會損毀既有存檔**。
- **utility process 崩潰或卡住。** → 主行程存活、pty 不受影響；狀態回報為「掃描失敗」而非
  永遠停在進行中。要設逾時。
- **首次掃描 24 秒，使用者第一次開 overlay 會等。** → 啟動後的那一趟通常已經跑完（D6）；
  真的還在跑時 overlay 呈現「掃描進行中」而非空白（spec 已要求）。
- **存檔一年約 145 MB，且只增不減。** → 已知並接受（D3）。**目前沒有清理機制**；
  若日後要加，那是一個新的決定，不該悄悄加進來 —— 一個會自己刪資料的存檔，違反它自己的目的。
- **dev 與正式版各一份存檔。** → 既有 userData 隔離的必然結果。實作時要記得，
  否則會誤判成「資料掉了」。
- **存檔含使用者輸入的完整內文，那是這台機器上最私密的一份文字之一。** → 只寫進 userData，
  不經網路、不整批送 renderer、畫面上只放高頻極短訊息（spec 已要求三條）。
  **但它確實在磁碟上，且沒有加密** —— 與 `~/.claude/projects` 的原始 transcript 同等級，
  只是活得更久。這是使用者在知情下的裁決。
- **24×7 熱圖可能撞到字級的地板（`2xs` 為 13px）。** → 若塞不下，正確處置是替
  `typography-scale` 開一份 delta（它有「字級尺度涵蓋 renderer 既有的所有級距」那條），
  **不是**偷寫 `text-[10px]`（會被 `typography.test.mjs` 擋）或 `style={{fontSize}}`（繞得過去，
  而那正是問題）。動工時先量一次欄寬再決定。
- **活動列的第五個入口偏離雛型。** → 已於 `workspace-layout` 的 delta 中留下裁決紀錄。
