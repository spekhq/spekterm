## Context

動機見 `proposal.md`。這裡只列**限制了解法**的既有事實，每一條都指向程式碼。

**收件匣這一側已經定案的語意，三條都承重：**

1. **重複的判定分兩種姿態**（`intake-service.ts:160-171`）：同一識別碼、**內容相同 ⇒ 靜默消費**；
   同一識別碼、**內容不同 ⇒ 可見的警示**，語意是「識別碼搶佔，有一件事沒進來」。
   **這條直接否決了天真的回補** —— thread 會長大，同一則 mention 隔天再投一次就是「同 id
   不同內容」，於是使用者每次啟動收到一則**假的**搶佔警告，而那個通道正是本能力唯一的警訊。
   **而「內容」不只是本文**：`digestOf`（`intake-store.ts:76-93`）涵蓋
   `originKind` / `originId` / `title` / `body` / `actor` / `originLabel` **六個**欄位，
   其中 `actor`（發話者顯示名稱）與 `originLabel`（頻道名稱）**由第三方隨時可改，
   且與訊息本身是否被編輯無關** —— `intake-schema.ts:57` 的註解就寫著後者「是可變的字串」。
2. **本文超過上限是拒絕，不是截斷**（`intake-schema.ts` 的 `TOO_LONG`，上限 4000）。
   截斷只能發生在 producer 這一側。
3. **識別碼的字元集含 `.` 與 `:`**（`intake-id.ts` 的 `ID_CHARSET`），註解裡已經寫著
   「Slack 的 `C123.1699` 這種識別碼需要它」—— Slack 的座標塞得進去，不必另編碼。

**本 change 要跨過的既有邊界：**

- `ptyEnv()`（`terminal.ts:133`）把使用者的互動 shell 環境合併進**每一個** pty。
- `settings:get`（`ipc/settings.ts:59`）把整個偏好物件原樣轉手給 renderer。
- 同一組偏好欄位有**兩處**各自維護的白名單清單（`preferences-store.ts:139` 的解構、
  `:246-258` 的保留），型別檢查對兩者皆零感知。本 change 會加上第三處（投影）。

**外部事實（已查證）：** Socket Mode 沒有重送佇列，斷線期間的事件就是掉了；多條連線（上限 10）
是為了換連線時不中斷，不是擴充。Socket Mode 的 app 上不了 Slack Marketplace。
`search.messages` 只吃 user token。

**外部事實（未查證，而 D1 讓它不再承重）：** Slack 官方的 Socket Mode 與 Events API 文件
通篇只講 bot 事件與「perspectival to a member installing your application」的 workspace 事件，
**沒有一句話明說 user-scope 的事件會不會經 WebSocket 送達**。

## Goals / Non-Goals

**Goals**

- 有人在 Slack tag 使用者本人時，那件事出現在收件匣，帶著足以判斷的上下文。
- **app 關著的期間不漏** —— 桌面 app 大多數時間是關著的，這不是邊角情形而是常態。
- 機密不流出主行程，且「流出」的三條路各有一道結構性的守衛。
- 偏好欄位的白名單從三份清單收斂成一份，漏掉即編譯失敗。

**Non-Goals**

- **多租戶與上架**。見 D12 —— 本設計交付的是邊界位置，不是多租戶。
- **常駐**。app 關著時不維持連線；覆蓋那段空窗的是回補，不是背景服務。
- 從 spekterm 回覆 Slack、更新 thread、加 reaction。**單向**。
- tag 一個 bot（`app_mention`）。偵測的是 tag 使用者本人。
- Slack 以外的來源。`originKind` 已經不是列舉，新增來源不必動收件匣。

## Decisions

### D1 回補是主幹，即時是加速器

**兩條路徑都要有，但主幹是回補。** 啟動時以 Slack Web API 取回「上次水位之後、tag 到我的
訊息」，這條路徑**獨立於任何即時通道**；即時串流（若可用）只是把同一件事提早送到。

**為什麼不是「即時為主、回補為輔」**：桌面 app 大多數時間是關著的，而 Socket Mode 沒有重送
佇列 —— 以即時為主等於把最常見的情形（關機八小時）交給一個結構上補不了的機制。

**它同時解掉了那條未查證的事實。** user-scope 的事件若走不了 WebSocket，本設計退化成
「只有回補」：延遲從秒級變成「啟動時 + 週期輪詢」，**而其餘每一個模組一個字都不必改**。
那條事實於是從「錯了整個接取層要換」降級成「錯了就少一個加速器」。

- 考慮過 **Socket Mode only**：app 關著的期間全漏，且把未查證的事實放在承重位置。否決。
- 考慮過 **輪詢 only**：最簡單，但使用者在線時的延遲沒有必要地差。保留為 D1 的退化態。

### D2 回補用 `conversations.history`，不用 `search.messages`

`search.messages` 看起來更直接（一個查詢就找出所有 mention），但它有三個問題：
**結果受使用者在 Slack UI 裡設定的搜尋篩選影響**（官方文件明載）、搜尋索引有延遲、
它要另一個 scope（`search:read`）。前兩者的失效方式都是**靜默漏件**。

`conversations.history` 以 `users.conversations` 列出使用者所在的頻道，逐頻道自水位取回，
在本地比對 mention。它是確定性的、與即時路徑共用同一組 scope、沒有索引延遲。
代價是啟動時的 API 呼叫數隨頻道數成長 —— 以「水位 + 有上限的回看窗口 + 每頻道分頁上限」夾住。

> **回看窗口有上限這件事是一個刻意的缺口**：關機超過窗口長度的期間會漏。它必須寫進規格，
> 不能只活在程式碼裡。

### D3 投遞的內容是訊息座標的函式 —— 兩個機制，缺一不可

**這是 D4 的前提，也是唯一能讓重送不誤報的辦法**（見 Context 第 1 條）。目標是：
同一則 mention 無論何時被重新推導，`digestOf` 所涵蓋的**六個欄位全部**相同 ⇒ 重送落在
「內容相同 ⇒ 靜默」那一支。**只處理本文是不夠的**，因此有兩個機制：

**(a) 討論串的上界固定為 mention 那一則訊息本身**，不是「取到現在為止」。
語意上也對：使用者是在那個時間點被 tag 的，他需要的是**那時**的上下文。
mention 之後的回覆若又 tag 了他，那是另一則 mention、另一個座標、另一則 intake。

**(b) 所有會進 digest 的第三方字串，於首次投遞時與水位一起快照**，重新推導時沿用快照值，
**SHALL NOT 重新查詢**。清單（每一個都是實際的變動源，不是假想的）：

| 欄位／來源 | 什麼時候會變 |
|---|---|
| `originLabel` | 頻道改名 —— **一次改名影響該頻道所有被重新推導的 mention** |
| `actor` | 發話者改自己的 display name |
| 本文中的 mention 呈現 | `<@U123>` 幾乎必須解析成 `@顯示名稱`（否則使用者讀到一串 id），於是**顯示名稱被烤進本文** |
| 本文中的 link unfurl | unfurl 是訊息貼出**之後**非同步補上的 —— 隔 1 秒取與隔 1 天取不同 |

**為什麼 (b) 不是邊角**：重新推導最常見的觸發**不是**「使用者編輯訊息」，而是**水位遺失**
（重裝、profile 還原、設定檔損毀隔離）—— 那時整個回看窗口內的 mention 全部重投一次。
那段期間只要有**一個**頻道改名或**一個**同事改了暱稱，使用者就會在啟動時收到一批
「有一件事沒進來」的警示。**噪音與警訊走同一條通道，等於把警訊關掉**
（`docs/lessons/intake.md` 第五節）。

- **殘餘的缺口**：討論串中既有訊息**被編輯或刪除**時，重新推導的本文仍會不同 ⇒ 一則假的
  搶佔警示。這是 (a)(b) 都蓋不到的（它改的是訊息本身），且罕見且**可見**。登記為缺口。
- 考慮過 **在本地快取已投遞的整份本文**以保證位元組一致：多一份與本文同量級的狀態要維護。
  否決 —— 但**那條否決不涵蓋 (b)**：快照兩個短字串與快取整份本文不是同一個成本量級。
  （第一版 design 只有 (a)，並拿這條否決當作「其餘不必處理」的理由 —— 那是錯的推論。）

### D4 識別碼 = mention 訊息的座標，不是 thread 的座標

`slack:<team_id>:<channel_id>:<message_ts>`。字元集已合法（Context 第 3 條）。

**以 mention 訊息而非 thread 為單位**：同一條 thread 裡第二次被 tag 是一件新的事，
thread-scoped 的識別碼會讓它靜默消失。

`team_id` 不可省 —— 使用者日後接第二個 workspace 時，channel id 跨 workspace 不保證相異。

### D5 Slack adapter 投進檔案落點，不走行程內捷徑

adapter 住在主行程，卻寫檔給自己讀。這看起來是多餘的繞路，**但那個繞路就是契約本身**：

- 走檔案 ⇒ 多拿到的是**投遞檔的 512KB 上限**（`intake-source.ts:49`）與**拒絕的消費語意**
  （暫時性拒絕原封留著等重試）。**其餘四道守衛（正規化、識別碼驗證、重複、總量上限）
  都在 `deliver()` 之內**，行程內捷徑一樣拿得到 —— 第一版 design 寫「沿用既有的**全部**守衛」
  是誇大的，留著會讓下一個讀規格的人以為 `deliver()` 本身沒有守衛。
  裁決不變，但它靠的是下一條理由，不是這一條。
- 走檔案 ⇒ adapter 日後**可以被搬到另一個行程**（產品化時的必經之路，見 D12）而收件匣
  一個字不改。
- `deliver()` 的 `adapter` 由接收端決定、投遞內容自稱的來源一律不採信 —— Slack 的投遞與
  外部 producer 的投遞因此**在收件匣眼中沒有差別**，這是對的：Slack 的內容同樣不受信任。

### D6 截斷在 producer 側，且截斷標記寫在本文之內

超過上限是**拒絕**（Context 第 2 條），所以 adapter 必須自己截斷。

**截斷的作用域是所有 authored 欄位，不只是本文。** `intake-schema.ts` 有**兩個**上限：
`MAX_BODY_LENGTH = 4000` 套在 `body` 上，`MAX_FIELD_LENGTH = 200` 套在
`title` / `actor` / `originLabel` 上，任一超過即**整則被拒絕**。
**Slack mention 訊息的第一行拿來當 title 很容易超過 200 字元** ⇒ 症狀是某些 mention
永遠進不了收件匣，而使用者只看到一則看不懂的拒絕。第一版 design 只論證了 body，
那個缺口的形狀與它要修的是同一個。

**長度以正規化之後、UTF-16 code unit 為尺度判定**（`intake-schema.ts` 的既有語意）——
producer 的截斷必須同尺度，否則會在邊界上差幾個字元而被拒絕。

**截斷標記必須寫在 `body` 這個字串裡面**，不能是投遞 JSON 的另一個欄位、也不能由呈現層附加 ——
`body` 是唯一「呈現給人看的與交給 agent 的是同一份」的欄位（`bodyOf()` 是唯一的 accessor，
由 `intake-context-source.test.mjs` 釘住）。標記放在別處，使用者就會讀到「這裡被截斷了」
而 agent 讀不到。

截斷**保留最接近 mention 的內容**（thread 的尾端），不是開頭。

### D7 token 自己一份檔案，不寄居 `preferences.json`

三個獨立的理由，任一條成立就足夠：

1. `preferences.json` 的內容會被**投影到 renderer**（本 change 正在收斂的那條路）。
2. 該檔案的寫入路徑**從空物件重建**、每次儲存整份重寫 —— 寄居其中的欄位倚賴每一個寫入者
   記得保留它，而 issue #39 正是那條路徑咬人的實例。`intake-routing` 已就同一理由把規則
   分了出去。
3. 權限姿態不同：token 檔以 `0600` 建立，偏好檔沒有這個要求。

**token 檔與 Slack 的連線設定檔也是兩份，不是同一份。** 連線設定（workspace、要偵測的身分、
回看範圍、endpoint）**本來就要投影給 renderer**（UI 要顯示它們）；token 放在同一個物件裡，
那個投影就成了 D8 表格第一列所說的那條出口。分成兩份之後，「把 token 投影出去」需要先跨檔案
去拿它 —— 那是一個做得到但不會不小心做出來的動作。

**權限的三個實作陷阱**（都會靜默失效）：`fs.writeFileSync` 的 `mode` **只在建立時生效**，
檔案已存在（權限是舊的 0644）時不改；repo 的落盤慣例是「先寫 `.tmp` 再 rename」
（`preferences-store.ts:163-171`），**tmp 檔的權限同樣要 0600**，否則有一個短暫的全域可讀窗口；
`mode` 會被 `umask` 遮罩，且 **Windows 上 `0600` 沒有意義** —— 比照 `O_NOFOLLOW` 那條，
列為 Phase 6 打包驗收前必須確認的項目。

### D8 機密的**四**條出口，各一道結構性守衛

「不要把 token 洩出去」不是紀律問題，把出口逐一堵住才是：

| 出口 | 守衛 |
|---|---|
| IPC 投影 | 逐欄位白名單（D9），且機密**根本不在偏好那個物件裡**（D7）。**Slack 連線設定的投影也算一條** —— 它本來就要送「已設定／workspace 名稱／狀態」給 renderer，而 token 住在它隔壁 |
| **子行程環境** | 原始碼守衛：機密讀取入口不得被**任何建構子行程環境的模組**取用（`user-env`、`terminal`、`report-runner` 的 `delegateEnv`），**且 `process.env[...] =` 的指派不得出現在機密模組及其呼叫端** |
| 診斷輸出（`console.*`） | 讀取入口回傳的型別不可直接字串化為明文（不透明包裝，`toString` / `toJSON` 不吐內容） |
| **網路** | 見 D11 —— 這是本 change **新增**的一條，而它是唯一真的會把 token 送出本機的那條 |

**「不得被 `terminal.ts` 匯入」這個守衛範圍是不夠的**（第一版就是這樣寫的）：
`ptyEnv()` 是 `{ ...process.env, ...getUserEnv(), TERM }`，所以**任何模組往 `process.env`
寫一個值**都會讓它進到每一個 pty —— 那個模組不必是 `terminal.ts`、也不必被它匯入。
而 Slack 的 HTTP 用戶端正是最可能這樣做的地方（許多 SDK 讀 `SLACK_TOKEN` 之類的環境變數）。
CLAUDE.md 已經把這條列為承重（「絕不要『順手』把它們也 `Object.assign` 進 `process.env`」）。

**送往 renderer 的是「設定好了沒」與「我是誰」，不是 token 本身。**

### D9 偏好欄位收斂成一份表，漏掉即編譯失敗

三處清單（讀入的解構、`setTerminalFont` 的保留、`settings:get` 的投影）改為由**單一欄位表**
推導。每個欄位必須回答三件事：怎麼清理、屬不屬於字型群組（決定 `setTerminalFont` 要不要保留
它）、要不要送給 renderer。**三個答案都沒有預設值** —— 新增一個欄位時，「要不要送給 renderer」
是一個必須被作答的問題，而不是一個沉默的 `true`。

**表的型別是 homomorphic mapped type，不是 `Record`：**

```ts
{ [K in keyof Required<TerminalPreferences>]: FieldSpec<Required<TerminalPreferences>[K]> }
```

`Record<keyof TerminalPreferences, FieldSpec>` 讀起來等價，**但它會弄丟一件現在釘得住的事**
（實測，repo 自己的 tsc）：現在每個清理器的回傳型別各不相同且**直接指派給具名欄位**，
於是型別檢查釘得住「哪個清理器配哪個欄位」。統一成 `FieldSpec { sanitize: (v: unknown) =>
unknown }` 之後，把 `fontFamily` 配上 `clampSize`、`fontSize` 配上 `sanitizeFamily`
**零錯誤**。用上面那個形狀則兩條都是 `TS2322`，而「漏欄位」仍然是 `TS2741`。

**照 `Record` 實作會用一個新的靜默失效換掉舊的** —— 從「三處各自為政」換成
「表是單一來源但每一格接錯無人知」。那在這個 repo 是明確的退步。

- 三條性質實測皆成立：漏欄位 `TS2741`、漏答 `toRenderer` `TS2741`、
  多一個不存在的欄位 `TS2353`。（`Record<K,V>` 的 `K` 受限於 `keyof any` 而非 `keyof T`，
  所以它不是 homomorphic，optional 修飾子不被保留 ⇒ 每個鍵都必填。這一點兩種寫法相同。）
- 「未設定即省略」的語意保持不變（逐欄位判定 `undefined`），否則 `probe:workspace` 會紅 ——
  具體是 `scripts/probe-workspace.mjs:1713-1715` 那條以 `Object.keys(...).length === 0`
  為判準的斷言。投影若把未設定欄位寫成 `undefined`／`null`，它當場變紅。
- **這條必須跑對照組，而且是三個方向**：拿掉一個欄位、漏答一個答案、把清理器接錯。
  一個「拿掉之後沒有任何東西會紅」的防護就是一個遲早會被拿掉的防護
  （`i18next.d.ts` 那條教訓的同一形狀）。
- **預設值語意（「undefined 代表什麼」）不在本 change 的範圍內，已轉為 issue #43。**
  它**不是**第四處白名單，而是另一個問題，但同樣是漏一個不會紅 —— 實測共 **5 處、跨兩個
  realm**：`index.ts:202`、`ipc/terminal.ts:126,129`、`PreferencesProvider.tsx:106,108,110`。
  不在本 change 做的理由是結構性的：renderer 不能 import 主行程的模組，收斂需要一個
  `src/shared/` 的新模組，那是另一個 refactor。
  （`PreferencesProvider.tsx:25` 的註解本身就寫著這個危害，當時的處置是「收斂到 provider」
  —— 而主行程有它自己的三份。）

### D10 連線與授權的失效必須使用者看得見

Slack 這一側的失效**全部是靜默的**：token 被撤銷、scope 不足、WebSocket 斷了沒重連、
回看窗口不夠 —— 症狀一律是「Slack 上有人 tag 我，但收件匣是空的」，而使用者**分不出**
那是「沒人 tag 我」還是「連線死了」。

因此連線狀態要有一個使用者看得到的呈現，且**失效與閒置必須可區分**。
它與收件匣既有的「拒絕與警示 SHALL 有界」同一條紀律：彙整，不逐則洗版。

### D11 驗收以替身 Slack，真實連線刻意不在裡面

真實 Slack 要網路、要憑證、回覆不可重現。比照 `probe:insights` 的委派與 `probe:agent-view`
的替身 agent：**產生路徑以替身驗，真實那段由 dogfood 認定，而這條缺口寫進規格。**

替身要能演出這幾件事，否則對應的斷言是假綠：斷線、token 被撤銷、同一則 mention 被回補
第二次、thread 超過本文上限、一則 mention 落在回看窗口之外。

**接縫是可設定的 API endpoint，而它是 D8 表格裡那條「網路」出口。** 比照物都有明確的接縫
（`probe:insights` 注入委派命令、`probe:agent-view` 把替身 agent 放上 `PATH`），而這一個
不是中立的實作細節：**一個可覆寫的 endpoint 加上一份 token，就是「把憑證送到一個不是
Slack 的主機」的能力。**

使用者裁決 endpoint 做成**一般的設定項**（與 workspace／身分／回看範圍同一份設定檔），
理由是日後接 Enterprise Grid 或 proxy 比較靈活。**代價是憑證的目的地成了一個資料欄位**，
因此它必須配上三件事，否則那個代價是看不見的：

1. **只能由使用者明確操作改動** —— SHALL NOT 由投遞內容、routing 規則或任何外部輸入寫入。
2. **非預設值時畫面上看得見** —— 使用者要能知道「我的憑證正在送往一個非官方的主機」。
   一個沉默的 endpoint 欄位比沒有這個欄位更糟。
3. **scheme 限於 `https:`** —— 白名單，不是黑名單。

> 考慮過「只認環境變數、且 `app.isPackaged` 為真時完全不生效」（產物裡表達不出來）。
> 使用者選了設定項，因此改以上面三條承擔。**這個取捨寫在這裡，是為了讓日後放寬第 2 條的人
> 知道他在拆掉什麼。**

> **`probe:agent-view` 的教訓直接適用**：只斷言「我們送出了正確的參數」證明不了任何事 ——
> 那一輪的命令有語法錯，每次都失敗，而事件目錄只是安靜地空著。斷言要落在**結果**上
> （收件匣裡出現了那一則、且本文逐字元等於磁碟上的 context 檔）。

### D12 「擴充性」交付的是邊界位置，不是多租戶

使用者的要求是「之後做成產品時要能讓大家設定」。**本設計交付不了那件事**，而含混過去是錯的：

- Socket Mode 的 app 上不了 Slack Marketplace ⇒ 產品化必須換成 Events API + 公開端點。
- app-level token 一個 app 只有一份，多條連線之間是負載平衡 ⇒ 結構上是單人、單 workspace。

**能交付、而且真的降低日後成本的是邊界的位置**：adapter 只是收件匣的一個 producer（D5），
它與收件匣之間的介面是「一個目錄 + 一份 JSON」。換接取層時，要改的是 adapter 自己；
收件匣、routing、session 的建立與預填**一個字都不必改**。連線設定是資料而非常數
（D7 的檔案），所以「讓別人填自己的 token」不必改程式碼。

這個張力寫進規格的 Purpose，不是只寫在這裡。

### D14 身分自憑證推導，不是設定出來的（實作時的裁決）

「要偵測誰被提及」與「連到哪個工作區」**不做成設定欄位**，改為在連線時自憑證推導
（`auth.test` 回傳它擁有者的 user id 與 team id）並快取。

**理由是失效模式。** 一個填錯的「要偵測誰」，症狀是**什麼都不會發生** —— 而那與「沒有人提及我」、
與「連線已失效」在畫面上完全相同。D10 花了一整條 requirement 在讓後兩者可區分；再引入一個
同樣形狀的失效源，等於把那條的價值抵消掉一部分。自憑證推導則**表達不出來填錯**。

- 第一版 spec 把身分列在「使用者可編輯的資料」裡，**delta 已隨此裁決更新**（不靜默偏離）。
  該 requirement 的用意（不是常數、不需重新安裝）完全保留 —— 推導更強地滿足它。
- 快取落在連線設定檔裡，但**沒有面向 renderer 的 setter**。它是「呈現用的衍生事實」，
  與 `secret-store` 的 `has()` / `names()` 同一類。

### D15 不需要新增任何依賴（實測）

Node 22.22（本 repo 的 `.nvmrc`，也是 Electron 43 內的版本線）**同時具備全域 `fetch` 與全域
`WebSocket`**。回補只需要 HTTPS 呼叫，即時路徑（Socket Mode 在 `apps.connections.open` 之後
就是一條普通的 WSS 連線）只需要 WebSocket —— 兩者都不需要 Slack 的官方 SDK。

**這順帶關掉兩個風險，而第二個正是本 change 剛立的守衛所防的**：

1. 依賴放錯 `dependencies` / `devDependencies` 區塊時，dev 完全正常而打包後一啟動就
   `MODULE_NOT_FOUND` —— 唯一驗得到它的載體是 `probe:package`（最貴的那一層）。
2. **許多服務 SDK 會讀約定俗成的環境變數**（`SLACK_TOKEN` 之屬）。那正是 D8 表格第二列與
   `secret-scope` 守衛①所防的向量：往 `process.env` 寫一個值，它就進到**每一個 pty**。
   不引入 SDK，這件事連發生的機會都沒有。

> **Electron 主行程的全域 `WebSocket` 尚未實測**（只驗了系統 Node）。它是即時路徑的前提，
> 而即時路徑在 D1 之下是加速器 —— 不成立時退化為輪詢，其餘模組不動。第 7 組會一併實測。

### D13 watcher 建立點的數字

`watcher.ts:24` 的註解與 `watcher-error-reporting` 的條文由「四個」改為「七個」，並列出實際的
七處。**條文所依賴的論證不受影響** —— 「一對一佔多數所以預設不必填」與「顯式傳入是孤例所以
要有測試釘住」兩條在 7 = 6 + 1 之下比在 4 = 3 + 1 之下更強。走 delta，不直接編輯主 spec。

## Risks / Trade-offs

- **user-scope 事件走不了 Socket Mode** → D1 已使它非承重：退化為只有回補，其餘不動。
  **實作順序上先做回補**，即時路徑排在其後，於是這條風險在最晚的時點才需要答案。
- **回看窗口之外的 mention 會漏**（關機超過窗口長度）→ 缺口寫進規格；窗口長度是設定而非常數；
  連線狀態的呈現要讓使用者看得出「回補只看到這麼遠」。
- **訊息被編輯或刪除 ⇒ 一則假的識別碼搶佔警示**（D3 殘餘）→ 罕見且可見，不靜默。登記為缺口。
- **頻道很多時啟動的 API 呼叫數** → 水位 + 窗口 + 每頻道分頁上限三重夾制；回補分批、
  不阻塞主行程（收件匣已有同形的條款）。
- **Slack 內容是不受信任的輸入，而它會成為 agent 的第一則 prompt** → 這是收件匣**既有**的
  威脅模型，兩道人類防線（讀本文、注意到拒絕）不變。本 change 不得放寬任何一格。
- **`docs/lessons/intake.md` 第五節那條缺口鏈，在接上第一個真實來源之後第一次會被真的走到**
  → 指出它是不夠的，要有機制。具體路徑：`MAX_PENDING = 200`（`intake-store.ts:65`），
  達到之後 `CAPACITY` 是**暫時性拒絕、不消費** —— 投遞檔留在落點、**每次掃描重讀一次**，
  而 producer 還在繼續寫新檔。一個活躍的 Slack 使用者離線一週後開機就會走到這裡。
  **處置：producer 每輪回補的投遞則數要有上限**，且達到上限時使用者看得到（已寫成
  requirement，不只是缺口登記）。
- **第一次使用時 routing 多半是空的** → `intake-routing` 規定「無規則亦無 fallback 時拒絕並
  說明」（方向是對的），但那意味著第一批 mention 全部是解析不出的待處理項目。
  這不是 bug，是預設體驗；處置在 UI（設定 Slack 時一併提示要設 fallback），不在規格。
- **憑證的目的地是一個資料欄位**（D11 的使用者裁決）→ 以「只能由使用者明確操作改動 +
  非預設值時可見 + scheme 限 `https:`」三條承擔。放寬任何一條都要回來看 D11。
- **新增依賴進 `dependencies`** → 放錯區塊時 dev 完全正常、打包後一啟動就 `MODULE_NOT_FOUND`。
  `probe:package` 是唯一驗得到它的載體。

## Migration Plan

沒有資料遷移。既有的偏好檔不需要改版本：`agentStatus` 補進讀取白名單之後，**磁碟上原本就
寫著的值會第一次被讀回來** —— 對曾經關掉它的使用者，那個開關會回到他當初設定的狀態。
這是修好，不是行為變更，但值得在 tasks 裡標一句。

實作順序由風險決定，不是由模組決定：

1. 偏好欄位表 + 三處收斂 + 投影守衛（**與 Slack 無關，先落地、先能 commit**）
2. watcher 數字校正
3. token 的保管與三道出口守衛
4. **回補路徑**（主幹；到此為止 Slack 已經可用）
5. 即時路徑（加速器；那條未查證的事實在此才需要答案）
6. 連線狀態的呈現
