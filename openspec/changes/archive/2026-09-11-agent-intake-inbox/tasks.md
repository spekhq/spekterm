## 1. 收件匣的資料層（主行程，純邏輯）

- [x] 1.1 定義 intake 的三組欄位型別（可驗證／第三方撰寫／來源專屬原始內容）與 `parseIntake()`，
      **回傳型別不含第三組**；以 node:test 驗解析結果上不存在該欄位
- [x] 1.2 補一道 `npm test` 原始碼守衛：原始投遞的型別與讀取函式**只能被保存那一個模組引用**
      （比照 `watcher-source.test.mjs`）。**對照組**：在別的模組加一行 import，守衛必須變紅
- [x] 1.3 欄位驗證：型別逐一檢查、字串長度上限、未知欄位丟棄、**本文長度上限**
      （上限訂在「人會讀完」的量級，理由寫進註解 —— 它是人類閘門有效性的唯一旋鈕，
      而把它調大不會讓任何東西變紅）；以 node:test 驗每一類畸形輸入皆被拒絕且不拋出
- [x] 1.3b **來源種類不得以 enum 白名單拒絕**：以 node:test 驗一個系統不認得的 `origin.kind`
      仍正常進入收件匣（**對照組**：把 kind 做成 enum 白名單 → 必須變紅）。
      1.3 的方向是相反的（「未知**欄位**丟棄」），照它寫出來的驗證器很自然會拒絕未知 kind
- [x] 1.4 識別碼的**三段**驗證（字元集白名單 ＋ 整串否決 `.`／`..`／空字串 ＋ 長度上限）。
      **長度上限由檔名長度反推**（可逆編碼會使長度增加，再加上目錄前綴與副檔名才是 `NAME_MAX`
      的預算）；以 node:test 驗「上限長度的識別碼確實產生得出保存檔」與「超過上限即拒絕」。
      以 node:test 用**其餘欄位皆合法**的 payload 只換 `id`，並在同一支測試先斷言乾淨版本
      進得來（**對照組**：只留字元集白名單，`..` 那條必須變紅 —— 白名單若含點號會放行它）
- [x] 1.5 落盤檔名由識別碼的 **hex 編碼**推導：消費 **UTF-8 位元組**、輸出字母表僅 `0-9a-f`、
      **編碼之前不得施加任何 Unicode 正規化**（一行出於好意的 `.normalize()` 會把兩個相異識別碼
      映到同一個檔名，正是本條要防的；而它通過「輸出字母表」與「可逆」兩項檢查）。以 node:test 驗
      「僅大小寫不同」與「NFC／NFD 形式不同」的兩個識別碼得到不同檔名且內容可分別讀回
      （**對照組一**：改用識別碼原文 → 必須變紅；**對照組二**：改用 sha1 前 8 碼 → 以一組
      預先算好的前綴碰撞驗證它變紅，證明「不可用雜湊截斷」這條不是空話）
- [x] 1.6 保存**以寫入已驗證的位元組達成**（`openNoFollow` ＋ root-relative 解析，root ＝
      `<userData>/intake`），保存成功後刪除投遞檔；**不得以 rename 搬移投遞檔**。
      以 node:test 兩個 fixture 各驗一次：**leaf 是 symlink**、**中間目錄是 symlink**，
      斷言目標未被寫入**且**無 symlink 時確實產生保存檔。
      **兩條 scenario 各配一個 mutation，不共用**：rename 版本**只會讓中間目錄那條變紅**
      （`rename(2)` 不跟隨最後一段的 symlink，它把那個 link 本身換掉）；leaf 那條的 mutation
      是把 `openNoFollow` 換成普通 `open`。寫成「兩條都會紅」會跑出一紅一綠，而最可能的結論
      是「leaf 那條沒有鑑別力」——它其實是承重的，只是守的是另一條路
- [x] 1.7 store：狀態 index 與保存區分家，三態、已接受者記錄 sessionId；
      以 node:test 驗寫入後重新載入狀態與關聯皆不變
- [x] 1.8 **去重鍵與內容的保留期限分開**：去重鍵永久、內容可過期；以 node:test 驗「內容已清除
      之後，同一識別碼再投遞仍被視為重複」
- [x] 1.9 待處理總量上限，達到時回傳**可呈現的**原因；以 node:test 驗既有待處理項不受影響

## 2. 投遞入口

- [x] 2.1 `deliver(intake)` 為**唯一**入口（驗證、去重、落盤都在它之後）；以 node:test 驅動它驗
      完整流程
- [x] 2.2 檔案 adapter：**mkdir 落點 → 建立監看 → 掃描既有內容**（此順序會讓中間抵達的檔案
      處理兩次，而去重承擔它；相反順序會**漏掉**而漏掉是靜默的）。以 node:test 驗「落點中先有
      檔案才啟動」時該 intake 進得來（**對照組**：移除掃描 → 必須變紅，`ignoreInitial: true`
      寫死於 `watcher.ts:80`）。監看 SHALL **同時處理新增與變更** —— 補寫發生在同一個路徑上，
      不會再產生一次新增；2.6 的載體若不經真實 watcher，要另有一條釘住事件訂閱清單的測試
- [x] 2.3 **兩條入口匯流到同一條路徑**：以 node:test 讓**三份**畸形投遞（識別碼不合法、
      超出大小上限、**以及一個 index 裡已存在的識別碼**）各在啟動前與啟動後各來一次，
      斷言六次結果相同。第三份是關鍵：前兩份都走驗證分支，**一個跳過去重的掃描器會全綠**，
      而那正是最可能發生的 bug（上一輪讀完但還沒刪檔就被關掉）。
      守衛寫成**禁止式**：掃描器模組不得出現 `JSON.parse` 或 `parseIntake`
      （「必須呼叫 `deliver()`」擋不住「先自己驗一遍再呼叫」）
- [x] 2.4 只採納 `.json`（沿用 `agent-events.ts:254` 的先例）；以 node:test 驗其他副檔名不被讀取
- [x] 2.5 檔案大小的**雙重檢查**（`stat` 在前、讀回長度在後，比照 `fs-service.ts:228`）；
      以 node:test 驗超限者**未被解析**
- [x] 2.6 解析失敗的項目**原封留在落點**（不移走、不刪除、不改名），且不阻斷其後的項目。
      以 node:test 用**同一份檔案**驗兩種處置：寫入殘缺 → store 為空且檔案仍在 → 補完同一份 →
      該 intake 出現（**對照組**：改成解析失敗即刪除或改名 → 「補完後出現」必須變紅）
- [x] 2.7 解析失敗**不阻斷其後的項目**：以 node:test **同步呼叫一次壞的、`await` 它返回、
      再呼叫好的**，斷言後者進得來。**順序必須由呼叫建立，不可靠 `readdir` 或 watcher 的到達
      順序** —— 砍掉隔離目錄之後，「原封不動」與「從來沒有被處理過」在磁碟上完全相同，
      排序反過來這條就什麼都沒測到
- [x] 2.8 **永久性與暫時性拒絕的去向**：永久性（識別碼不合法、超長、型別不合、同內容重複）
      被消費且其後啟動不重複呈現；暫時性（達總量上限）原封留在落點並於上限解除後重新處理。
      以 node:test 各驗一次（**對照組**：把暫時性也消費掉 → 「上限解除後進得來」必須變紅）
- [x] 2.9 **投遞的處理不阻塞主行程**，啟動掃描**分批**進行、剩餘者留待下一批而非拒絕；
      以 node:test 驗大量投遞時掃描讓出 event loop（總量上限保護的是收件匣，不是主行程的
      工作量 —— 它必須先讀檔才判定得出）
- [x] 2.10 新模組的**註解中不得出現 `createServer`**、訂閱 API **不得命名為 `listen`**
      （`probe-core.mjs:321` 是純文字比對）；跑 `npm run probe:core` 確認

## 4. routing 的解析
