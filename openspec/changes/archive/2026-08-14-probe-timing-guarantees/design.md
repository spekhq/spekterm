## Context

前置調查（見 proposal）採到三件事：被測 renderer 會在執行中途被判定為不可見並進入背景節流
（rAF 停擺、計時器節流到 1 秒）；失敗的形狀是**畫面不更新**（CDP 往返 5ms／次卻等滿 18.2 秒）；
慢的形狀是**少數區間各卡數秒**，而它們在停用背景節流之後完全消失。

**證據的邊界要先講在前面**（本文件其餘部分都建立在它上面）：

- 唯一那則 `raf=0` 的現場**採自一輪 37/37 全綠的執行**。它證明狀態會發生，不證明「那些紅出自
  這個狀態」。
- 現象是偶發的（七輪中明確觀測到三輪，而三輪是**下界** —— 多數輪次只在啟動時判定過一次）。
- `hidden` 的**成因未確立**。虛擬螢幕上沒有視窗管理器、只有一個視窗，沒有東西可以遮住它。

因此本 change 的處置有一部分是**假說驅動**的，而 D7 是為此存在的：**鑑別力以多輪觀測建立，
不以單輪的一紅一綠建立**。

此外三個結構缺陷與上面那個假說無關，各自獨立成立：

1. **無限等待**：`docs/lessons/probes.md:336` 記載「對已 `close()` 的 CDP client 求值會無限等待，
   不拋錯、不逾時」——**記載了兩個月，從未修**。而 `pollFor` 的時限**只在兩次讀取之間檢查**
   （`instrument.mjs:185`），一次不返回的 `read()` 讓那個時限形同不存在。
2. **關閉即返回**：`quitGracefully`（`probe-terminal.mjs:415`）送出 SIGTERM 就返回，而主行程收尾
   時正在原子寫 `sessions.json`。同一形狀在 `probe-workspace.mjs:129` 更弱（連 `pkill` 都沒有）。
3. **哨兵缺席**：破壞性前提（寫入損毀內容）不成立時，那條斷言**仍然可能通過**。

## Goals / Non-Goals

**Goals:**

- 讓探針的執行環境**不再**把被測 renderer 推進背景節流，**並建立該處置確實有效的證據**。
- 讓「探針對被測 app 的每一次操作都會在有限時間內返回」成為**表達不出違反的結構**。
- 讓破壞性前提的成立與否成為**看得見的斷言**，且事後可確認被處置的正是那一份。
- 讓根因**下次還查得出來** —— 處置哪天失效時，輸出要說得出「沒有 frame 被產生」。

**Non-Goals:**

- **不修 #6 / #7**（使用者已裁決）。
- **不動任何產品程式碼。** 背景節流是 Chromium 對真實情境的正確行為。
- **不拆 `runMode`**（#21 的建議）。
- **不查明 `hidden` 的成因**（見 Open Questions —— 處置不依賴它，但**有效性依賴它**，故以 D7 補償）。
- **不在本 change 關閉 #17 / #19 / #21**（見 proposal）。

## Decisions

### D1. 旗標一律加，不只在虛擬螢幕上加

`electronExtraArgs()` 現有的兩個旗標（swiftshader）**只在虛擬螢幕模式回傳**，因為它們補的正是
「虛擬螢幕沒有 GPU」。直覺會把新旗標放進同一個判斷。

**不這麼做。** 新旗標補的是「視窗不可見時不要節流」，而**那與螢幕是虛擬還是實體無關**：
`PROBE_DISPLAY=physical` 是給人親眼看的逃生口，人一旦切到別的視窗，同一個失效方向就回來了。

**取兩個旗標**：`--disable-backgrounding-occluded-windows`（遮蔽觸發的背景化）與
`--disable-renderer-backgrounding`（不可見觸發的降權）。

> **兩個旗標涵蓋的是兩條不同的路徑，而我們不知道走的是哪一條。** 觀測到的只有
> `visibilityState === 'hidden'` 且 `hasFocus() === true`；「遮蔽」是推論，而虛擬螢幕上根本
> 沒有東西可以遮住那個唯一的視窗。因此這裡**不是**「兩個旗標哪一個承重」的問題（那是效率），
> 而是「**有沒有一個有效**」的問題（那是有效性）—— 由 D7 回答。

**替代方案（已否決）**：產品層設 `webPreferences.backgroundThrottling: false`。它會讓**真實
使用者**的視窗被遮住時也不節流（耗電），為了驗收而改變出貨行為 —— 方向反了。

### D2. frame 的證據：實作手段由 spike 決定，spec 只描述能力

需要的能力是：**判斷兩個時點之間有沒有 frame 被產生**，而且取樣本身**不得 hang、不得在被測
頁面留下常駐物**。

| 候選 | 形狀 | 實測（spike，2026-08-14） |
|---|---|---|
| **A. 畫面時鐘** `document.timeline.currentTime` | 同步、純讀取、零副作用 | **成立** —— 見下表 |
| **B. 一次性動畫框回呼** `requestAnimationFrame(() => { window.__rafSeen = true })`（**不 await**），下一次求值讀旗標 | 不阻塞、非常駐 | 成立（隱藏時未執行、重新顯示後補跑），但會在頁面留一個布林 |
| C. 常駐 rAF 計數器 | —— | **已否決**：等同執行期注入的測試分支 |
| D. `await` 一次 rAF 回呼 | —— | **已否決**：在正好要偵測的那個狀態下永遠不 resolve —— **一個為了診斷 hang 而寫的探測，自己會 hang** |

**採 A**（同步、零副作用）。**它是實測的，不是推論的** —— 本 repo 已兩次栽在「從語意推論 API
行為」上，而若 A 不成立，它就是一個**永遠不會說話的診斷**，其單元測試卻**一條都不會紅**
（那些只驗欄位被帶回與純函式的兩個方向）。

spike 以「自己起一個 `BrowserWindow` 再 `hide()`」造出停擺狀態（測的是引擎的性質，與被測的
是不是產品頁面無關）：

| | rAF ticks | `document.timeline.currentTime` | `performance.now()`（對照組） |
|---|---|---|---|
| 視窗可見（1.5 秒） | +85 | **+1539.7** | +1503 |
| 視窗隱藏（2.5 秒） | **+0** | **+0**（凍結於 1556.4） | +2503 |

**對照組是承重的**：`performance.now()` 前進了 2503ms，證明兩次取樣確實隔了那麼久 —— 於是
「timeline 沒動」不可能是「取樣太快」。

> **由實測帶出的實作約束（原設計沒有寫到）**：**兩次取樣的間隔必須明顯大於一個 frame**
> （60Hz 下約 16.7ms）。間隔太短時兩次可能落在同一個 frame 內，畫面時鐘本來就相同 ——
> 那會**誤報「沒有 frame」**。取 250ms（與 `pollFor` 的預設輪詢間隔同級）。
> B 案沒有這個問題，但它需要跨兩次求值，反而更難安排。

**不進 `ok` 判定**（既有 `DIAGNOSTICS` 的同一條理由）：進了判定就改變那七條紅**自己的判準**，
日後將分不出「紅燈變了」是因為採證還是因為判準。

**spec 只描述能力，不指定手段** —— 於是 spike 的結果不會推翻已寫下的 requirement。

### D3. CDP 的每一次往返都有時限，且連線關閉即失敗

四處收口：

| 缺口 | 現況 | 處置 |
|---|---|---|
| 已送出、回應永不抵達 | `send()` 靠 message id 配對，無時限 | 每次往返給時限，逾時 reject 並**載明方法名** |
| 連線已關閉，pending 掛在半空 | `ws.close()` 之後那些 promise 永遠不 resolve | `close` / `error` 時把 pending 全部 reject |
| 連線關閉**之後**才發起的往返 | 送進關掉的 socket，永遠不返回 | 記已關閉旗標，**立即**拋（不等時限） |
| 握手與目標探詢 | `connect()` 只等 `open`／`error`；`waitForPageTarget` 的 `fetch` 無逾時 | 各自給時限（`fetch` 取 **3 秒** —— 它打的是 loopback 的 `/json/list`，而它的外層窗口是 30 秒，時限取得太大就等於沒取） |

**往返時限取 30 秒**，與 `waitForPageTarget` 的窗口同級。它是**癱瘓的防線，不是效能的閘門**：
觀測到的病態阻塞是 5–10 秒級，而停用節流之後同樣的段落 184 次往返合計 2.2 秒。

**逾時之後連線仍然可用** —— 只移除該次 pending。

> **一次逾時 ＝ 一次段落中斷，這是刻意接受的代價，必須寫出來。** 原提案宣稱「呼叫端多半在
> `pollFor` 之內，下一輪會重試」——**那是錯的**：`pollUntil`（`cdp.mjs:219`）沒有傳
> `tolerateErrors`，而 `pollFor` 在未開容忍時會**立刻把例外往外拋**（`instrument.mjs:181`）。
> 於是一次 30 秒的往返逾時會讓該段落中斷。
>
> **仍然接受它**：段落中斷是**有邊界、有堆疊、會被段落隔離接住**的失敗，而 hang 會讓整輪永遠
> 不結束（#22 的 1.5 小時）。兩者不同級。**不順手把 `pollUntil` 改成容忍** —— 那會把每一條
> 「等不到就紅」的斷言變成「等不到就重試到窗口耗盡」，改動的是十一支探針數百條斷言的語意，
> 遠超本 change 的範圍。

**時限要可注入**（`connect(target, { createSocket, callTimeoutMs, connectTimeoutMs })`，預設取
具名常數）：否則單元測試造不出「回應永不抵達」——每條逾時測試都得真的跑 30 秒，而 `npm test`
的定位是**秒級、可隨時跑**。既有八處 `connect(target)` 的呼叫姿態不變。

### D4. 關閉被測 app 要等它真的結束 —— 作用域涵蓋兩支探針

形狀：送出訊號 → 等 `exit` 事件 → 逾時（**10 秒**）則 SIGKILL 並輸出一行。

- **時限不可省。** 少了它就是把競態換成 hang —— 那正是 #22。
- **10 秒的理由**：`probe-terminal.mjs` 有 13 處呼叫，而 `docs/lessons/probes.md:328` 記載
  「面板留有未存變更時關閉會觸發原生對話框，它會擋住主行程訊息迴圈使 SIGTERM 失效」——
  那條路徑上每一次都會吃滿時限。10 秒遠小於段落時限（8–14 分鐘），13 次全部吃滿也只有 130 秒。
- **升級要出聲**：「app 沒有在時限內回應 SIGTERM」本身就是關於產品的資訊。
- **不用 `pollFor`**：等的是事件，不是輪詢。既有守衛（`wait-source.test.mjs`）的判準是「迴圈中
  的 `Date.now()` 比較」，事件 ＋ `Promise.race` 不落在其中，也不該為了通過守衛改寫成輪詢。

**作用域（原提案判斷錯誤，經實作再次修正 —— 兩次都是往擴大的方向）**：

第一次修正是加入 `probe-workspace`：它關閉後立刻以同一個 profile 重啟，隨即斷言「清單順序跨
重啟還原」與「字型偏好跨重啟還原」—— **被斷言的正是舊行程收尾時寫的那份檔案**，而它的
`close()` 是九支裡最弱的（`SIGTERM` ＋ `sleep(600)`，連 `pkill` 都沒有）。`:1101` 的註解記載
該條曾在第二輪 `test:e2e` 紅過並歸因為「列還沒渲染」；**關閉端的寫檔競態是那次歸因未曾排除的
替代解釋**（CLAUDE.md 對「兩個行程共用 userData、後寫的贏」已有明文警告）。

**第二次修正發生在實作時，理由是「載體」**：spec 那條「同一資料目錄重啟前一律等待」需要一個
**會變紅**的載體，而一份稽核紀錄不會變紅。唯一可執行的守衛判準是「**探針中不得直接送出
graceful 終止訊號，一律經單一入口**」——「這個站點之後會不會以同一個 profile 重啟」**靜態
判定不出來**，而一個判定不出來的守衛等於沒有守衛。

於是**全部五個 graceful 站點一律收斂**（`SIGKILL` 的連根拔除路徑不在此列，那是另一回事）：

| 站點 | 原本 | 收斂的理由 |
|---|---|---|
| `probe-terminal` `quitGracefully` | `SIGTERM` 即返回 | issue #8 本體，13 處呼叫 |
| `probe-workspace` `close` | `SIGTERM` ＋ `sleep(600)` | 同 profile 重啟 ＋ 跨重啟斷言 |
| `probe-files` `close` | `SIGTERM` ＋ `sleep(400)` ＋ `pkill -9` | 風險本身不成立（`pkill -9` 之後舊行程不會寫檔），**但單一入口是守衛的前提** |
| `probe-openspec` `close` | 同上 | 同上 |
| `probe-core` 收尾 | **`SIGTERM` ＋ `Promise.race([exited, sleep(5000)→SIGKILL])`** | **它已經是 `quitAndWait` 的手寫版** —— 留著就是第二份實作 |
| `probe-shell` 收尾 | `SIGTERM` | 成本為零 |
| `probe-identity` 收尾 | Linux 走 `process.kill(-pid, 'SIGKILL')`，**win32 才 `SIGTERM`** | 那個 fallback 分支同樣經入口；SIGKILL 那條不動 |

**收斂的獲得不只是一致性**：`probe-core` 那份手寫等待證明了這個需求本來就存在於別處，而它
**與 `wait-source.test.mjs` 擋手寫等待迴圈是同一條紀律** —— 一個由紀律維持的假設，擋不住下一份
被順手寫出來的實作。

### D5. 破壞性前提要有兩條不變式，不是一條

`runRestore` 的損毀韌性段落補：

1. **寫入之後、重啟之前**，讀回該檔並斷言其內容確實仍是損毀的。
2. **重啟之後**，斷言被隔離的那個 `.corrupt-` 檔的**內容就是我們寫進去的那一份**
   （現況只數 `quarantined.length === 1`）。

**第一條只覆蓋一半的時序**：競態是「舊主行程的 rename 蓋掉損毀內容」，若那次 rename 落在哨兵
**之後**、啟動**之前**，哨兵照樣綠而斷言照樣驗錯東西。**第二條在任何時序下都成立** —— 它證明
被隔離的正是我們寫進去的那一份，而那正是這條斷言宣稱在驗的東西。

> **對照組跑出來的東西比預期強（實測）**：把損毀內容覆蓋成 `[]`（**合法 JSON、只是 schema 不符**）
> 之後，產品**照樣隔離了它** —— 於是既有那條「照常啟動，且原檔保留」**仍然通過**
> （分頁＝0、隔離檔＝1）。也就是說 #8 描述的假綠不只在「被覆蓋回一份正常的 session 清單」
> 時發生，**任何一份會被隔離的內容都會讓它通過**。第二條不變式抓到了（隔離檔內容是 `[]`
> 而不是 `{ 損毀的內容`）。**它擋的不只是時序競態，還有「隔離的是別的東西」。**

D4 讓競態不再發生；D5 讓它下次再發生時**看得見**。三者不互相取代。

### D6. 文件與票的更新，屬於本 change 的交付

- `docs/lessons/probes.md`：記入現場、失敗的形狀（畫面不更新 vs 連線變慢）、慢的形狀
  （少數區間各卡數秒 vs 每次往返都慢），以及判讀規則。**並更正 #17 那條教訓的實例**。
- `CLAUDE.md`：「探針跑在虛擬螢幕上 —— 而那限定了驗收的效力」補上第二條限制（不覆蓋背景節流）。
- 票：**#8 / #22 關閉**（有修法、有對照組）；**#17 / #19 / #21 加註採證後保持 open** ——
  它們的內容有一半在本輪**未重現**，而一個未重現的現象不能用一個未驗證的機制結案。

### D7. 處置的鑑別力：多輪觀測，不是單輪對照

**這是本 change 最容易被跳過、而跳過就等於沒有對照組的一步。**

現象偶發（下界 3/7），所以：

- **單輪的一紅一綠說明不了任何事。** 前置調查自己就有反例：同一段落、同樣無旗標，
  `openspec-basics-1` 紅而 `openspec-basics-2` 全綠。
- 驗收因此是：**加旗標後連跑 N 輪**（N ≥ 8，對應 3/7 的基準率下「連續 N 輪都沒撞到」的機率），
  每輪同時以外部觀測記錄 `vis=` 與 frame 狀態，並記錄紅燈數與 CDP 阻塞區間數。
- **判準取「≥2s 的往返區間數」而不是總耗時** —— 前者是那個病的直接指紋（無旗標 11 個／4 個，
  有旗標 0 個），後者會被段落長度稀釋。
- **外部觀測必須在旗標側也採到**（前置調查只採到無旗標側；`watch-openspec-flag.log` 是 0 bytes，
  因為那一輪 12.5 秒就跑完而觀測者晚了）。**沒有旗標側的 `vis=` 資料，就無法區分「處置有效」
  與「這 N 輪剛好沒撞到」。**

## Risks / Trade-offs

**[處置可能根本無效（成因未確立）]** → 這是本 change 最大的風險，由 D7 直接處理。若 N 輪觀測
仍撞到 `hidden`，則旗標無效，**結論要照實寫**：#17 / #19 / #21 保持 open（本來就不關），
而 D2 的診斷成為下一輪調查的器材。**此時本 change 的其餘四項仍然成立**（它們與這個假說無關）。

**[旗標掩蓋了產品在背景節流下的真實缺陷]** → 沒有任何 requirement 描述它，而真實環境中「視窗
被遮住時停止渲染」是正確的。處置是**把作用域限制寫進 spec**，形狀比照 `terminal-sessions` 既有
的「自動化驗收通過 SHALL NOT 被詮釋為畫素正確」。

**[CDP 逾時 ＝ 段落中斷]** → 刻意接受，理由見 D3。**這個代價原本被一句錯誤的「會重試」掩蓋著**。

**[`quitAndWait` 引入新的 hang]** → 由它自己的時限與 SIGKILL 升級擋住。

**[frame 診斷是一個永遠不會說話的欄位]** → 由 D2 的 spike 擋在交付之前。若 A 案不成立而改用
B 案，spec 不需要改（它只描述能力）。

**[`awaitMounted` 的診斷取樣自己拋錯]** → 「等不到掛載」最常見的原因就是 renderer 不在了，
而此時 `evaluate` 會拋。取樣**必須**包 try/catch 並照常回傳原值 —— 否則十一處呼叫端會從
「回傳最後的判定物件」變成 throw，而 `describeMounted(value)` 正是為「判定沒有回傳值」準備的。

**[耗時基準改變]** → 預期會變快。收尾時記錄新基準並註明**與舊數字不可比**（舊的那些輪次有一部分
跑在節流狀態下，而那件事在當時看不見）。

## Open Questions

- **`hidden` 的成因是什麼？** 未查明。虛擬螢幕上沒有視窗管理器、只有一個視窗。它一旦被查清楚，
  可能讓 D1 的兩個旗標其中之一（或兩者）變成不必要 —— 也可能顯示兩者都無效。**D7 的觀測是這個
  未知的替代品，不是它的答案。**
- **那些 5–10 秒的單次阻塞是什麼？** rAF 停擺解釋得了「畫面不更新」，解釋不了
  `Runtime.evaluate` 的送達延遲（它不需要 frame）。可能是被節流的 main-thread task 排程，
  也可能是另一個獨立現象。**它在停用節流後消失（0 個 ≥2s 區間），所以處置涵蓋了它** ——
  但機制未確立，不得寫成已知。
