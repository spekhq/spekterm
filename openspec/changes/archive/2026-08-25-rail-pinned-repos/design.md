## Context

rail 今天是一個 `<ul className="flex-1 overflow-y-auto">`，內容依序是：全域項目（`RailRow`，
`folderId: null`）、一條 `aria-hidden` 的分隔線、然後 `folders.map()`。**清單的順序就是呈現順序**
—— `workspace-folders` 與 `global-session` 各有明文，並且各自帶著一段「rail 的列位置與 folder
清單的索引相差一位，SHALL NOT 當成同一個座標系」的警語。這個 repo 已經被那個 off-by-one 咬過
三次（拖曳落點、`Shift+↑`、`Shift+↓` 各一次），因此**任何會讓「呈現順序」與「清單順序」分家的
設計，成本都遠高於它看起來的樣子**。

拖曳排序走 `useDragReorder`（滑鼠事件自製，非 HTML5 DnD），命中判定以各項目**中線**回傳一個
**插入點** `0…count`，提交前經 `commitIndex()` 換算成序位；`onMouseDown` 已濾掉非左鍵。捲入
可視範圍走 `useScrollIntoView`，它以 `scrollIntoView({ block: 'nearest' })` 實作，觸發條件壓成
一個純量 key。

本 change 要在這之上加一個 pinned 狀態，並讓 pinned 的那一段**不隨 rail 捲動**。

## Goals / Non-Goals

**Goals:**

- pinned 是 workspace 的持久狀態，重啟後還原。
- **呈現順序仍然等於清單順序**；與移動有關的列空間是唯一刻意引入的第二種索引（D1／D3）。
- pinned 段（全域項目 + pinned folders）在 rail 捲動時留在視野內。
- 兩個 pin 入口（hover 圖釘、folder 右鍵選單），以及「拖過分界即改變 pin 狀態」。
- 全域項目恆為 pinned 段的第一列，且該狀態不可取消。
- 置頂段不得讓「捲入可視範圍」這條既有要求靜默失效。

**Non-Goals:**

- **不限制 pinned 的數量**（使用者裁決）。改以**保證其餘段的最小高度**承接極端情況 ——
  那不是對 pin 數量的上限，而是對「下半段必須還能用」的直接編碼（D2、Risks）。
- 不改變 `Ctrl+↑↓` / `Ctrl+Tab` 的巡覽規則 —— 它們照呈現順序走，而呈現順序沒有改變。
- 不為 session 子列或分頁加 pin。這個 change 只處理 rail 的**項目**。
- 不做「最近使用」之類的自動排序。未 pinned 那一段仍然完全由使用者手排。

## Decisions

### D1 —— 資料模型：per-folder 旗標 ＋「pinned 恆佔清單前綴」的不變式

`PersistedFolder` 新增 `pinned?: boolean`。**同時在 `WorkspaceStore` 內強制一條不變式：
pinned 的 folder 恆佔清單的前綴。** 載入時以**穩定分割**正規化（手改過的檔案不因此被隔離 ——
那是外觀問題，不值得讓使用者整個 workspace 消失），其後每一次變動都維持它。

於是**呈現順序 ≡ 清單順序**：rail 的列渲染與 `Ctrl+↑↓` 的巡覽都不必動。

**但這不等於「沒有第二個座標系」。** D3／D8 為拖曳與 `Shift+↑↓` 引入了一個**含分隔線的列空間**
（`folders + 分隔線`），它與 folder 索引在分界之下相差一位。那是**刻意引入**的，因為分界必須是
一個到得了的落點；代價是**凡與移動有關的索引都必須一致地待在列空間裡**（`count`、`rectOf`、
`onMouseDown` 傳入的索引、`isDropTarget`、`dropAtEnd`、`drag.fromIndex` 的比較），換算只在提交
那一處發生。D1 保證的是「清單本身不需要第二種順序」，不是「沒有第二種索引」——
**這兩件事此前被我寫成同一件，那正是這個 repo 咬過三次的那類混淆。**

考慮過的替代方案：

- **只存旗標，呈現時才做穩定分割（不動陣列）。** 好處是 unpin 之後 repo 會回到它原本在未 pinned
  段裡的相對位置。**否決** —— 它讓呈現索引 ≠ 清單索引，正是上面那個咬過三次的東西。代價是
  unpin 的落點要另外定義（見 D9），那是一次性的、寫得下來的規則。
- **workspace 層存一個 `pinnedCount`。** 「pinned 散落在中間」會**表達不出來**，比旗標更結構化。
  **否決** —— `remove` 必須依被移除者的位置有條件地遞減，那是一個新的、會被忘記的義務；而一個
  越界或錯誤的 count 會**靜默地把 folder 標成另一種狀態**。per-folder 旗標的 `remove` 一個字
  都不必改（前綴性質自動維持）。不變式改由 store 的單一私有方法擔保（D7）。

`pinned` 是**使用者意圖**，與 `hasOpenSpec` / `branch` 那兩個「衍生狀態一律不落盤」的欄位不同類
—— 它沒有磁碟上的事實可以重算。

### D2 —— pinned 段**位於捲動容器之外**，不用 CSS sticky

rail 的 `<aside>` 底下改為兩個並列的 `<ul>`：pinned 段（不捲動）與其餘段
（`flex-1 min-h-0 overflow-y-auto`，即今日那個捲動容器）。分隔線是 pinned 段的最後一列。

> **本決策是在估算 tasks 時翻案的**（原本選的是 `position: sticky; top: 0` 留在同一個捲動
> 容器內）。翻案的理由不是美感，是三件當時沒算到的事 —— 記在這裡，因為「為什麼不是 sticky」
> 是往後最可能被重問一次的問題。

**兩者在「pinned 段裝得下、且沒有人呼叫 `scrollIntoView`」時看起來一樣** —— 都是從捲動位置 0
就固定在頂端。但它們**不等價**，而差異全部落在對我們不利的那一側：

1. **遮擋問題從結構上消失（決定性的一條）。** 捲動容器的視口從 pinned 段的下緣才開始，容器內的
   元素**不可能**被它蓋住 —— `scrollIntoView` 沒有東西要避讓。這刪掉的不只是幾行 CSS，是一整套
   「量測 pinned 段高度 → 寫進 CSS 自訂屬性 → 只施加於未 pinned 段的目標」的機制，以及它
   「用到上一輪高度」的時序風險。本 repo 的判準是明確的：**使不變式無法被違反的結構，勝過由
   避讓機制維持的不變式。** sticky 在這裡不只是「要多做一點事」，它是**主動製造**了那個要避讓
   的東西。
2. **內容過高時仍然到得了。** `top: 0` 的 sticky 元素一旦高於視口，**它自己的下半永遠捲不到**；
   移出捲動容器的區塊可以自己內部捲動。
3. **`scrollHeight` 的變動來源比較少。** pin／unpin 與子列展開不再改變**其餘段**的
   `scrollHeight`，於是瀏覽器的 scroll anchoring 少了一批候選 —— 而這個 repo 的驗收已經因為
   anchiring 假綠過一次。

> **這裡曾經有一條「驗收改動量差一個數量級（26 處選擇器）」的理由，它是錯的，已刪除。** 實際是
> **18 處**，而且前提就不成立：sticky **不需要**多包一層 `<div>` —— `position: sticky` 直接掛在
> pinned 的那幾個 `<li>` 上就行，**零個選擇器要改**。（那個變體真正的問題是「一整段變動高度的
> 東西」很難用逐列 sticky 做對，那才是否決它的理由，而不是選擇器。）留著這段，是因為一個**可以
> 被一段話推翻的理由**，比沒有理由更糟 —— 它會招來它想擋的那次改回去。

**這個選擇也有它自己的帳，而且不便宜**：捲動容器從一個變成兩個之後，**拖曳的命中判定不再健全**
（見 D3 的「裁切」一節），而且 flex 的收縮會波及 `<h2>` 與底部的加入入口（見下）。

**版面的三個約束（缺一不可，前兩個是實測出來的）**：

- **`<h2>` 與底部的加入入口要 `shrink-0`。** 它們同樣是 `<aside>` 的 flex item、收縮因子同為 1，
  於是負的剩餘空間會分給**三個**項目而不是一個。`<h2>` 帶著 `truncate`（`overflow: hidden`）
  ⇒ 自動最小尺寸為 0 ⇒ **實測從 35px 被壓到 22px，標題文字被裁掉**。
- **其餘段要有最小高度**（使用者裁決）。其餘段是 `flex: 1 1 0%`，縮放收縮因子為 `1 × 0 = 0`
  —— 它不會收縮，但也**拿不到任何剩餘空間**，實測會直接變成 `clientHeight: 0`。**這不是
  「pin 太多」才會遇到的事**：一個 repo 都沒 pin，光是全域項目展開十來個 session 就到得了
  （見 Risks）。最小高度直接編碼「下半段必須還能用」，而不是限制使用者能 pin 幾個。
- **pinned 段 `min-h-0 overflow-y-auto`**，使它在極端情況下自己內部捲動，內容不會變成不可達。

翻案要付的帳，還有一筆在 spec 上：`keyboard-navigation`「捲入可視範圍」的表格裡，`Ctrl+Tab`
那一列寫著「該 session 的子列位於 rail 的**同一個**捲動容器內」。pinned repo 的子列從此位於捲動
容器**之外** —— 而該要求真正的不變式是「目標可見」，對一個不會被捲走的目標**恆常成立**。該表格
的措辭隨本 change 一併修訂。

### D3 —— 分隔線是一個**真正的落點列**；pin 狀態由落點推導，拖曳機制不多帶一個位元

命中判定的列集合從「folders」擴為「**folders ＋ 分隔線**」，即 `useDragReorder(folders.length + 1, …)`，
`rectOf` 對分隔線那一列回傳它自己的 DOMRect。提交時把落點（列空間）翻譯成 `(folderIndex, pinned)`：

```
S  = 分隔線的列索引（＝ 當下的 pinned 數）
S' = S - (fromRow < S ? 1 : 0)      // 移除被拖曳項目之後，分隔線的列索引
toRow                               // ＝ onCommit 交來的 toIndex（列空間）
pinned      = toRow <= S'
folderIndex = pinned ? toRow : toRow - 1
```

> `commitIndex()` 是 `useDragReorder` 的**模組私有**函式，呼叫端拿不到，也**不要為此 export 它**
> —— `onCommit(fromIndex, toIndex)` 交來的第二個參數就是換算後的 `toRow`。

**為什麼要這樣，而不是在 `useDragReorder` 上多掛一個「指標在分界哪一側」的位元**：

- 分界兩側各自是一個**真正到得了的落點**（`insertAt = S` ＝ pinned 段的最後一格、
  `insertAt = S + 1` ＝ 未 pinned 段的第一格），於是 `workspace-layout`「拖曳的落點與插入指示線
  一致」那條**原封不動地成立** —— 指示線畫在插入點那一列之前，兩個落點畫在分隔線的上方與下方，
  各自對應正確的結果。
- **「拖到自己原本的位置為無操作、且不畫指示線」也原封不動地成立。** 這一條是關鍵：把最後一個
  pinned repo 拖到分隔線**下方**時，它的 folder 索引其實**沒有改變**（`folderIndex` 前後同值）
  —— 若沿用 folder 索引來判斷「有沒有移動」，這個**只改變 pin 狀態**的拖曳會被判為無操作而
  靜默丟失。在列空間裡它是 `fromRow = S-1 → toRow = S`，**確實移動了一列**，既有的閘門自然放行。
- `useDragReorder` 的**檔案**一行都不必改，它仍然被分頁列與 session 子列共用。

**分隔線放在兩個 `<ul>` 之間，作為它們的 sibling —— 不放在 pinned 段之內。**
若放在 pinned 段之內，它會是該段的**最後一個**子節點，於是該段一旦內部捲動，它就是**第一個
離開視野**的東西 —— 而 spec 要求它於任何捲動位置可見，D3 也倚賴「拖過那條線」是個穩定的目標。
放在兩段之間，它不屬於任何捲動容器，那兩個性質才真的成立。它仍然是一個命中列（`rectOf` 需要
它的 ref）。全域項目仍不進命中集合（`global-session`：它不可拖曳、也不作為落點）。

**列空間必須貫徹到底 —— 這是最容易漏的一半。** 除了 `count` 與 `rectOf`，下列每一處都要換成
列索引，漏掉任何一處都是靜默的：

| 位置 | 今日 | 改為 |
|---|---|---|
| `onMouseDown(index, …)` | folder 索引 | 列索引 |
| `isDropTarget(index)` | folder 索引 | 列索引 |
| `dragged={drag?.fromIndex === index}` | folder 索引 | 列索引 |
| `dropAtEnd && index === folders.length - 1` | 最後一個 folder | **列空間的最後一列** —— 全部 folder 都置頂時那是**分隔線**，否則是最後一個未置頂 folder |

漏掉第一列的具體後果（`S = 0` 時）：拖曳 folder 0 到它自己的下半部會算出 `commitIndex(0, 2) = 1`
≠ 0 ⇒ **畫出一條幽靈指示線，並送出一次會被 store 靜默吞掉的提交**；而既有探針只斷言「順序不變」
—— **假綠**。漏掉最後一列的後果：全部 repo 都置頂時，「拖到線的下面來取消置頂」這個唯一的手勢
**沒有任何指示線**。

#### 裁切 —— 兩個捲動容器讓命中判定不再健全

`insertAtFor` 依 **DOM 順序**掃描，並用**未裁切**的 `getBoundingClientRect()` 比中線。今天只有
一個捲動容器，DOM 順序與螢幕上的垂直順序**一致**，所以它是對的。pinned 段一旦內部捲動，被裁掉
的置頂列其 rect 會落在**其餘段的下方** —— 游標停在一個看得見的未置頂列上，掃描卻先命中一個看不
見的置頂列，於是**把一個使用者根本沒碰的 repo 置頂到任意位置**。

處置：**`rectOf` 回傳「該列的 rect 與其所屬容器可視區的交集」，完全被裁掉時回 `null`**。
`insertAtFor` 對 `null` 已經是 `continue`，於是看不見的列不會被選中，而可見的列仍然依螢幕順序
排列。**這件事做在呼叫端**（`WorkspaceRail` 的 `folderRectOf`），`useDragReorder` 因此仍然不必改。

### D4 —— 遮擋以**結構**消除，不引入任何避讓機制

D2 的直接結果：pinned 段不覆蓋在捲動容器之上，捲動容器的視口從它的下緣才開始，於是
`scrollIntoView` 沒有東西要避讓。**本 change 因此不引入 `scroll-margin-top`、
`scroll-padding-top`、`ResizeObserver`，也不引入任何量測 pinned 段高度的程式碼。**

這一段留在 design 裡，是因為**若日後有人把它改回 sticky，下面兩個坑會原封不動地回來**：

- **`scrollIntoView({ block: 'nearest' })` 會把目標貼齊視口上緣**，也就是貼到 sticky 段的底下。
  捲動確實發生、目標確實落在視口的座標範圍內、斷言確實會過、**使用者什麼都沒看到**。
- **教科書解法（在捲動容器上設 `scroll-padding-top`）是錯的。** 它只要一行，但它會把 sticky 段
  **自己的**目標弄壞：那些列位於視口的 `[0, N)`，落在加了 padding 的「最佳可視區」之外，於是
  `Ctrl+↑↓` 選中一個 pinned repo 時瀏覽器會**試圖捲動**去滿足它 —— 而該列是 sticky 的，捲動不會
  讓它移動，淨結果是畫面無故跳回頂端。那違反 `keyboard-navigation`「目標已完整可見時 SHALL NOT
  捲動」。正確的形式是掛在目標上的 `scroll-margin-top`，且**只施加於 sticky 段之外的目標**。

`keyboard-navigation` 的 spec 仍然保留「可見 SHALL 指未被遮擋」與對應的兩條 scenario ——
它們在目前的結構下恆為真，而那正是重點：**它們是防止上述回歸的載體**，不是一個需要程式碼去
維持的約束。

### D5 —— 圖釘的可見性規則：**它是狀態時恆常呈現，是入口時才 hover**

- **pinned 的項目恆常呈現圖釘**（實心）—— 它同時是狀態指示與 unpin 的入口。
- **未 pinned 的項目只在 hover 時呈現圖釘**（空心）—— 它只是入口，與既有的「＋」「✕」同一族。
- 全域項目恆常呈現，且**停用**（見 D6）。

理由：「它在不在分界之上」雖然也能表達 pin 狀態，但那要求使用者去對照分隔線的位置；而 unpin
的入口若只在 hover 出現，使用者無從知道這一列是不是可以 unpin 的。狀態與入口在這裡剛好是同一顆
控制項，可見性就依它當下是哪一種角色。

第二個入口是 **folder 標題列的右鍵選單**（今天只有 session 子列有）：「Pin to top」／「Unpin」
與「Remove…」。`ContextMenu` 是共用元件，鍵盤操作（焦點落在第一項、`↑↓` 循環、`Enter` 觸發）
已經在它裡面 —— **動它要跑 `probe:terminal` 與 `probe:files` 回歸**。右鍵不會啟動拖曳
（`useDragReorder.onMouseDown` 已濾掉非左鍵）。

### D6 —— 全域項目的**停用**圖釘，與「rail 不呈現不可操作的控制項」的張力

`workspace-layout` 有一條血淋淋的紀律：rail 曾有一顆 `◈`，它的 `onClick` 裡只有
`stopPropagation()`，因為「一顆長得像按鈕、按下去卻什麼都不發生的指示燈，會反覆消耗使用者的
注意力去確認它是不是壞了」，已被移除。全域項目要呈現一顆**點不下去**的圖釘，看起來正是同一件事。

**兩者的差別是可辨識的，而且 rail 上已有先例**：

- `◈` 的問題不是「不能點」，是它**沒有宣告自己不能點**，也不傳達任何狀態 —— 它與可點的按鈕
  長得一模一樣。
- 全域項目的圖釘帶著 `disabled` 與 `aria-disabled`、視覺上置灰、游標不是 `pointer`，且 tooltip
  說明它恆置頂。它**傳達一個狀態**（pinned，且不可取消），而那正是使用者需要知道的事。
- **同一個元件裡已經有這個先例**：folder 路徑失效時，那一列的「＋」是 `disabled` 的，並附一句
  說明。那顆按鈕從來沒有被當成 `◈` 的同類。
  > **但先例只能引用到這裡為止**：那顆「＋」用的是 `ICON_BUTTON_CLASS`，它**含 `cursor-pointer`
  > 且 `opacity-0` 直到 hover** —— 既不符合上一點所說的「游標不是 `pointer`」，也不適用於一顆
  > 要**恆常呈現**的圖釘。停用樣式要另外寫，不能直接沿用那個 class。

因此全域項目**不提供右鍵選單** —— 它沒有可移除、也沒有可切換的東西，一個只有停用項目的選單
才真的是 `◈` 的同類。

### D7 —— IPC：兩個具名操作，共用一個維持不變式的私有方法

`WorkspaceStore` 內部只有一處會改變位置與旗標：

```
private place(id, folderIndex, pinned)   // 唯一維持「pinned 佔前綴」的地方
```

對外兩個操作，因為 UI 真的是以兩種方式在想這件事：

| 操作 | 誰是權威 | 另一個怎麼推導 |
|---|---|---|
| `reorder(id, toIndex, pinned)` | **位置**（使用者拖到／按到那裡） | pin 由落點推導（D3） |
| `setPinned(id, pinned)` | **pin 狀態**（點圖釘／選單） | 位置為跨界的最小移動（D9） |

`pinned` 在 `reorder` 上是**必填**，不設「省略 ＝ 維持現狀」的預設 —— 呼叫端有兩個（拖曳、
`Shift+↑↓`），兩者都必須主動決定它，而一個會被忘記的預設值在這裡的失效是靜默的（跨界的移動
變成只換位置不換狀態，畫面上就是「它跑到上面去了但沒有被 pin」）。

既有的 `reorder` 語意保留：未知的 id 為無操作、越界的目標位置夾制於範圍內、只改順序不動內容。

#### 「只改置頂狀態」的移動會被**三道**閘門吞掉，不是一道

D3 論證了 `useDragReorder` 的提交閘門（`toIndex !== fromIndex`，在列空間裡成立）會放行。
**那只是第一道。** 同一條路徑下游還有兩道以 folder 索引為準的早退，而跨界的移動其 `folderIndex`
**前後同值**，兩道都會命中：

| 位置 | 現況 | 後果 |
|---|---|---|
| `WorkspaceStore.reorder`（`workspace-store.ts`） | `if (Number.isNaN(to) \|\| to === from) return` | **旗標不寫入、`save()` 不發生** |
| `useWorkspaceFolders.reorderFolders` 的樂觀更新 | `if (to === from) return current` | 本地複本保留舊的置頂狀態 |

兩道都必須改成「**位置與置頂狀態皆未改變**時才早退」。這正是 spec 那句「一次只改變置頂狀態的
移動 SHALL 仍被提交」要防的東西 —— 而它此前只在 design 的一個地方被論證為成立，論證只涵蓋了
三分之一。

（樂觀更新那一道尤其不能漏：`useWorkspaceFolders` 的註解已經記載，少了樂觀套用會讓**連按
`Shift+↓` 靜默丟失移動**；跨界的移動若被那道閘門擋下，同一個症狀會以新的形式回來。）

### D8 —— `Shift+↑↓` 跨越分界時改變 pin 狀態，而**分界本身算一格**

`Shift+↑↓` 是鍵盤版的「移動一格」，與拖曳共用 D3 的落點語意：最後一個 pinned repo 按 `Shift+↓`
→ 它變成未 pinned 段的第一個。**此時它在畫面上的位置幾乎沒有動** —— 動的是圖釘與分隔線。

考慮過：讓它跳過分界（直接與第一個未 pinned repo 交換並同時 unpin）。**否決** —— 那會讓
「剛剛 unpin、位於未 pinned 段第一個」這個狀態**用鍵盤永遠到不了**，而它正是 unpin 之後最自然的
落點（D9）。既有那條「選中全域項目時 `Shift+↑↓` SHALL 為無操作」不受影響：它連移動都不會發生。

**但「只有一個 folder 時為無操作」這條既有條款與本決策直接衝突，必須改。** 只有一個 folder 時，
它**永遠**與分界相鄰：未置頂時 `Shift+↑` 應該置頂它，置頂時 `Shift+↓` 應該取消置頂。無操作的
條件因此收窄為「**該次移動不跨越分界**」。**這個衝突用既有的 scenario 抓不到** —— 那條 scenario
只斷言「順序不變」，而在兩種讀法下順序都不變。

同一個機制也讓既有那條「到達端點時不循環」的 scenario 失效：選中第一個 repo 按 `Shift+↑`，
在新規則下會**置頂它**。「順序不變」字面上仍為真 ⇒ **探針保持綠燈，而 fixture 的置頂狀態已經
被改掉**，該段落其後每一條斷言都建立在被污染的狀態上。兩條 scenario 都要重寫。

### D9 —— unpin 的落點：跨界的**最小移動**

- `setPinned(id, true)` → 移到 pinned 段的**末端**。
- `setPinned(id, false)` → 移到未 pinned 段的**首端**。

兩者都是「跨過分界、走最短的距離」。這是 D1 的直接代價（陣列不再記得它原本在未 pinned 段的
相對位置），把它明訂下來就不會有人期待另一種行為。

## Risks / Trade-offs

- **其餘段會被擠成零高度，而且「一個 repo 都沒 pin」就到得了** → 實測：`<aside>` 的三個 flex
  item 中，其餘段是 `flex: 1 1 0%`（拿不到剩餘空間就是 0），於是**全域項目展開十來個 session
  ＋ 視窗矮一點，整份 folder 清單就消失了**。今天那些列只是被捲走，捲回來就在 —— 這是**比現狀
  差的回歸**，不屬於「pin 幾個是使用者自己的決定」那個已接受的取捨（全域項目是被系統 pin 的）。
  → 處置（使用者裁決）：**保證其餘段的最小高度**（約三到四列），溢出的部分由 pinned 段內部捲動
  吸收。**不限制能 pin 幾個** —— 這條夾制編碼的是「下半段必須還能用」，不是 pin 的數量上限。
  → 殘留缺口：pinned 段本身仍可能高到需要內部捲動，那時分隔線之上要捲才看得完。已接受。

- **`aside > ul` 從一個變成兩個** → 5 處直接抓捲動容器的探針程式碼會抓到**第一個**（不捲動的
  pinned 段）。**失效方向是混合的，不是全部假綠** —— 這一點此前寫錯了：
  `probe-keyboard.mjs` 有兩處是 `scrollHeight > clientHeight + 10` 的前置 `check()`，它們會
  **大聲失敗**；而「SHALL NOT 捲動」那一批會**安靜地變綠**。
  → 緩解：兩個 `<ul>` **各自帶 `aria-label`**（自字典取得），探針以標籤指名捲動容器。
  → **對照組要小心**：因為有大聲失敗的那一半，一個「看到紅燈就以為驗證完成」的對照組會漏掉
  安靜的那一半。對照組必須分別確認兩種徵狀。
  → **而且只換容器還不夠**：`SELECTED_FULLY_VISIBLE`、`SELECTED_HEADER`、`FOCUSED_ROW` 是以
  `aria-current` 跨**兩個** `<ul>` 找列，卻拿**一個**容器的 rect 去量。選中的是置頂的 repo
  （或恆為置頂的全域項目）時，拿其餘段的 rect 去量必然得到「不可見」⇒ **對正確的實作亮紅燈**。
  列與容器必須成對取得。

- **「有載體」與「載體有鑑別力」是兩件事** → pinned 段與遮擋的每一條斷言，在 **rail 內容沒有真的
  超出可視範圍**時**恆為真**。`keyboard-navigation` 已經把這件事寫進要求本身（「驗收 SHALL 在
  項目數確實超出容器可視範圍的情況下進行」）。
  → 緩解：探針的環境必須種到 rail 真的捲得動，並且**先斷言它捲得動**（`scrollHeight > clientHeight`）
  再斷言其餘的事。遮擋那一條的斷言要寫成「目標的上緣 ≥ pinned 段的下緣」，而不是「目標在視口內」
  —— 後者對一個被完全蓋住的目標**照樣通過**，那正是這條要防的失效。

- **兩個 pin 入口 ⇒ 兩條路徑** → 只驗一條就放行，是這個 repo 反覆重演的「補一條 scenario 與
  覆蓋一條 scenario 是兩個動作」。
  → 緩解：圖釘與右鍵選單各自要有自己的驗收斷言，不共用。

- **分界兩側的兩個落點只差幾個像素，而指示線畫在一條本來就存在的線上** → 分隔線是
  `border-t` 一條 1px 的線加上 4px 的上下 margin。`insertAt = S`（置頂段末格）把
  `border-t-2 border-t-accent` 畫在**分隔線自己身上**，`insertAt = S + 1` 畫在第一個未置頂列
  上 —— 兩者相距不到 10px，而且前者疊在既有的 hairline 上。**沒有置頂 repo 時（每個使用者的
  初始狀態）尤其難分辨。**
  → 緩解：兩個落點的指示線要在視覺上可辨（顏色、粗細或位移），並且 spec 要明訂它們可辨。
  → **而且全 repo 目前沒有任何探針在驗插入指示線**（`grep border-t-accent scripts/*.mjs` 零命中）
  —— 既有那條「拖到自己原本的位置 SHALL NOT 呈現指示線」一直沒有載體，而本 change 讓指示線變成
  承重的。這一條要補。

- **「把 repo 拖到最上面」這個既有手勢的語意改變了** → 沒有任何置頂 repo 時，分隔線是第 0 列，
  於是分隔線中線以上的整片區域（含全域項目那一塊）都對應 `insertAt = 0` ⇒ **置頂它**。今天同一
  個手勢只是把它移到 folder 索引 0。這是使用者裁決「拖過界＝改變 pin 狀態」的直接推論，並非
  缺陷，但**它會發生在每一個既有使用者身上**，值得在發佈說明裡講一句。

- **側欄來源選單的順序會跟著置頂順序改變** → `PanelSourceBar` 依 folder 清單順序呈現。置頂會
  改變那份順序，於是它也跟著重排。**多半是使用者要的**，但沒有任何 spec 說過這件事。
  → 緩解：確認它確實是期望行為；若是，於實作時記一筆，不另開 requirement。

- **`aria-label` 同時是探針的選擇器** → 新增的圖釘與選單文案一旦與探針的字面值分家，症狀是
  「選不到元素」而不是「斷言失敗」。
  → 緩解：文案一律進 `en.json`，探針經 `scripts/lib/copy.mjs` 取用；**文案內不得出現單引號、
  雙引號、反引號**（探針的選擇器是用字串拼出來的，實測曾因一個所有格的撇號讓整個 evaluate
  throw，而畫面上沒有任何一條紅的斷言）。

- **舊設定檔的相容** → 沒有 `pinned` 欄位的條目一律視為未 pinned；正規化是 idempotent 的。
  **不升 `WORKSPACE_VERSION`** —— 舊版的 `parseWorkspace` 只挑它認得的三個欄位，多出來的
  `pinned` 會被忽略，於是新版寫出的檔案在舊版上仍然讀得起來（退版時 pin 狀態消失，folder 一個
  都不會少）。若改以升版處理，舊版會因 `version !== 1` 而**把整個 workspace 隔離**，那是遠差的
  失效模式。
