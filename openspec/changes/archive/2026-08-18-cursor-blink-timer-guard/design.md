## Context

`terminal-sessions` 的「渲染資源僅供當下顯示的終端」已經吃過一次教訓，把「釋放」的定義從
「移除產物」擴充成「**歸還並存額度**」（issue #24 / `webgl-context-release`）。

這次（#25 / #28）證明該路徑持有的資源**還有第三種**：一個週期性工作（游標閃爍，600ms）。
它與並存額度**各自獨立地**被釋放或不被釋放 —— 上游套件的缺陷讓額度歸還了、週期性工作沒停。

**既有驗收對此結構性地無感**：依「該終端的產物是否存在」判定者看不見（殘留者不留產物）；
依「並存額度是否歸還」判定者看不見（額度確實歸還了）；終端數、文件結構、session 清單皆不變。
它躲過九支探針數個月，最後由使用者回報「用久了變慢」而被發現。

當下的缺陷已由依賴升級（`d7d85fe`）解決。**本 change 要補的是「怎麼看得見它」**。

## Goals / Non-Goals

**Goals:**

- 讓「釋放時停止週期性工作」成為**可觀察、可失敗**的驗收。
- 判準不倚賴套件私有欄位、不倚賴建置產物行號、**不只認一種排程機制**。
- 該斷言**有鑑別力**：依賴退回 `@xterm/addon-webgl@0.19.0` 時必須變紅。

**Non-Goals:**

- 不改產品程式碼。
- 不做「偵測任何一種計時器洩漏」的通用機制 —— 那會把應用程式合法建立的計時器算進來，
  製造偽陽性，而偽陽性的下場是這條斷言被關掉。
- 不分離 #28 尚未定位的「顯示↔隱藏與銷毀哪一條漏得多」。

## Decisions

### D1：觀察對象是「週期性工作是否仍在執行」，而且要兩種互補的觀察

規格已把判準寫成機制中立的性質（不得取自私有欄位、不得取自建置產物位置、不得只認一種排程機制）。
設計層面採**兩種觀察並用**，各自補對方的盲點：

| 觀察 | 性質 | 盲點 |
|---|---|---|
| **存活的週期性計時器數**（攔截 `setInterval` / `clearInterval`，以週期長度過濾） | 精確、可數出**幾個** | 綁定「以 interval 排程」這一種機制 |
| **閒置時的畫面更新請求速率**（攔截 `requestAnimationFrame` 取樣） | **機制中立** —— 遞迴延遲呼叫或自我排程的更新請求同樣現形 | 只說「有沒有」，數不出幾個；且會被其他來源的更新請求干擾 |

被否決的兩個作法：

- **讀 `_cursorBlinkStateManager` 私有欄位** —— 名稱隨版本改變，套件重構時查詢**選不到而回傳
  零**，斷言於是變綠。本 repo 最常見的假綠形狀。
- **以呼叫點的檔名行號歸因 rAF** —— bundle 的雜湊與行號**每次建置都變**。（診斷時可用，
  排查期間的一次性工具即如此；但那是一次性的排查，不是要長期維護的斷言。）

### D2：注入是必要的，並且要正面回應 `mounted.mjs` 的既有結論

`scripts/lib/mounted.mjs` 檔頭寫著「**在頁面裡裝一個常駐計數器同樣不可取：探針不在產品程式碼
裡塞測試分支，那條紀律一樣適用於執行期注入**」。本設計做的正是注入，因此必須說清楚差別，
否則下一個人有現成的理由把這個段落否決掉：

1. **產品程式碼零改動**，注入只存在於探針的 CDP 連線內，段落結束即隨該 app 實例消失。
2. 攔截的是**平台 API**（`setInterval` / `requestAnimationFrame`），不是應用程式或套件的內部。
3. **關鍵差別：這裡沒有「不注入」的選項。** `mounted.mjs` 那條之所以成立，是因為當時存在一個
   不必注入的訊號（掛載後的可觀察狀態）。而本要求所防的失效**在外部完全沒有徵狀** —— 那正是
   它躲過九支探針的原因。選擇不是「注入 vs 更好的訊號」，是「注入 vs 沒有覆蓋」。

### D3：注入時機 —— 連上之後注入即可，不需要 `addScriptToEvaluateOnNewDocument`

**第一版設計此處是錯的**，記下來以免重蹈：原本要求「注入 SHALL 早於頁面自己的 script」，
並打算用 `Page.addScriptToEvaluateOnNewDocument`。但探針的 `launch()` 是**先啟動 electron、
再連上**，連上時頁面早已載入完畢 —— 該 API 只作用於其後建立的 document，對當下這份**一個字
都不會執行**。要生效必須注入後 `Page.reload()` 再等重新掛載。

**而這一步根本不需要**：段落自己 seed 的 profile 沒有任何持久化 session，第一個終端是段落
自己開的。連上後、建立任何 session 之前注入，即涵蓋全部週期性工作。
**「建立 session 前計數為零」這條前置斷言，同時就是「注入夠早」的證明。**

### D4：四個絕對數，不是「未增加」

**第一版設計此處也是錯的**：它把「基線」同時用於「一個終端顯示中＝1」與「全部關閉後回到基線」
兩處，而後者的正確值是 **0**。那個歧義容得下一個 `count <= 1` 的實作 —— 建立一個、關閉、
洩漏一個，照樣通過。

四個點各自釘死絕對值：

| 時點 | 期望 | 它擋住什麼 |
|---|---|---|
| 尚未建立任何 session | **0** | 過濾條件誤中其他來源；注入太晚 |
| 一個終端顯示且持有焦點 | **1** | 判定條件一個都匹配不到（恆零 ⇒ 後面全部空綠） |
| 切換若干次後全部關閉 | **0** | 承重斷言：釋放沒有停止週期性工作 |
| 終局後再建立一個終端 | **1** | **觀察在中途失效**（reload、渲染路徑掉回 glyph、補丁被蓋掉）⇒ 終局的零是空綠 |

最後一列是第一版沒有的。非零基線擋得住「開頭就數不到」，擋不住「基線之後才失效」——
而那兩者的終局值都是零，在輸出上無法區分。

### D5：焦點是承重前置，且失敗訊息必須能分辨四種失效

實測套件原始碼：週期性工作僅在 `isFocused` 為真時啟動（`isFocused` 還要求該終端的隱形輸入
元素持有焦點**且** document 本身持有焦點），失焦時暫停。**因此「顯示中」推不出「恰為 1」。**

段落 SHALL 確認焦點前提；且「恰為 1」失敗時，其 detail SHALL 帶上 document 焦點、
當前 focused 元素、以及渲染路徑 —— 否則**注入太晚／渲染路徑未生效／終端沒焦點／週期常數改變**
四種失效在輸出上完全分不開，而它們的處置各不相同。

實作前先做一次 spike 確認焦點在探針環境下確實成立（虛擬螢幕、無視窗管理員）。

### D6：動作序列涵蓋兩種轉換，且必須關掉「當下顯示中」的那一個

規格對「顯示→隱藏」與「銷毀」是**兩條分開的條文**，且主 spec 明寫「銷毀需要各自的條文與
各自的驗收」，並要求銷毀路徑的驗收**取樣於顯示中的終端**（已隱藏者的資源早已於轉為隱藏時
釋放，以它為對象的斷言在銷毀路徑失效時依然全綠）。

本段落**不為兩條各寫一個斷言**，理由：任一條漏掉都會讓終局計數高於零，一條斷言即可涵蓋，
分開反而要多付一趟啟動成本。**但那條紀律的實質不能丟** —— 關閉序列中 SHALL 至少有一次是
關閉**當下顯示中**的那一個，否則銷毀路徑根本沒有被走到。

### D7：以週期長度過濾，定義域是整個頁面

第一方程式碼沒有碰撞（renderer 唯一的 `setInterval` 週期是 60 秒）。但**過濾器作用於整個
頁面**，第三方（套件自身的其他計時器、dev 模式的工具）未普查。D4 的第一列（尚未建立 session
時為 0）就是讓這件事**可觀察**的地方：有其他來源落進同一個桶，它會先變紅。

若上游改變閃爍週期，第二列（恰為 1）變紅並指出「一個都沒數到」。**這是刻意的** ——
一個會在前提改變時變紅的過濾條件，優於一個會靜默漏算的。

### D8：段落安排與成本

`probe-terminal.mjs` 的**每個段落本來就各自 `launch()`**（21 處），序列執行、重複使用同一個
debugging port，因此**不需要**宣告前置、也沒有 port 爭用問題。（第一版設計此處引用了
`runPanelRestoreDegradation` 作為「自帶啟動」的先例 —— 那支段落在 `probe-openspec.mjs`，
與本段落無關。）

段落需依既有慣例掛 `onTimeout: killStrays`：逾時的段落不會走自己的 `finally`，漏了它會留下
electron 行程。

**成本**：一次 electron 冷啟動 + 四個量測點 + 建立／切換／關閉的往返，且**在 build 與 dev
兩個模式各跑一次**。以既有段落為尺標，預估每個模式數十秒。（第一版寫「數秒」，低估了一個
數量級。）

## Risks / Trade-offs

- **[焦點前提在探針環境不成立]** → 段落無法建立基線。以 D5 的 spike 先確認；失敗時 detail
  指得出是焦點問題。
- **[過濾條件與上游的週期常數綁定]** → 由 D4 第二列承接（變紅並指出「一個都沒數到」）。
- **[rAF 觀察被其他來源干擾]** → 它是**交叉檢查**而非承重斷言；承重的是計時器計數。
  若干擾使它不穩定，處置是縮小它的斷言強度，不是放寬計時器計數。
- **[注入與 `mounted.mjs` 的既有紀律相衝]** → 已於 D2 正面回應。若日後出現不必注入的訊號，
  本設計應被取代。
- **[本段落只證明「終局為零」，不證明「過程中沒有暫時性的多餘計時器」]** → 接受。
  規格要求的是釋放，不是任一瞬間的上界。

## 實作期間的量測結果，以及它們如何改變了本設計

以下每一條都是實測，且多數推翻了上面某個決定。留在這裡，因為**推翻的過程比結論有用**。

### R1：探針的操作方式決定了缺陷會不會出現 —— 這是本次最重要的發現

第一版段落以**點擊分頁**切換 session。在**含缺陷的版本**上，七條斷言**全綠**。

原因：點擊會把輸入焦點移到分頁元件上，於是即將被隱藏的終端**先失焦**，而失焦會讓底層套件
`pause()` 其週期性工作並清掉計時器 —— **缺陷被操作方式本身掩蓋**。

改成鍵盤（`Ctrl+Tab` 切換、`Ctrl+Shift+W` 關閉，焦點不移動）之後，同一個版本上承重的那條斷言
**正確變紅**（全部 session 關閉後仍殘留一個 600ms 計時器）。

**推論**：這也解釋了為什麼真實使用者比合成操作更早遇到它 —— 鍵盤是主要的切換方式。
此條已寫入 spec，因為它是任何未來實作都必須知道的前提。

> **若當初沒有跑對照組，這個 change 會交付一條永遠綠的斷言，並宣稱缺口已補上。**
> 這是本 repo「對照組是唯一擋得住假綠的東西」的一次實際發生。

### R2：所倚賴的版本在探針環境下游標閃爍不會啟動 ⇒ 本設計的載體無法出貨

同一個 app、同一個虛擬螢幕環境，只換套件版本：

| | 閃爍計時器 | 畫面更新請求 |
|---|---|---|
| `addon-webgl@0.19.0` + `xterm@6.0.0` | 建立（週期 600） | ~3.3/s |
| `addon-webgl@0.20.0-beta.298` + `xterm@6.1.0-beta.302` | **完全沒有** | **0.0/s** |

而**同一個 beta 在實體螢幕上的真實 app 中閃爍正常**（實測 1.7/s）。已排除：週期常數、
`isFocused` 實作、`decPrivateModes` 預設、`_restartInterval` 形狀、reduced-motion、
文字閃爍的 viewport 閘 —— 兩版的相關程式碼逐一比對皆相同。指向性最強的線索：同一個
`isFocused &&` 分支裡，5 分鐘的 idle timer 有被排、600ms 的 blink timer 沒有。
已回報上游：**xtermjs/xterm.js#6113**。

**後果**：非零基線（D4 第二列）在該版本上無法建立 ⇒ 段落無法武裝 ⇒ **不出貨**。
段落程式碼與量測模組**完整貼在 issue #29 的留言裡**（GitHub 是耐久的；本機的 `~/spekterm-diag/` 不在版控內，指向它等於指向會消失的東西 —— 本 repo 已經因此吃過一次虧），待上游解決後可直接放回。

### R3：改以「上游修正是否存在於安裝的產物」為代理載體

`scripts/xterm-blink-release.test.mjs`。它**不宣稱驗行為**，只擋「依賴被退回或被改成浮動版本」。
對照組**已實測**：退回 `0.19.0` 並 `npm ci`，第一條斷言變紅。

它另有一條防自身失準的斷言：先確認該欄位名仍存在，否則「找不到舊形狀」會被誤判為「修正還在」。

### R4：D8 的成本估算與段落安排更正

`probe-terminal.mjs` 的每個段落本來就各自 `launch()`（21 處），不需要宣告前置、無 port 爭用
（第一版誤引了 `probe-openspec.mjs` 的 `runPanelRestoreDegradation` 作為先例）。
實測單一段落在 build 模式約 18–30 秒。

### R5：交叉檢查的門檻寫錯過

「全部關閉後畫面更新請求回到閒置」原本設 `< 5 次/秒`，而**一個殘留計時器正好是 1.7 次/秒**
—— 它會放過自己要抓的東西，且該值就印在同一行的 detail 裡。應為 `< 1`。
**一個門檻若寬於它要偵測的訊號，它就不是門檻。**
