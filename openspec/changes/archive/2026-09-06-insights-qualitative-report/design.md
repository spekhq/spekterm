## Context

動機見 `proposal.md`。這裡只記與作法有關的現狀與約束。

**既有的三層已經到位**：`conversation-archive` 把來源 NDJSON 萃取成逐列存檔（含使用者訊息完整
內文）；`insights-aggregate.ts` 於**讀取時**彙總成 `Insights`；`InsightsOverlay` 呈現。
語氣分類目前也在讀取時計算（`classifyTone`），**存檔裡沒有任何分類結果** —— 這是易名不需要
資料遷移的原因。

**兩件本次實測、且各自推翻了一個直覺的事實**（2026-09-05，`claude` 2.1.261）：

1. **`-p` 的 prompt 與 stdin 會被串成同一則 user 訊息，而該記錄沒有 `isMeta`。**
   實測 `printf '…' | claude -p '…'` 產生的記錄是 `type: "user"`、`isMeta` 不存在。
   意思是：**跑一次讀後感，就會在 `~/.claude/projects/` 底下寫進一則約 200 KB 的「使用者訊息」**，
   而下一次掃描會把它當成真的使用者輸入。這正是 `docs/lessons/transcript.md` §一 記錄過的那個
   「最長 92 萬字元的 prompt 其實不存在」，只是這次是**我們自己製造**的。
   不處理的話，這個功能會逐次污染它自己分析的那份資料。
2. **`--output-format json` 回傳結構化結果**（`result` / `is_error` / `subtype` /
   `total_cost_usd` / `num_turns` / `permission_denials`），**不必解析散文判斷成敗**。

## Goals / Non-Goals

**Goals**

- 讀後感的每一條論斷都**可被機械查證**，查不到出處的**結構性地進不了報告**。
- 委派的產物**不進入**這個功能分析的資料集。
- 委派層與掃描層同形（注入式 spawn、單一併發、逾時、只回錯誤碼），可在 Electron 之外測。

**Non-Goals**

- **不做對話全文檢視器。** 既有規格已把原文呈現限縮在兩處，本次只增加第三處並給它上限。
- **不做自動排程。** 讀後感只在使用者按下時跑 —— 它要花錢，而自動花錢需要另一套同意模型。
- **不做多模型比較、不做報告之間的自動 diff。** 歷次報告並存且可各自打開就夠了；比較由人做。
- **不驗證真實委派。** 見下方 D8。

## Decisions

### D1：語料以 stdin 餵給 `claude -p`，不寫暫存檔、不讓它自己去讀

**選這個**：指令走 `-p` 引數，語料走 stdin，兩者由 CLI 串成單一 prompt（已實測）。

- **對照「寫成暫存檔、讓 agent 用 Read 去讀」**：那需要開放工具權限，讓一趟本該是純函式的委派
  變成 agentic（讀幾次、讀哪些由它決定，結果不可重現），而且**檔案內容一樣會進它的 transcript**
  （以工具結果的形式），沒有省下任何暴露，卻多了一份明文暫存檔。
- **對照「全部塞進 `-p` 引數」**：`ARG_MAX` 雖然夠，但語料會出現在行程的命令列上 ——
  同一台機器上任何一個 `ps` 都看得到。stdin 沒有這個問題。

**委派一律關閉工具。** 這趟工作不需要任何工具，而開著它就有可能去讀 repo。關閉之後
`permission_denials` 非空即為異常訊號。

### D2：委派在一個**專屬的空目錄**下執行，而同一個常數同時決定「排除誰」

D1 的代價是 Context §1 那則 200 KB 的偽使用者訊息。處置：

- 委派的 cwd 固定為 userData 之下一個**專屬的空目錄**。空目錄意味著它不會載入任何 repo 的
  `CLAUDE.md`、skill 或 settings —— **同一個決定順帶關掉了「repo 指示滲進分析」這條路**。
- 掃描時**排除該目錄所對應的專案目錄**。排除值**不是另外寫一份字串**，而是拿決定 cwd 的那個常數
  去跑 `encodeProjectDir()` 算出來的。**兩者因此不可能漂移** —— 這比「記得同步兩個地方」強，
  而本 repo 的教訓反覆是同一句：不接受某個東西要由結構保證。
- 委派結束後**刪掉它那一份 transcript**（`session_id` 在 JSON 輸出裡，路徑因此算得出來）。
  這不只是整潔：那是語料的**第二份副本**，落在我們的權限控制之外，而且會活 30 天。

**為什麼不用 `CLAUDE_CONFIG_DIR` 把它整個導去別處**（那才是最徹底的結構性隔離）：
`docs/lessons/transcript.md` 已記錄實測 —— 換掉設定目錄會**連認證一起換掉**，那一趟會認證失敗。
所以隔離只能做到「同一個設定目錄下的另一個專案目錄」，而排除與刪除兩件事一起補上這個缺口。

### D3：引用由**我們**查證，metadata 由**我們**填 —— 模型只負責挑句子

報告以結構化形式回傳，每條論斷是 `{ claim, quote }`。主行程逐條處理：

1. 把 `quote` 正規化（收斂空白）後，在語料中找**完全相符的子字串**。
2. 找不到 → **丟棄該條論斷**，並計入「已丟棄」。
3. 找得到 → 從**我們自己的存檔列**取出它的日期與專案，填進報告。

**模型不提供 metadata，因此它無法把一句話掛到錯的日期或錯的 repo 上。** 它唯一能做的是挑一句
真的存在的話 —— 而那句話存不存在，是可判定的。

- **對照「請它務必附上出處」**：那是靠「沒有人再送它」保證，不是靠結構。**agent 寫出來的東西永遠
  讀起來很有道理，包括它錯的時候**，而散文沒有對照組可言 —— 這是這整個功能唯一的守衛，不能是
  一句叮嚀。
- **「已丟棄」的條數要顯示在報告上。** 那個數字本身就是這份報告可信度的指標：10 條裡丟了 3 條，
  使用者就知道該用什麼態度讀剩下的 7 條。藏起來才是不誠實。
- 輸出可能被包在 markdown 圍籬裡 → 解析容許剝除圍籬，但**解析失敗即整份失敗**，不產出半份報告。

**上限**（與既有兩處同一族，理由相同：這三個位置都不該長成全文檢視器）：
單條引用 ≤ **60 字元**、每份報告 ≤ **20 條**論斷。

### D4：委派層與 `ScanRunner` 同形

新的 `ReportRunner` 沿用 `insights-service.ts` 的形狀：注入 `spawn`、單一併發、可注入的計時器、
狀態為 `idle | running | failed`、**只回錯誤碼不回文案**。

- **理由與掃描相同再加一條**：`claude` 的 stderr 可能含絕對路徑或帳號資訊，而錯誤訊息會被畫到
  畫面上。錯誤碼裡沒有路徑可放。
- **但不重用那支 `utilityProcess`。** 掃描行程的職責是解析一份會隨版本改變的格式（崩潰隔離是它
  存在的理由）；委派則是等一個外部行程回話，它本來就在自己的行程裡。塞在一起會讓「掃描崩潰」
  與「委派逾時」共用一組狀態。
- 逾時給足（語料大時要跑幾分鐘）且可注入 —— 既有教訓：**一支慢得離譜的測試通常是在等一個它
  不該等的東西**。

### D5：語料超過上限時**從最舊的一端截斷**，並讓報告記錄實際涵蓋的期間

範圍拉到一年時語料會遠超單次可處理的量。三種處置裡：

- **抽樣** —— 悄悄改變了這份報告在講什麼，而畫面上看不出來。否決。
- **拒絕並請使用者縮小範圍** —— 誠實，但把問題丟回去。
- **從最舊的一端截斷，且報告的「涵蓋期間」記錄的是真正送進去的那一段**（不是使用者要求的那段）。
  誠實且仍然可用。**採用這個。**

### D6：報告吃儀表板已算好的數字

送進去的除了語料，還有 `aggregate()` 產出的那些量。**不讓它自己重估** —— 否則兩個分頁會各講各的
數字，而使用者無從判斷誰對。這也讓提示可以要求它「解釋這些數字」而不是「數這些數字」，
而後者正是模型最不擅長的事。

### D7：「我的語氣」降格為「字面線索」是純呈現層的改動

分類在讀取時計算，存檔裡沒有分類結果 → **不需要資料遷移**。改動範圍是規則檔的檔名與六個 key、
`insights-aggregate.ts` 的型別命名、字典、以及探針的選擇器。

**同時補上現在沒有的 unmatched 計數。** 現行實作六類各自獨立累加，一則都沒中的訊息不知去向；
標籤改誠實之後，分母也必須誠實。

### D8：真實委派不進探針，而這個缺口要明寫

探針跑在 xvfb 上、要求可重現、且不該花錢或需要網路。**真實的 `claude` 委派因此沒有自動化載體。**

- 產生、查證、丟棄、落盤、失敗分類**全部**以注入的假委派驗（`ReportRunner` 的 `spawn` 是注入的，
  這正是它存在的理由）。
- **真實委派由 dogfood 認定**，比照 `terminal-sessions` 那條「自動化驗收通過 SHALL NOT 被詮釋為
  程式化繪製的呈現是正確的」。這條缺口寫進 spec，不是寫在這裡就算了。
- **查證邏輯的對照組**：餵一條引用不存在於語料的論斷，確認它**真的被丟棄**且丟棄數加一 ——
  沒有這條，「查證」可能整段沒被呼叫而測試照樣全綠。

## Risks / Trade-offs

- **報告讀起來永遠很有道理，包括它錯的時候** → D3 的機械查證 + 丟棄數外顯。這是唯一的守衛，
  它擋得住「引了不存在的話」，**擋不住「引了真的話但推論錯了」** —— 後者由使用者看得到原句來承擔，
  而那正是為什麼引用是強制的。
- **委派把語料寫成第二份副本，落在權限控制之外** → D2 的刪除。刪除失敗（行程中途被砍）時那份
  副本會留下，而**掃描已經排除了它**，所以至少不會污染資料 —— 但它仍是一份未受保護的副本。
  已知缺口，不假裝解決。
- **`claude` CLI 是外部介面，旗標與輸出格式會隨版本改變** → 依賴的欄位**列成一份完整清單**，
  每一個都要在實作時實測存在：`result`（回覆本體）、`is_error` / `subtype`（成敗）、
  `session_id`（算出要刪除的紀錄路徑）、`total_cost_usd`（費用）、`permission_denials`
  （工具是否真的被關掉）。**模型不在清單裡** —— 報告記錄的是「本應用程式請求的模型」，
  那是我們自己傳出去的值，不必從回覆讀。解析失敗即整份失敗，**不要**依賴 stderr 的文字。
- **成本不可預測** → 報告記錄並顯示 `total_cost_usd`，模型可選。**不做自動排程**（Non-Goals）。
- **未登入 / CLI 不存在 / 逾時 / 輸出無法解析 / 全部論斷都被丟棄** —— 這五種必須是**可區分**的
  狀態。既有教訓：`sourceAvailable === null` 曾被顯示成「沒有資料」，而那句話是錯的。
- **兩個分頁的鮮度不同** → 報告一律顯示產生時間、實際涵蓋期間、模型與丟棄數；儀表板的範圍與報告
  的範圍不同時要看得出來。這是本次拆分頁的全部理由，不能只做在版面上而不做在標示上。

## Migration Plan

無資料遷移（D7）。既有存檔照用，既有掃描不變。

**回退**：本次全部改動可整體 revert —— 存檔格式一個位元組都沒動，回退後舊版讀同一份存檔照常運作。
已產生的報告會留在 userData 之下成為孤兒檔案（不影響任何東西），與 `conversation-archive`
對待孤兒的既有立場一致：不動它。

## Open Questions

- **使用者的全域 `~/.claude/CLAUDE.md` 仍會被委派載入**（cwd 為空目錄擋得掉 repo 的，擋不掉全域
  的）。是否以 `--append-system-prompt` 抵銷，可在實作時再定 —— 它不改變規格、作法或工作切分。
- **全域 `settings.json` 的 hooks 同樣不受 cwd 影響。** 它們不是工具，關閉工具擋不掉它們，
  而它們的 stdout 有可能污染 `--output-format json` 的解析 —— 徵狀會是「回覆無法解析」，
  使用者看到「模型壞了」，真正的原因是他自己的一個 hook 印了一行字。是否有途徑停用，
  待實作時實測；它不改變規格的條文，只改變某一種失敗的成因分佈。
- 預設模型的選擇同理，延後。

## Scenario → 載體對照表

**填「既有」時必須真的把那條斷言找出來。** 這個 repo 已經五次「補了 scenario 卻沒有覆蓋」，
而第五次的形狀是**對照表做了、填表的方式錯了** —— 39 條憑印象填的「既有」裡有 4 條是假的。
下表每一條「既有」都附了檔案與行號；核不到的一律寫「無載體」＋理由。

> **這張表被獨立 review 抓到四條錯的「既有」，後來又在實作階段的逐條核對中抓到四條假的「新增」**
> （宣稱有測試而根本沒寫）。兩批加起來八條，而兩次寫它的時候我都自認核對過。
>
> **第一批（review 抓到的）：**
> 兩條行號漂移（212→226、230→232），一條把**另一條 scenario 的載體**填成了自己的
> （「分類規則對使用者可見」填了 `:220`，那是「百分比不相加為 100%」的斷言），
> 一條寫著「本次未改動該路徑」而**同一份 delta 就改了它**。
> 抓到它們的是一次獨立的 review，不是再讀一遍。
> **第二批（實作完成後逐條核對抓到的）：** 四條標「新增」的 scenario 在表上寫著它會有某個
> 單元測試，而那些測試從來沒被寫出來 —— 表是在寫測試**之前**填的，填的是意圖而不是事實。
> 其中一條（刪除失敗）在補載體時**當場抓到實作會謊報**：`rmSync({ force: true })` 對不存在的
> 路徑不拋錯，於是「委派 cwd 一直算錯」會被回報成「已刪除」。
>
> **教訓的下一層：「我逐條核對過」這個宣稱本身也需要對照組。** 核對的方式必須是
> 開檔案讀那一行的字串（既有）或讀那個 `it(...)` 的名稱（新增），不是憑印象確認一個看起來
> 合理的行號，也不是把「我打算寫的測試」寫成「載體」。
