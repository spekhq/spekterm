## Context

`session-rename-and-reorder` 定下了 session 標籤的三層優先序（**使用者指定的名稱 > pty 宣告的 OSC
標題（僅 `claude` 目標）> 本地標籤**），並在使用者接管命名權後，替 pty 的每一次改名安排一個**確認
對話框**（`TitleConflictDialog`：採用它的名稱／保留我的名字）。

第二次 dogfooding 的實測：**這個對話框會無限重跳。**

現行 `setTitle()`（`src/renderer/src/shell/terminal/sessions.tsx:224`）在 `customTitle` 存在時的判定是：

```
if (next === undefined || next === target.customTitle || next === target.pendingTitle) return previous
→ 否則設 pendingTitle（＝跳對話框）
```

而「保留我的名字」（`keepCustomTitle()`）**只把 `pendingTitle` 清成 `undefined`**，不留下任何「使用者
已經拒絕過」的痕跡。於是 pty 下一次宣告標題時，三個短路條件與第一次完全相同 —— 對話框再跳一次。
**連 pty 送出同一個標題都會再跳**：那條 `next === target.pendingTitle` 的短路，在使用者按下「保留我的
名字」的瞬間就失效了（`pendingTitle` 已被清空）。而 `claude` 隨任務進展**持續**重新宣告標題。

當初的 spec **已經察覺 agent 會頻繁改名** —— 才有「同一時間至多只有一個待確認的標題…否則頻繁改名的
agent 會把使用者的畫面淹沒」那條。但緩解只做到「不同時堆疊多個對話框」，沒有處理「**沿著時間軸反覆問
同一個問題**」。這不是漏寫一行 `dismissed` 旗標，是這個對話框存在的**前提本身**不成立。

**約束**

- 三層優先序是既有規格，且是對的 —— 本 change 不動它。
- login shell 的 session 一律不採用 pty 宣告的標題（`session-navigation-and-labels` 的裁決），因此
  「pty 想改名」這個情境對它本來就不存在。本 change 只影響 `claude` 目標。
- 導航快捷鍵的抑制以 `document.querySelector('[role="dialog"], [role="menu"]')` 判定
  （`KeyboardNavigation.tsx:68`）—— 與對話框的**身分無關**。移除一個對話框不改變這條邏輯，但會**減少
  一組驗收載體**（見 D4）。

## Goals / Non-Goals

**Goals:**

- 使用者替 session 命名之後，**不再因為 pty 改名而被打斷** —— 一次都不。
- 「交還命名權」仍然做得到，且路徑單一、可發現：**把名字清空**。
- 交還的那一刻，標籤**立即**回到 `claude` 當下最新宣告的標題，不必空等它下一次宣告。
- 移除對話框所空出的驗收缺口（快捷鍵抑制的第三種載體）**必須補回**，不得靜默吞掉。

**Non-Goals:**

- **不改三層優先序。** 使用者指定的名稱仍然最優先。
- **不做非模態提示**（分頁上的小徽章 / toast 告訴使用者「claude 想改名」）—— 見 D2。
- **不在命名對話框裡呈現「pty 目前宣告的標題」作為預設值或提示。** 它是誘人的加分項（使用者取名後
  就再也看不到 claude 的標題了），但那個資訊在終端內容裡本來就看得到，而清空名字也能立刻看到它。
  範圍守住。
- **不改 login shell 丟棄 OSC 標題的規則。**
- 不動拖曳排序、不動 `SessionNameDialog` 本身。

## Decisions

### D1：使用者命名 ＝ **永久**接管命名權，pty 的標題此後靜默丟棄

`customTitle` 存在時，pty 宣告的標題**不呈現、不確認、不覆蓋**。對話框整個移除。

**為什麼不是「保留我的名字 ＝ 此後靜音」（記一個 `titleAuthority: 'user'` 旗標）？** 那個方案能修好
「無限重跳」，但它仍然要打斷使用者**一次** —— 而那一次的資訊價值趨近於零：使用者**才剛親手把它命名
為 b**，緊接著問他「pty 想叫它 a，要採用嗎？」，答案幾乎必然是「不要」。一個答案可預測的問題，不值得
一次打斷。

更關鍵的是：**三層優先序本身就已經是那個裁決。** 「使用者指定的名稱 > pty 宣告的標題」這句話的意思
就是「使用者說了算」。在它之上再疊一個確認對話框，是**對同一件事問第二次**。命名這個動作本身，就是
使用者對命名權的宣告。

**代價**：使用者失去「一鍵採用 pty 新標題」的入口（例如他隨手取的名字後來覺得不如 claude 的好）。
這個代價由 D3 抵銷 —— 清空名字即可，而且清空的那一刻拿到的是**最新**的標題，比舊對話框提供的
（某一次宣告的快照）更有用。

### D2：不做非模態提示（徽章 / toast）

「claude 想把這個 session 改叫 X」這個資訊，值不值得佔用畫面？**不值得。**

- 它**高頻**（claude 持續改標題）—— 一個持續閃動的徽章，與持續彈出的對話框在「令人分心」這件事上
  只有程度差別。
- 它**已經有更好的來源**：那個 session 的終端內容本身。claude 的標題是它對自己正在做的事的摘要，
  而使用者只要看一眼終端就知道。
- 它的**行動性為零**：使用者看到這個提示之後能做什麼？清空名字 —— 而那件事他隨時都能做，不需要提示
  催他。

### D3：接管期間，pty 的標題**仍持續被記錄**（只是不呈現）

`setTitle()` 在 `customTitle` 存在時，**照樣更新 `title` 欄位**，只是標籤的取用順序讓 `customTitle`
贏。

**為什麼不是「接管後直接丟棄、連記都不記」？** 因為那會讓 D1 的代價變得難以承受：使用者清空名字想
交還命名權時，標籤會退回本地標籤（`claude 1`），**空等到 claude 下一次宣告標題為止** —— 而那可能是
好幾分鐘後、也可能永遠不會（若那個 session 剛好閒置）。「清空名字」是本 change 保留的**唯一**交還
路徑，它必須是即時且確定的，否則使用者會覺得「清空之後名字不見了」。

記錄的成本近乎零（一個既有欄位照常寫入）。既有的「值沒變就不建新陣列」短路要保留 —— agent 會反覆
送同一個標題，那條短路防的是無謂的整棵樹重繪。

### D4：消失的第三種「對話框抑制」驗收 → 換成 `VizOverlay`（**不是**接受降為兩種）

CLAUDE.md 記著：「`probe:keyboard` 與 `probe:terminal` 對**三種**對話框（session 命名、標題衝突、
files 的）各驗一次抑制 —— **只驗一種就宣稱涵蓋，等於沒驗**」。標題衝突對話框（第三種，斷言位於
`scripts/probe-terminal.mjs:1325`）刪除後，只剩兩種，且兩種都在 `probe:keyboard` 裡。

那條「三種」的紀律，守的不是數字，而是**「每一個對話框都真的遵守了 `role="dialog"` 這個慣例」** ——
抑制邏輯是身分無關的通用判定，它的失效模式從來不是「邏輯寫錯」，而是**某個新對話框忘了寫
`role="dialog"`，於是靜默地不被尊重**。載體越多樣，這個慣例被檢驗得越紮實。

**現成的替代載體：`VizOverlay`（`src/renderer/src/shell/openspec/VizOverlay.tsx:62`，Graph 與 Timeline
的全視窗 overlay）本來就是 `role="dialog"`，而它從未被驗過快捷鍵抑制。** 這個缺口是本 change 順手發現
的，不是為了湊數而發明的：overlay 開著時按 `Ctrl+↓` 切 repo（畫面被 overlay 蓋住，切了也看不見）正是
抑制存在的理由，而它比標題衝突對話框**更常被使用者遇到**。

由 **`probe:openspec`** 承載（它已經會開 overlay 了，加一條斷言的邊際成本近乎零）。
**不由 `probe:keyboard` 承載** —— 它的 fixture 是自建的暫存 repo，沒有 `openspec/` 目錄，開不了 overlay。

淨效果：三種抑制驗收**仍是三種**（session 命名、files、Graph/Timeline overlay），且第三種換成了一個
更真實的情境。**這不是「填補」，是把一筆隱藏的技術債換成資產。**

### D5：`probe:terminal` 的驗收改為**驗新行為**，不是刪掉了事

刪掉的是三條斷言（衝突對話框出現 / 保留我的 / 採用它的）。新的驗收必須真的能抓到「重跳」這個 bug 的
**回歸**，因此它的形狀是：

1. 一個 `claude` 目標的 session（由既有的 **stub `claude`** 驅動 —— PATH 前置 + `HOME` 隔離，
   `probe:terminal` 已有這套機制），先讓 pty 宣告標題 `a`。
2. 使用者把它改名為 `b`。
3. **讓 stub 再宣告標題 —— 而且要送兩種**：一次**同一個** `a`（這正是使用者回報的情境，也是舊實作
   連這都會問的地方），一次**不同的** `c`。
4. 斷言：**全程不出現任何 `[role="dialog"]`**，且標籤恆為 `b`。
5. 清空名字 → 斷言標籤**立即**變成 `c`（pty 最新宣告的那個）。**這條就是 D3 的證據** —— 它同時證明
   「接管期間仍在記錄」與「交還是即時的」。少了它，D3 只是一句宣稱。

第 4 步的「不出現對話框」是一個**否定斷言**，天生有假綠風險（若 stub 根本沒送出標題，它也會通過）。
因此第 5 步是**必要的對照組**：標籤變成了 `c`，就證明那些 OSC 標題**真的抵達了** `setTitle()`。
沒有第 5 步，第 4 步等於什麼都沒驗。

## Risks / Trade-offs

- **[使用者失去「一鍵採用 pty 標題」的入口]** → 由 D3 抵銷：清空名字即可，且拿到的是最新標題。
  這條路徑已寫在 spec（「清空 ＝ 放棄命名權」），本 change 讓它成為唯一路徑，也因此它的**可發現性**
  變得比以前重要 —— 但命名對話框本來就在那裡，清空是自然動作。若日後 dogfooding 顯示使用者找不到它，
  再考慮在對話框上加一行提示（本 change 不做，見 Non-Goals）。

- **[「不出現對話框」是否定斷言，容易假綠]** → 以 D5 的第 5 步當對照組（標籤變成 `c` ⇒ OSC 標題確實
  抵達了）。這是 CLAUDE.md 反覆記取的教訓（OSC 8 連結那條假綠、`naming.test.mjs` 的對照組）。

- **[移除 `pendingTitle` 是 state 形狀的破壞性變更]** → 影響面完全在 renderer 內部
  （`SessionState`、`SessionsApi`、`MainStage` 的掛載點），無持久化、無 IPC 契約牽涉 —— session 狀態
  不落盤。TypeScript 會把所有引用點逼出來。

- **[CLAUDE.md 與 spec 記著舊規則]** → 兩者都要改。CLAUDE.md 的「session 的命名權可以被使用者接管」
  那段整段改寫；`keyboard-navigation` spec 那條列舉三種對話框的句子要換掉第二種。**這類「文件記著已被
  推翻的事實」正是本 repo 最容易累積的債** —— 一條過期的規則會讓下一次的判斷建立在錯誤的前提上。

- **[Timeline/Graph overlay 的抑制若其實是壞的呢？]** → 那正是 D4 要驗出來的。`VizOverlay` 帶了
  `role="dialog"`，理論上已被抑制邏輯涵蓋，但**從未被驗證過**。若它其實是紅的，那是本 change 白撿的
  一個真 bug（且修法極可能只是補一個屬性）。
