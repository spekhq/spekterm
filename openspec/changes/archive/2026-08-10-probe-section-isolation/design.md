# 設計：探針的段落隔離與真實成本基準

## Context

一輪 `test:e2e` 實測 25.6 分鐘，但**兩支探針中途 throw、其後段落完全不執行**：

| | 實測 | 實際跑完了嗎 |
|---|---|---|
| `probe:terminal` | 937s | ❌ build 10 段全跑；**dev 只跑了 `runMode` 一段**就在 `openSessionViaMenu` throw |
| `probe:openspec` | 209s | ❌ 在 `createSession` throw，後段（worktree 聚合、反向導覽、quick-open）整片沒跑 |
| `probe:keyboard` | 332s | ✅ 完整（198/200，兩條 dev 紅燈） |
| 其餘 5 支 | 59s | ✅ 完整 |

`probe:terminal` 只跑 build 段的實測是 **166 秒、126/126 全綠** —— 也就是說 **dev 的
`runMode` 一段吃掉 771 秒，比 build 的全部 10 段還貴 4.6 倍**。

**這推翻了本 change 前一版的整個成本模型。** 那一版寫「dev 段有 21 次 launch，771 ÷ 21 ≈ 每次
冷啟動 35 秒」，據此把 dev 收斂為白名單、宣稱省 47%。但那 20 次 launch 從未發生 —— 771 秒是
一次 launch 加上 68 條斷言的互動花掉的。**成本跟著互動次數走，不跟著 launch 次數走**，而唯一
真正貴的那一段（`runMode`）正是收斂方案要保留的。

前一版的失效方式值得記下來，因為它是本 repo 反覆重演的教訓的第四次實例：**它拿了一個方便取得
的量（總耗時 ÷ 靜態計數的段落數），當成規格真正在乎的量（每段實際花的時間）**，而那份 proposal
甚至已經對 `probe:openspec` 標註了「中途 throw 中斷，其實沒跑完」—— **同一個檢查沒有套用到
terminal 身上。**

因此本設計的第一目標不是壓縮成本，而是**讓成本可被測量**。

## Goals / Non-Goals

**Goals:**

- 一個段落的失敗不再吞掉其後的段落 —— 一輪跑完能拿到完整的一張圖。
- 讓「哪些段落現在是紅的」成為已知（`probe:terminal` 的 dev 段有 9 個段落狀態不明）。
- 取得一份沒有中斷的成本基準，作為後續任何最佳化的依據。
- 三支重探針具備一致的段落結構與 `PROBE_ONLY`。

**Non-Goals:**

- **不做 dev 模式的收斂。** 前一版正是在這裡垮的。收斂需要「dev 全跑要多久、哪些段落真的紅」
  這兩項資料，而它們**只能由本 change 產出**。
- **不修 issue #17 / #19。** 隔離會讓它們的紅燈**更完整地被看見**（現在有些根本沒跑到），
  但定位與修復是各自的工作。
- **不平行化、不刪探針、不縮短等待窗口**（理由見 proposal）。
- **不追求本 change 讓 `test:e2e` 變快** —— 它幾乎確定會變慢，見 proposal 的警告。

## Decisions

### D1. 隔離的粒度是段落，不是斷言

段落內部的 throw 由執行器捕捉，記為「該段落失敗」並附錯誤訊息，然後繼續下一個段落。

**為什麼不做更細的粒度**（例如每條斷言各自 try/catch）：探針的斷言之間有狀態依賴 —— 一條
`check()` 之前往往有好幾步 UI 操作。在斷言層級隔離會產生大量「因為前一步沒做成功而必然失敗」
的紅燈，那與 `docs/lessons/probes.md`「一條沒有 `detail` 的 `check()`，失敗時等於什麼都沒說」
是同一種病：噪音會淹掉訊號。段落是既有的、有語意的邊界。

**為什麼不是「什麼都不做，反正 `run-probes.mjs` 不 fail fast」**：那條紀律只存在於**探針之間**。
`run-probes.mjs` 的檔頭寫著「付了十幾分鐘就該拿到完整的一張圖，而不是第一支紅了就停」——
**同一個論證在探針之內一字不改地成立**，而它從未被套用進去。

### D1b. 段落必須有時限 —— 隔離只擋得住 throw，擋不住 hang

**這一條是實作階段才浮現的，而它推翻了 D1 的一個隱含假設**：D1 寫「段落內部的 throw 由執行器
捕捉」，把「段落的失敗」等同於「段落拋出例外」。實測證明那個等式不成立。

`runRestore` 的 dev 段在 `app.quitGracefully()` 卡住 **1 小時 30 分**，`test:e2e` 永遠不會結束，
而該段落的五個 electron 行程一直活著。`try`／`catch` 對此毫無作用 —— **一個永遠不 resolve 的
Promise 不會 throw**。

**逾時比中斷更糟**：中斷至少會結束、會印堆疊、會讓下一輪有機會跑。一個 hang 掉的段落什麼都不給，
而且看起來像「還在跑」。

因此段落的執行包一層時限：逾時記為失敗（原因與例外區分）、其後段落照跑、**並強制清除該段落
留下的行程**（逾時的段落不會走到自己的 `finally`，沒有其他人會收它建立的 app 與 pty）。

時限**逐段可設**：`runRestore` 在 dev 下有 5 次冷啟動、`runDormantHint` 只有 1 次，一刀切的數字
不是太鬆（等於沒有）就是會誤殺。

> **這個失效模式是被段落隔離本身逼出來的。** 此前 `runMode` 在 dev 一 throw 整支就中斷，根本走不到
> `runRestore` 的 dev 段 —— 那個 hang 從來沒有機會發生。**這正是本 change 的目的**（把看不見的
> 變成看得見的），只是它先絆倒了 change 自己。

### D2. 依賴宣告的用途是「區分紅燈與未執行」

段落可宣告它依賴哪些前置段落。前置失敗時，依賴它的段落標記為 **`未執行（前置失敗）`**，
不執行、也不計入紅燈。

**這是隔離能不能用的關鍵，不是加分項。** `probe:openspec` 全程只有一次 `launch()`，22 個區塊
共用同一個 app 與累積狀態 —— 少了這個區分，前段一失敗就會連鎖出一整片紅燈，而它們全部指向
同一個根因。**一片紅燈與一次中斷同樣無法閱讀**，只是換了一種形式。

輸出中三種狀態必須可區分：`通過` / `失敗` / `未執行（前置失敗）`。

> **順帶**：依賴宣告讓 `PROBE_ONLY=<某段>` 能自動帶上前置。少了它，單獨跑一個缺前置的段落
> 會「紅得莫名其妙」，而那與產品缺陷長得一樣（`docs/lessons/probes.md`：「驗收有前置條件時，
> 前置沒成立會紅得莫名其妙」）。

### D3. 段落機制抽到 `scripts/lib/sections.mjs` 共用

`probe:terminal` 現有的 `SECTIONS` + `PROBE_ONLY` + `wanted()` 是這個模組的原型。抽出來的理由
與 `run-probe.mjs` 收攏螢幕選擇相同：**三份各寫一次，遲早會有一份不一樣**。

模組負責：段落宣告（名稱、函式、依賴）、模式迴圈、逐段 try/catch、依賴解析與 skip 標記、
`PROBE_ONLY` 篩選、context 傳遞、結果總結。**「沒有任何 dev 段要跑時不啟動 dev server」**
這條現在只有 terminal 做對，抽出來之後三支都自動享有。

**context 傳遞**：段落可回傳 context（profile、marker、stub、app 實例、既有的中間變數），
由執行器併給後續段落。`probe:openspec` 的五段共用同一個 app，靠的就是它。

**context 必須分模式保存** —— build 與 dev 各自建立 fixture，兩者的 context 不得互串。

### D4. 切分 `probe:openspec`：切點只決定隔離粒度，不決定誰被執行

把 3000 行的單一 `runMode` 依既有的 `console.log` 標題切成 5 段：`runPanelBasics` /
`runBrowseAndOverlays` / `runAnchoringAndCoordinate` / `runWorktreeAggregation` /
`runQuickOpenScope`。**22 個 `console.log` 區塊必須全部有歸屬**（前一版的對照表漏掉了「不含
openspec 的 folder」那一塊）。

**本版的切分風險遠低於前一版**：前一版因為「dev 只跑白名單段落」而要求每段自帶前置，而那
**實際上切不開** —— `runAnchoringAndCoordinate` 的第一條斷言要求兩個 active change，那個狀態
由「多個 active change：不猜」區塊建立，而該區塊被歸在 dev 不跑的段落裡；`runPanelBasics`
結束時還明文「還原：後面每一段都站在 repo-single 上」。**本版每個段落在兩種模式下都照跑**，
狀態鏈完整，切點只影響「一段失敗時，多大範圍被標記為未執行」。

> 前一版那個錯誤本身值得留在紀錄裡：它命中的正是自己寫下的風險條目 ——「切錯地方的症狀是
> 後段前置不成立而紅得莫名其妙，而那與產品缺陷長得一樣」。

`probe:terminal` 的 `runRestore` 在本版**不切分** —— 切分它唯一的動機是「dev 只跑前綴」，
那個動機已隨收斂決策一起移出範圍。

### D5. 建置跳過開關：`PROBE_SKIP_BUILD=1`，且必須吵

`probe:*` 目前一律 `npm run build && …`（實測 14 秒）。改為由 `scripts/run-probe.mjs` 決定
（預設建置），並提供跳過的開關。

**風險是假綠**（跳過建置卻改了產品程式碼，驗到舊產物）。緩解：

- 跳過時 SHALL 印出 `out/` 的 mtime 與「本輪未重新建置」的明確警告。
- 該開關 SHALL NOT 出現在 `test:e2e` 或任何預設路徑上。

**`test:e2e` 的建置次數必須維持一次。** `run-probes.mjs` 對 9 支各 spawn 一次 `run-probe.mjs`
—— 若把建置搬進 `run-probe.mjs` 而不處理這件事，一輪會建置 **10 次**（多付約 9×14 秒，正好
吃掉本 change 想省下的迭代時間）。作法是 `run-probes.mjs` 自己建置一次後，以**內部參數**
（非使用者可見的環境變數開關）告知子行程不必再建 —— 它與 D5 的使用者開關是兩個東西，不得
共用同一個旋鈕。

> 曾考慮以「比對 `out/` 與 `src/` 的 mtime 自動決定是否重建」取代開關。否決：那道判斷的邊界
> （`node_modules`、設定檔、`package.json`）**每漏一個就是一次假綠**，且失效時完全無聲。
> 一個吵的手動開關，比一個安靜的自動判斷可靠。

### D6. 耗時數字不寫死在文件裡

`docs/lessons/probes.md:298` 的「`probe:terminal` 一輪約 4 分鐘」實測為 15.6 分（且那 15.6 分
還是**沒跑完**的）。**修法不是改成新數字**（下次一樣會過期，而且隔離之後它馬上又會變）：
`run-probes.mjs` 本來就會印每支耗時，文件改為指向那份輸出，只保留數量級與相對成本。

（前一版把這句話的位置寫成 `CLAUDE.md`，三個 artifact 都指錯檔案 —— 照那份 tasks 逐條實作，
那個過期的數字會原封不動留著。）

## Risks / Trade-offs

- **[`test:e2e` 變慢，且慢多少事先不知道]** → 這是目的不是副作用（proposal 已警告）。
  `probe:terminal` 的 dev 段有 9 個段落從未執行過，總量無從估計。**緩解不是壓縮，是讓
  `PROBE_ONLY` 在三支上都可用**，使日常迭代不必跑完整輪；完整輪次仍然是封存前的事。
- **[隔離之後冒出一批新的紅燈]** → 幾乎確定會發生（那 9 個段落狀態不明）。它們**不是本
  change 造成的退步**，是本來就存在而看不見的。處置：逐條開 issue，不在本 change 內修
  —— 但**必須逐條記錄**，否則「已知的缺口」與「被追蹤的缺口」的差別又會被抹掉。
- **[切分 `probe:openspec` 引入靜默 regression]** → 切分不得改動任何斷言的內容、順序與狀態
  前提。驗收口徑：**以 build 模式**切分前後的斷言總數與通過數一致（dev 模式的總數會因為
  隔離而上升，不能拿來對照）。
- **[依賴宣告不完整]** → 症狀是某段被錯誤標記為「未執行」，或單獨跑時缺前置。驗收 SHALL
  對每一個宣告了依賴的段落單獨以 `PROBE_ONLY` 執行一次。
- **[逐段 try/catch 吞掉本該讓人注意的錯誤]** → 捕捉到的錯誤必須完整輸出（訊息 + stack），
  且該段落計為失敗、影響最終 exit code。**隔離不是容忍。**

## Migration Plan

純腳本與文件變更，無資料格式、無 IPC、無產品程式碼改動。rollback 即 `git revert`。

驗證順序：先以 `PROBE_ONLY` 單段確認機制（含刻意 throw 的對照組），再跑完整一輪取得新基準。
