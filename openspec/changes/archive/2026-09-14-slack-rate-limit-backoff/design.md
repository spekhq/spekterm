## Context

動機見 `proposal.md`。設計上只需要四個既有事實：

1. **`SlackFailure` 已經帶得動這個資訊** —— `slack-api.ts` 對 429 回的是
   `{ kind: 'transient', error: 'rate_limited', retryAfterSeconds }`。解析是對的，缺的是消費端。
2. **一輪的結構是「逐頻道迴圈」**（`slack-backfill.ts`），而失效目前是 `failure ??= scanned.failure`
   —— **先到的贏**，然後 `continue` 到下一個頻道。
3. **`SlackRuntime` 已經有時鐘注入點**（`deps.now`）與假時鐘測試（上一個 change 為週期輪詢加的）。
4. **端點是使用者可編輯的設定**（`slack-settings-store`）—— 於是回應的內容**不是完全可信的輸入**。
   這一條在 D4 承重。

## Goals / Non-Goals

**Goals:**

- 對端說「等一下」時，**這一輪剩下的頻道不再打**，且**下一輪在時限之前不開始**。
- 使用者明確的操作（存下憑證）撞上退避期時**不被靜默吞掉**。
- 解除 `ROUND_INTERVAL_MS` 註解裡那句「縮短之前先看 issue #46」的前置條件。

**Non-Goals:**

- **不縮短 `ROUND_INTERVAL_MS`。** 那是獨立的一次裁決，而本 change 的目的是讓它變成安全的操作。
- **不做 per-method 的速率帳本**（見 D3）。
- **不涵蓋即時路徑。** Socket Mode 的事件流不受這條速率上限管轄；`apps.connections.open` 雖是
  一次 API 呼叫，但它一輪最多一次，不是壓力來源。
- **不實作「解禁後自動補做」。** 見 D5。

## Decisions

### D1：退避的資訊走 `BackfillOutcome` 的**獨立欄位**，不寄生在 `failure` 上

`runBackfill` 在 outcome 上新增 `retryAfterSeconds?: number`，`SlackRuntime` 據以算出截止時間。

**為什麼不直接讀 `outcome.failure.retryAfterSeconds`**：那個欄位是「**先到的贏**」。一個在第 2 個
頻道發生的網路錯誤會先佔住 `failure`，而第 5 個頻道的 429 就**永遠讀不到** —— 於是退避靜默地不發生，
而症狀是「偶爾沒有退避」，沒有任何東西會紅。獨立欄位讓兩者互不遮蔽。

考慮過的替代：把 `failure ??=` 改成「速率上限優先覆寫」。否決 —— 那是在一個既有的優先序規則上
疊一條例外，而**下一個加失效種類的人不會知道那條例外存在**。

### D2：新增第五種 failure kind `rate_limited`，而不是比對 `error === 'rate_limited'` 字串

理由是**呈現層需要分得出來**：「Slack 要我們等一下」與「你的憑證失效了」的處置完全不同
（前者什麼都不必做，後者要換 token）。而那正是上一個 change 才剛付過學費的形狀 ——
`missing_scope` 被歸進 `auth`，畫面上說了一句會害人白做一輪的話。

**代價已知且必須主動償付**：CLAUDE.md 記著「加一個列舉值時，把所有 `===` 比較 grep 一遍」，
TypeScript 一條都不會攔。實際站點（已 grep，共五處）：

| 站點 | 目前行為 | 本 change 要做的判斷 |
|---|---|---|
| `slack-service.ts:175` 早退 | `auth` / `scope` 時不開即時連線 | **不加入** —— 速率上限與即時連線無關 |
| `slack-service.ts:263` `#merge` | 同 kind 同 error 才合併計數 | 自動涵蓋，無需改 |
| `slack-service.ts:261` `needed` | 只有 `scope` 有 | 無需改 |
| `slack-backfill.ts:308` `NameCache` | `auth` 時整份放棄 | **要改** —— 速率上限也該整份放棄，不要繼續打 `users.info` |
| `SlackSettings.tsx:55-62` `statusCopy` | scope / auth / 其餘 | **要改** —— 新增一句，帶「何時會再試」 |

### D3：退避是**一個全域截止時間**，不是 per-method 帳本

Slack 的上限是 per method per workspace，所以理論上「`conversations.history` 被擋」不影響
`users.info`。但**一輪是全有全無的單位** —— 我們沒有「只跑一半的頻道」這種中間狀態可以交付，
而綁住的方法本來就只有一個（`conversations.history`，每頻道一次，是唯一隨規模線性成長的）。

一份 per-method 的帳本會增加狀態、增加測試面，而**行為上不會有任何差別**。
**刻意的簡化，寫進規格的實作註記而非條文。**

### D4：`Retry-After` 缺席時用保守預設，而且**上下界都要夾**

- 缺席或非有效秒數 ⇒ **60 秒**。不是零 —— 對端已經明確拒絕了，零等於不退避。
- 上界 **15 分鐘**。理由不是「不相信 Slack」，是**端點是使用者可編輯的設定**（見 Context 4）：
  一個回 `Retry-After: 99999999` 的端點會讓這個能力**永久停擺**，而畫面上只會顯示「正在等待」。
  一個能被輸入資料無限期關閉的能力，是一個可以被關掉的能力。
- 下界 1 秒。

### D5：退避期內的那一輪**跳過，不排隊補做**

補做會在解禁的那一刻形成尖峰 —— 那正是速率上限存在的理由。而跳過的代價是有界的：
下一次週期到期時（最多再 5 分鐘）就會跑，而水位機制保證跳過的期間不會漏任何一則。

**這使「跳過」與「漏掉」是兩件事** —— 規格上要說清楚，否則下一個人會以為跳過的那一輪的內容沒了。

### D6：使用者觸發撞上退避期 —— **不繞過，但一定要講出來**

三個選項：

| | 結果 |
|---|---|
| (a) 無視退避照跑 | 尊重使用者的操作，但**那正是讓 token 進到更長懲罰期的做法** |
| (b) 跳過並顯示「Slack 要求稍後再試，下次嘗試時間 HH:MM」 | 採用 |
| (c) 排隊，解禁時自動跑 | 與 D5 矛盾（尖峰），且使用者已經離開那個畫面了 |

**(b) 的承重部分是後半句而不是前半句。** 存下憑證卻什麼都沒發生，與「功能壞了」在畫面上完全
相同 —— 這正是這個能力花了一整條 requirement 在防的事（「失效與閒置必須可區分」），
而一次靜默的跳過會把那條 requirement 在這條路徑上作廢。

### D7：驗收的可觀察面是**替身收到的呼叫數**

「不再送註定失敗的請求」這件事在收件匣上看不見（那些請求本來就不會產生任何卡片）。
可觀察的是**替身端**：讓 `stub-slack.mjs` 在第 N 次 `conversations.history` 回 429 +
`Retry-After`，然後斷言該輪對 `conversations.history` 的呼叫數 **等於 N**（而非頻道數）。

- **對照組**：把中止改回 `continue` ⇒ 呼叫數等於頻道數 ⇒ 該斷言變紅。
- 跨輪那一半由單元測試以**假時鐘**承擔（`slack-service.test.ts` 已有那套設施）。
  探針驗不了它 —— 要等 5 分鐘。

### D8：退避狀態只活在記憶體裡

重開 app 即遺失，於是啟動那一輪可能立刻再撞一次 429。**這是刻意的**：

- 代價是**一次**被拒絕的請求，而它會立刻重新學到。
- 落盤的代價比較大：一個「關機一天後開機」讀到的截止時間是過期的，需要與當下時鐘比較才能用，
  而那條比較在時鐘被調整過時會失準 —— 為了省一次 429 而引入一個依賴牆上時鐘的持久狀態，不划算。

**寫成規格裡的一條缺口**，不是靜默的實作細節。

## Risks / Trade-offs

- **新增列舉值，而 TypeScript 不會攔任何既有的 `===`** → D2 已把五個站點逐一列出並標註處置；
  tasks 要逐條對。這是 CLAUDE.md 記載重演過兩次的形狀。
- **「一輪之內中止」是替既有操作加上第二個早退條件** → CLAUDE.md 記著這一類要把路徑上所有早退
  grep 一遍。已知路徑上另有兩處早退（`delivered >= maxPerRound` 的上限、`scanned.failure` 的
  `continue`），而**新的中止必須排在既有兩者之前判斷**，否則「上限已滿」會先吞掉它。
- **水位語意不得被中止動到** → 中止時已掃完的頻道其水位照常前進，未掃的頻道下一輪重來。
  這與既有的 `continue` 語意相同，中止只是少送了註定失敗的請求。斷言要明寫。
- **時鐘必須走 `deps.now()`** → 直接呼叫 `Date.now()` 會讓假時鐘測不到，而症狀是測試通過但
  行為錯（既有的週期輪詢測試就是靠這個注入點）。
- **替身要新增能力（回 429）** → 那份替身現在只會回 200；不先做這件事，整條路徑會是零覆蓋，
  而「補一條 scenario 與覆蓋一條 scenario 是兩個動作」是本 repo 重演過五次的教訓。

## Migration Plan

無資料格式變更、無持久狀態變更（D8）、無設定項變更。退版即回到現行行為。
