## Purpose

讓使用者從對話 view 送出訊息與選擇給 agent，並以 agent 自己回報的等待狀態決定何時可以送出，
使「答案被打進錯的地方」在結構上不會發生。

## ADDED Requirements

### Requirement: 送出的許可由 agent 回報的等待狀態決定

系統 SHALL 依 `agent-event-bridge` 的等待狀態決定是否接受送出：

| 等待狀態 | 自由文字 |
|---|---|
| 就緒 | 接受 |
| 忙碌 | 接受 |
| 等待選擇 | **拒絕** |
| 未知 | **拒絕** |

判定 SHALL NOT 以終端畫面的內容為依據。

**agent 正在等待使用者許可（工具核准、計畫核准）SHALL 歸入「等待選擇」，SHALL NOT 停留在
「忙碌」或被歸入「就緒」。** 這不是狀態機的一個角落，**它就是本能力存在的理由本身** ——
一則被送進許可提示的自由文字，其後果是替使用者做出一個他從未同意的決定。

因此本條對**訊號的及時性**有要求，而不只對分類正確性：等待許可的狀態 SHALL 於該提示對使用者
出現之前或同時成立，SHALL NOT 晚於它。一個「提示已經在畫面上、而狀態仍是忙碌」的窗口，
與完全沒有這個狀態是等價的 —— 因為忙碌是允許送出的。

**「未知」是其餘一切，不是一份列舉。** 任何無法明確歸入前三者的情況 SHALL 為未知 ——
包含系統尚不認得的等待方式。以列舉實作的判定會在 agent 新增一種等待方式時靜默落回其他分支。

#### Scenario: 就緒時送得出去

- **WHEN** 某個 agent session 的等待狀態為就緒，使用者於對話 view 送出一則訊息
- **THEN** 該訊息送達 agent

#### Scenario: 忙碌時仍可送出

- **WHEN** 某個 agent session 的等待狀態為忙碌，使用者於對話 view 送出一則訊息
- **THEN** 該訊息送達 agent

#### Scenario: 許可提示出現時不停留在忙碌

- **WHEN** agent 於執行工具的過程中提出一個需要使用者許可的請求
- **THEN** 自該請求對使用者出現起，該 session 的等待狀態即為等待選擇
- **AND** 不存在一個「請求已出現而狀態仍為忙碌」的窗口

#### Scenario: 系統不認得的等待方式歸入未知

- **WHEN** agent 進入一種系統尚不認得的等待狀態
- **THEN** 該 session 的等待狀態為未知
- **AND** 自由文字送不出去

### Requirement: 等待狀態未知時拒絕送出，並指向終端 view

等待狀態為**未知**時，系統 SHALL 拒絕送出，SHALL 說明原因，且 SHALL 指出使用者可切換到終端
view 直接操作。

**SHALL NOT 在未知時試送。** 兩種失敗的代價不對等：「不確定就送送看」的失效是把內容打進一個
正在等待其他輸入的位置（已知的真實後果包含替使用者做出未經同意的選擇）；「不確定就不送」的
失效只是使用者多切換一次 view。

#### Scenario: 未知時拒絕並說明

- **WHEN** 某個 agent session 的等待狀態為未知，使用者嘗試於對話 view 送出
- **THEN** 該內容未被送達 agent
- **AND** 呈現拒絕的原因與切換到終端 view 的指引

#### Scenario: 未注入事件回報時對話 view 仍可讀

- **WHEN** 某個 agent session 未注入事件回報
- **THEN** 對話 view 照常呈現其內容
- **AND** 送出入口為停用狀態並說明原因

### Requirement: 等待選擇時拒絕自由文字，並呈現正在等待什麼

等待狀態為**等待選擇**時，系統 SHALL 拒絕送出自由文字，SHALL 呈現 agent 正在請求什麼
（其請求的對象與辨識參數），且 SHALL 指出使用者可切換到終端 view 回答。

呈現的內容 SHALL 來自事件所帶的資料，SHALL NOT 由系統自行推測。

**本能力 SHALL NOT 提供在此 view 內作答的入口。** 這是一條刻意的界限：

- agent 回報的事件**不含它呈現給使用者的選項**（實測 2026-09-06、CLI 2.1.263：許可請求的
  payload 帶的是「要不要改變權限規則」的建議，**不是畫面上那幾個選項**）。
- 因此在此作答只能靠**猜測終端畫面上的編號或位置** —— 而那正是本 change 明文禁止的依賴。
  猜錯的後果不是「沒有反應」，是**替使用者做出一個他從未同意的決定**。

**知道「正在被問什麼」本身即為價值**：使用者不必先切回終端才發現 agent 卡在一個提示上。

#### Scenario: 等待選擇時自由文字送不出去

- **WHEN** 某個 agent session 正在等待選擇，使用者嘗試送出一段自由文字
- **THEN** 該文字未被送達 agent
- **AND** 呈現 agent 正在請求什麼，以及可切換到終端 view 回答

#### Scenario: 不提供在此 view 內作答的入口

- **WHEN** 某個 agent session 正在等待選擇
- **THEN** 此 view 不呈現任何可送出選擇的入口

#### Scenario: 於終端 view 作答後狀態離開等待選擇

- **WHEN** 某個 agent session 正在等待選擇，使用者於終端 view 完成作答
- **THEN** 該 session 的等待狀態不再是等待選擇
- **AND** 自由文字重新送得出去

> 最後一條需要一個**離開**等待選擇的訊號，而它與進入的訊號不是同一個。缺了它，狀態會停在
> 等待選擇，其後每一則自由文字都送不出去 —— 使用者看到的是「送出入口壞了」。

### Requirement: 送出的內容在其抵達紀錄之前呈現為未確認

系統 SHALL 於送出後立即呈現該內容，並 SHALL 將其標示為**尚未確認**，直到它出現在該 session
的紀錄中為止。

**SHALL NOT 直接呈現為已送達的訊息** —— 送進 pty 不等於 agent 收下了它。兩者一致時使用者
看不出差別，不一致時（agent 沒收到、或收到的與送出的不同）使用者會看見一則從未發生的訊息。

一段時間內未出現於紀錄時 SHALL 明示，SHALL NOT 無限期保持未確認而不說明。

#### Scenario: 送出後先呈現為未確認

- **WHEN** 使用者於對話 view 送出一則訊息
- **THEN** 該訊息立即呈現且標示為尚未確認
- **AND** 它出現在紀錄中之後該標示消失

#### Scenario: 未出現於紀錄時明示

- **WHEN** 使用者送出的訊息在一段時間內未出現於紀錄
- **THEN** 呈現該訊息未被確認，並指出可切換到終端 view 查看

### Requirement: 送出的內容不得被詮釋為終端控制序列

送出的內容 SHALL 被 agent 當作訊息文字接收，SHALL NOT 因其中含有控制字元而觸發終端的控制行為、
中斷 agent、或**使該訊息未能送達**。

**未能送達是本條實際觀察到的失效方向，而它比「被誤解」更難察覺** —— 使用者看不到任何錯誤，
只會以為自己沒按到送出。

多行訊息 SHALL 作為單一則訊息送達，SHALL NOT 因換行而被中途送出。

**本條的觀察對象是「agent 實際收到了什麼」，SHALL NOT 以「本應用程式送出了什麼」代替。**
後者是同義反覆 —— 它斷言我們送出了我們決定要送的東西。可行的觀察方式是自 agent 的紀錄讀回。

#### Scenario: 含控制字元的輸入不觸發控制行為

- **WHEN** 使用者送出一段含有終端控制字元的文字
- **THEN** agent 的紀錄中出現一則對應的使用者訊息
- **AND** 該 session 未被中斷、其 pty 仍在執行

#### Scenario: 多行訊息作為單一則送出

- **WHEN** 使用者送出一則含有多行的訊息
- **THEN** agent 的紀錄中出現**恰好一則**使用者訊息，且其換行完整保留
- **AND** 不產生多則訊息
