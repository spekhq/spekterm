## Context

動機見 `proposal.md` 的 Why。這裡只放推導這個作法所需要的現場。

**落點的監看只掛一次。** `HandoffService.start()` 在 app 啟動時對 `outbox/` 根建立一個
`depth: 1` 的監看者，此後不再重建。每個 session 的落點是它底下的一層子目錄。

**落點的建立則每次 spawn 都跑一次。** `prepareOutbox()` 目前是
`rmSync(dir, { recursive: true })` 接 `mkdirSync(dir)`。監看者綁定的是目錄這個**對象**
（inotify watch 掛在 inode 上），不是它的路徑；刪掉再建立之後路徑同名而對象已換，監看者留在
一個不再有任何動靜的舊對象上。

**它的失效形狀有一個會誤導診斷的細節**（實測，chokidar 5，`depth: 1`）：那次替換**不發出任何
目錄事件**（沒有 `unlinkDir`、沒有 `addDir`），於是「在 `unlinkDir` 時重新掛上」這條補救路徑
**結構上不存在**。但落點裡若有殘留檔案，刪除它們**會**發出 `unlink` —— 也就是說，一個掛
`watcher.on('all', …)` 去診斷的人會看到那個落點**確實有事件流出來**，因而排除掉「監看死了」
這個假設。**看到事件不代表監看還活著。**

**而它是一個競態，不是一個確定的規則** —— 這一條決定了修法的方向：

| 落點的準備方式 | 其後寫入的投遞 |
|---|---|
| 落點已存在，rm + mkdir 不讓出 event loop（現況） | **收不到任何事件** |
| 落點已存在，rm → 讓出一個 tick（`await sleep(0)`）→ mkdir | `unlinkDir` → `addDir` → `add`，正常 |
| 落點已存在，**不刪除目錄** | `add` 正常 |
| 落點**不存在**，rm + mkdir（新建的 session） | `addDir` → `add`，正常 ← **這是它躲過驗收的原因** |
| 落點已存在，rm + mkdir，但監看為輪詢 | `add` 正常（輪詢對 inode 的替換免疫） |

第二列是一個陷阱：它會讓對照組變綠，而它把不變式押在「chokidar 來得及把刪除處理完」這件
時序上。

**去重的權威是狀態 index，不是落點的清空。** 一則交接的 id 由「來源 session ＋ 投遞內容的
摘要」推導，重複投遞回 `DUPLICATE` 且 `consume: true`，且 `IntakeStore` 的紀錄不過期 ——
一份已經處理過的殘留即使被重讀，既不會建立第二個 session，也不會留在落點裡。

**而 session 的識別碼不重複。** 於是 `prepareOutbox()` 清得到的殘留**只有一種**：同一個 session
在上一次 app 執行中留下的東西 —— 而那正是啟動掃描本來就會讀到的。真正沒有清理路徑的孤兒落點
（app 被強制結束、該 session 再也不會被 spawn），它**永遠碰不到**。

## Goals / Non-Goals

**Goals:**

- 被重新準備過的落點，其後寫入的投遞**仍被偵測**。
- 這件事由**結構**保證（我們根本不碰那個目錄），不由時序、也不由補救掃描保證。
- 載體在「落點曾被重新準備」的情境下驗 —— 新建落點的情境驗不出這件事，而既有的載體全部在那一側。
- 順帶關閉一個既有的資料損失：一則尚未被消費的待處理交接不再於下次 spawn 時被銷毀。

**Non-Goals:**

- 不動監看層（`IntakeSource` / `createWatcher`）。
- 不改「落點隨 session 結束而清除」（`clearOutbox` 維持刪除整個目錄 —— 那時沒有人還需要監看它）。
- 不處理 app 被強制結束所留下的孤兒落點（session id 不重複，那些目錄不會再被準備一次）。
  它是既有的缺口，本 change 既不修正也不擴大它。

## Decisions

### D1：修在**建立端**，不修在監看端

落點被換掉是**我們自己做的事**，不是檔案系統或 chokidar 的不確定行為。修在建立端，
「被監看的對象被換掉」這件事就表達不出來；修在監看端則是替自己製造的狀況養一個補償機制。

考慮過並否決的替代：

- **在 `unlinkDir` 時重新掛上** —— 實測那個事件根本不會發出（見 Context）。**這條路不存在。**
  落點裡有殘留時發出的 `unlink` 也不能當鉤子：落點為空時它同樣不發。
- **落點改用輪詢監看**（`usePolling`）—— 實測輪詢對 inode 的替換免疫，但它是一個永久的喚醒成本，
  且它掩蓋的是一個我們有能力不製造出來的問題。
- **每次準備落點就重建整個監看者** —— 可行但成本是 O(還原的 session 數) 次監看重建，
  且每次重建都要跟一次掃描；用一個重的機制去換一個我們可以直接不做的動作。

### D2：`prepareOutbox()` **不再移除任何東西**

改為：落點不存在就建立，已存在就**保持原樣**。清除殘留這個動作整個移除。

**「只清掉目錄裡的項目、保留目錄本身」也能修好偵測，但它輸給「完全不清」** —— 兩者都讓被監看的
對象不被換掉，差別在清除這個動作本身還留不留：

| | 完全不清（採用） | 只清內容 |
|---|---|---|
| 偵測修好了嗎 | 是 | 是 |
| 不變式 | 「我們根本不碰那個目錄」—— grep 得到、無法被悄悄違反 | 「我們不換掉那個目錄」—— 仍須逐一檢查清除的寫法 |
| 清得到什麼 | — | **只有同一個 session 上一輪的殘留**，而啟動掃描本來就會讀到它 |
| 清不到什麼 | — | 真正的孤兒落點（Non-Goals 已排除） |
| 代價 | 被放棄的半成品永久留在落點中 | **會銷毀一則尚未被消費的待處理交接** |
| 失敗模式 | 無 | 逐一移除若不是遞迴的，遇到 agent 建的子目錄會整個拋錯 ⇒ 該 session **完全不注入交接**（`prepareOutbox` 的 `catch` 回 `null`），而畫面上什麼都沒有 |

決定性的是最後兩列：清除這個動作**清得到的東西幾乎是空集合**，而它的代價是真的會毀掉使用者的
一件工作交辦。**移除它比保留它更小、更強，而且當場關掉一個既有缺陷。**

**現場那行註解所寫的理由本來就不成立** —— 它寫的是「上一輪的殘留會讓一則早就處理過的交接在
重建之後又被投遞一次」，而處理過的早已被消費，即使沒有，去重也會在建立 session 之前擋下。
一個寫著錯誤理由的防護，下一個人無從判斷它可不可以被拿掉。

**但落點路徑被佔成檔案時仍須重建。** 實測 `mkdirSync(p, { recursive: true })` 在 `p` 已存在且
不是目錄時拋 `EEXIST` ⇒ `catch` ⇒ 該 session 靜默失去交接能力（而舊的 rm+mkdir 會自癒）。
因此準備的判定是：**是目錄就什麼都不做，不是目錄（或不存在）才移除後建立。**

> **這同時劃出修法保證的邊界**：它保證的是「**我們**不換掉它」，不是「它不會被換掉」。
> 落點被外力刪除或取代時仍然需要重建，而那一次重建照樣會讓監看失效 —— 規格的 SHALL 是絕對
> 措辭，涵蓋不到這個情形。這個缺口不在本 change 的範圍內。

### D3：**不**以「rm 與 mkdir 之間讓出一個 tick」修

實測它會過（見 Context 第二列），而那是最糟的一種「過」：不變式被押在 chokidar 的處理速度上，
機器忙一點、落點裡的項目多一點就可能再度失效，**而失效仍然是靜默的**。
D5 的第三條載體就是為了讓這個變體**紅得起來**。

### D4：不加「spawn 時順便掃一次落點」的補救網

它**擋不住這個缺陷** —— 現場那兩份投遞是在 spawn 之後九分鐘才寫進去的，掃描早就跑完了。
它能做的只是把 spawn 當下已存在的殘留撿起來，而那與本缺陷無關。加了它的實際效果是讓下一個
讀這段程式碼的人以為有一張網。

### D5：載體三條，而它們各自證明不同的事

| 載體 | 驗什麼 | 少了它會怎樣 |
|---|---|---|
| 主行程單元測試（真 chokidar、真檔案系統、暫存目錄） | 監看者掛上一個既有落點之後，對它呼叫一次 `prepareOutbox()`，其後寫入的投遞**經監看路徑**被處理 | 沒有任何東西證明偵測真的修好了 |
| `probe-intake.mjs` **新增的段落** | 被**還原**的 session 其落點寫入的交接建立了目標 session | 驗不到被出貨的那份程式碼與真實的還原路徑 |
| 「落點沒有被換掉」的結構判準 | 準備動作前後，落點**是同一個目錄物件** | **D3 那個陷阱實作會讓上面兩條全綠** —— 規格的「SHALL NOT 由時序保證」就沒有任何東西在守 |

**第三條的判準：準備之前對落點開一個 fd，準備之後讀 `/proc/self/fd/<n>`。** 路徑尾端出現
` (deleted)` 即代表那個目錄已被換掉。實測：rm+mkdir 之後為 `… (deleted)`，不刪除則乾淨。
**Linux-only** —— 其餘平台 skip 而非通過（`polling-mount.testkit.ts` 已有「環境造不出前提就
skip」的先例）。

> **不要用 inode 號碼當這個判準。** 實測 ext4 在 `rmSync` 之後立刻 `mkdirSync`，
> **20/20 次 inode 被重用** —— 一個以 inode 比對的測試會是一盞永遠亮綠的燈，
> 而它是下一個人第一個會想到的辦法。

**斷言的形狀是承重的。** 前兩條必須是「重新準備之後寫入的投遞被偵測到」，
**SHALL NOT 寫成「`prepareOutbox` 沒有呼叫 `rmSync`」** —— 那釘住的是實作，任何等價重寫都會
讓它無謂地變紅。第三條釘的是**可觀察的結構事實**（那個目錄還是不是同一個），不是某一行程式碼。

**單元測試的禁令要寫對**：`IntakeSource.start()` 內部最後一件事就是 `scan()`，測試一定要
`start()`。真正要禁的是**投遞寫入之後不得再直接或間接觸發 `scan()`** —— 包含一個不明顯的入口：
`HandoffService.endSession()` 會先 `await scan()` 再清除落點。走了掃描，舊實作照樣通過。

**probe 走「種入 ＋ 一次啟動」**：啟動前在 profile 中種一份 `sessions.json` 與對應的
`outbox/<id>/` 目錄，app 啟動時監看先掛上該落點、其後還原該 session 並重新準備它。
`probe-terminal.mjs` 的 `runDormantHint` 已有完整前例（種 `sessions.json` → 一次啟動 →
選 folder → 喚醒），替身 agent 也本來就同時吃 `--session-id` 與 `--resume`。

**而這一段需要一條正面前置**：本缺陷的必要條件是「監看**先**掛上該落點，`prepareOutbox` 才跑」，
而那在 probe 裡只靠時序成立 —— `handoffService.start()` 不被 await，失敗時也只 `console.error`。
少了前置，這一段在**舊實作下可能照樣全綠**。前置的作法：另種一個**沒有對應 session** 的孤兒
落點，在畫面就緒之後（啟動掃描早已結束）往它寫一份目標查無的投遞，斷言出現對應的失敗痕跡。
那證明監看活著且事件路徑通到底，且不會多開一個 session 污染其後的計數。

### D6：對照組兩條，分別指名它們該讓什麼變紅

`scripts/intake-control-groups.mjs`：

1. 把 `prepareOutbox` 退回「刪掉再重建」，`command: 'test'`，指名單元測試那條。
2. 同一個 mutation 走 probe，指名新增段落的那條斷言（要填 `section`）。

**兩條都要**：只登記其中一條，另一個載體就從來沒有被證明有鑑別力（該腳本檔頭明文警告過
這個形狀）。

> **原本規劃的第三條 mutation（「rm → 讓出一個 tick → mkdir」，用來單獨證明 fd 判準的鑑別力）
> 寫不出來** —— `prepareOutbox` 是同步函式，同步函式裡讓不出 event loop tick；改成非同步會
> 連帶改掉呼叫端，那就不是一個 mutation 了。因此 fd 判準與前兩條**共用第 1 條 mutation**
> （實測三條單元測試同時變紅）。它獨立的價值不在那個 mutation，而在**與時序無關**：日後這支
> 函式若變成非同步、或 chokidar 改以路徑重新掛上（R4），前兩條會開始變綠，而它照樣紅。
> 這一點寫在測試自己的註解裡。

## Risks / Trade-offs

- **R1：被放棄的半成品會永久留在落點中。** 一份寫到一半就沒有下文的 `.json` 不被消費，
  而準備動作不再清它 —— 它會在每次啟動掃描與每次 `endSession` 的掃描被重讀一次。
  → 代價是一次解析失敗（不消費、不通知），量級可忽略；落點隨 session 結束整個刪除，
  它不會無限累積。**以這個代價換掉「會銷毀一則真實待處理交接」是划算的。**
- **R2：單元測試用真的監看者，有 flaky 的體質。** → 以有界輪詢等待（不用固定 `sleep`），
  且失敗訊息要分得出「沒有收到事件」與「收到了但內容不符」—— 兩者的處置完全不同。
- **R3：probe 那一段的前置只靠時序成立。** → 見 D5 的孤兒落點前置。**這才是該擔心的事**；
  種入的還原本身沒有風險（`runDormantHint` 的前例與替身 agent 的 argv 處理都已確認）。
- **R4：chokidar 升級可能改變這個行為**（例如未來版本改以路徑重新掛上）。 → 那會讓 D6 的
  對照組變成「不再變紅」，而那正是它該發出的警報；屆時重新論證 D2 是否還承重，不要因為
  對照組不紅就把它刪掉。**這句話要寫進 mutation 的 `why` 欄位** —— 它在對照組跑起來時會被
  印出來，而這份 design 封存之後沒有人會再讀它。

## Migration Plan

無資料遷移：落點的位置、結構與投遞格式皆未改變。現場那兩份未被偵測的投遞已於使用者重新啟動
應用程式時由啟動掃描結清，不需要任何一次性處置。

退場：把 `prepareOutbox` 改回刪掉再重建即可，沒有任何持久化狀態依賴這個改動。
