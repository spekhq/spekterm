## Why

**收件匣目前只有在使用者主動去點它的時候才存在。**

活動列的 Handoffs 圖示沒有任何狀態：收件匣裡躺著三則待處理項目，和一則都沒有，畫面上**一模一樣**。
`agent-intake-inbox` 落地時這還說得過去 —— 那時唯一的 producer 是使用者自己用腳本投遞的，他知道自己
投了什麼。

**`slack-mention-intake` 落地之後，這個前提消失了。** 現在項目是**別人**在**任意時刻**推進來的：
有人在 Slack 提及使用者，那件事成為一則待處理項目。而沒有任何東西告訴他這件事發生了。

這掏空了上一個 change 的價值命題。那個 change 把「不遺失」做得很完整（三個回補觸發點、rate limit
退讓、去重），但**「不遺失」與「使用者知道」是兩件事**：項目確實安全地躺在收件匣裡，而使用者仍然
只能靠自己回去 Slack 看到那則提及 —— 那正是這條管線本來要取代的動作。一條沒有人知道它有東西的
管線，等於沒有這條管線。

## What Changes

三件事，它們是同一個問題的三個時間尺度：

1. **Handoffs 入口帶一個待處理數的標示。** 數字是**目前 pending 的項目數**（接受或忽略才減少，
   跨重啟保留 —— 那份狀態本來就落盤）。這是「我現在有幾件事沒處理」，長期有效。
2. **新項目進來時發一則作業系統原生通知。** 這是「剛剛發生了一件事」，而且**必須是作業系統的**
   —— 桌面 app 大多數時間不在前景，一個只在視窗內冒出來的提示在最需要它的時候剛好看不見。
3. **點下通知把視窗帶到前景並打開收件匣。** 通知的用途是把人帶到那則內容前面；只是閃一下而點了
   沒有反應，會被當成壞掉。

連帶必須處理的兩件事：

- **badge 需要一個常駐的訂閱者。** 目前 `intake:changed` 只有收件匣 overlay 在聽，而 overlay 只在
  開著時掛載；更麻煩的是主行程的收件者集合是在 renderer 第一次呼叫 `list()` 時才註冊的 ——
  **一個從來沒被打開過的收件匣，其變化不會推給任何人**。
- **通知的內容含第三方逐字撰寫的文字**（標題、發起者、來源標籤）。它必須走與收件匣呈現**同一份
  已正規化的值**，不得走原始內容；並且**總量必須有上界** —— 與 `agent-intake` 既有那條「面向使用者
  的拒絕與警示 SHALL 有界」同一條理由：一波 Slack 提及不得變成桌面上一排通知，那會同時磨掉通知
  這個通道本身的價值。

**不做的**：作業系統工作列／Dock 的 badge（`app.setBadgeCount` 在 Linux 上只有 Unity launcher 吃，
在這台機器上是靜默無效的，而靜默無效的東西不該做成 requirement）；通知的開關偏好（先看 dogfood
會不會吵，會吵再開一個 change 加旋鈕，不要預先造一個沒人轉的旋鈕）。

## Capabilities

### New Capabilities

無。這是既有兩個能力的擴充，沒有新的概念邊界。

### Modified Capabilities

- `agent-intake`（**新增**八條）：未處理的項目數在不打開收件匣時可見且與收件匣同源、新項目到達時
  發出通知且合併與總量皆有界、通知的內文取自已正規化的值且第三方欄位進入前先縮減、通知只有一種
  效果且不取用遠端資源、已顯示的通知必須被持有至結束、觸發通知把視窗帶到前景並打開收件匣、
  通知綁定於到達（回補進來的要通知／落盤中既有的不重新通知）、通知不可用時靜默降級。
  既有條文沒有一條需要改寫。
- `workspace-layout`（**新增**一條）：活動列的入口得攜帶一個由其背後能力決定的計數標示，
  而該標示不改變入口尺寸、無數時不佔位、不使入口列舉多出一項、且**不改變入口本身的無障礙標籤**
  （最後一項是承重的：那個標籤同時是驗收定位元素的手段）。
- `ui-localization`（**修改**「使用者可見的文案為英文」）：作業系統原生通知的標題與內文是
  **第五類**使用者可見文案。那條 requirement 目前把清單封閉在四類，而第 3 類的定義是「主行程
  **經 IPC 送達畫面**的錯誤訊息」—— 通知兩者都不是（它不過 IPC，由作業系統畫在 app 的框之外）。
  **這一條在第一版被誤判為「就是第 3 類」而完全沒有 delta**，而 CJK 守衛對兩者一視同仁，
  所以那個誤判不會讓任何東西變紅。

## Impact

**主行程**

- `src/main/intake-service.ts`：新增**到達**的訂閱通道。**既有的 `subscribe()` 與
  `DeliverOutcome.notify` 都不是它** —— 後者的語意是「這則**拒絕**要不要讓使用者看到」，
  成功路徑上恆為 `false`。這是本 change 唯一一處「接錯了就整條功能反過來」的地方。
- 新模組：通知的決策層（窗口、合併、上界、文字組裝與縮減），**不碰作業系統**。
- 新模組：通知的後端 —— 全 repo 唯一 import Electron 通知 API 的地方，且負責持有已顯示的通知。
- `src/main/ipc/intake.ts`：新增一條主 → renderer 的「打開收件匣」訊息。
- `src/main/index.ts`：組裝（含替身後端的選擇）、觸發時把視窗帶到前景。

**Renderer**

- 一個常駐於 `AppShell` 之下的收件匣狀態 provider（與 `PrefillProvider` 同一層）。
- `IntakeOverlay.tsx`：改為讀該 provider，並修掉一個既有的焦點缺陷（見 design D1／D8）。
- `ActivityBar.tsx`：入口帶計數標示；接收「打開收件匣」的指示。

**其他**

- `src/preload/index.ts`：`intake` namespace 新增一條訂閱。
- `src/shared/i18n/en.json`：通知與標示的文案。**通知的文案是 `ui-localization` 的第五類**。
- `scripts/intake-control-groups.mjs`：**先**把執行器補成能跑 `npm test` 級的 mutation
  （`slack-control-groups.mjs` 已有該分支，intake 這支沒有），否則本輪多數對照組判不出紅燈。
- `scripts/probe-intake.mjs`：計數與通知的段落，以及**本探針的第一個重啟段落**
  （`RESTART_PORT` 已保留但至今未使用）。
- `scripts/intake-coverage.test.mjs`：本 change 要登記進 `COVERED_CHANGES`。
- 新的 `npm test` 原始碼守衛：Electron 通知 API 的單一引用點。

**已知的覆蓋缺口**（全部要寫進規格，不是留在這裡）

- 「通知真的出現在桌面上」與「app 在背景時仍然發出」沒有載體 —— dogfood 認定。
- 桌面服務對內文的視覺再詮釋（折行、截斷）不在載體視野內 —— dogfood 認定。
- **通知不可用時偵測不到**：實測「支援通知」的回報在完全沒有通知服務時依然為真，而顯示既不拋錯
  也不回報失敗。已裁決不做主動偵測。
- 「視窗真的浮到前景」本輪不建置驗收環境 —— **是「本輪不做」，不是「做不到」**。
- 拒絕在收件匣之外自此完全看不見（已裁決的取捨）。
