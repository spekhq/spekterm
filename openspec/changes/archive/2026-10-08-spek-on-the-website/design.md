## Context

The site (`site/`, Astro + Starlight 0.42.5) is one Starlight project with two locales (root English,
`/zh-tw/`), a build that is its own gate (`site/scripts/build.mjs`: type check, content guards, link
validator, parity, origins, notices, content), and screenshots that come only from
`scripts/capture-screenshots.mjs`. Component overrides in place: `Footer` (disclaimer, source / license /
notices links), `Hero` (platform status under the download button). A route middleware
(`src/routeData.ts`) adds the share image and its alt text. Config-level, site-wide today: the title
("spekterm", which Starlight turns into the `<title>` suffix and `og:site_name`), the `social` GitHub link
(header and mobile menu), the `apple-touch-icon` head entry.

Facts about spek below come from the spek repository at v1.19.0 (2026-10-06; `v1` points at the same
commit): a web app (git clone + `npm run dev`, not on npm), a VS Code extension (`kewang.spek-vscode`), a
JetBrains plugin (`tw.kewang.spek`, IDEs 2023.3+, no worktree aggregation, runs only the `openspec` CLI,
serves its API through the IDE's built-in server), and a GitHub Action (`spekhq/spek@v1`, builds a static
HTML viewer and optional badges; `spek-version` defaults to `master`). Its interface has one language
(English). Its committed screenshots show a maintainer home path. Its static pages and web app load
Google Fonts; rendered markdown loads remote `https:` images except in VS Code (CSP). Its web app's API
server listens on port 3001 with no host (all interfaces) and `cors()` with no options, and
`/api/fs/browse` lists any directory. Its static-page builder shows the header repository label as the
fixed text "demo".

## Goals / Non-Goals

**Goals:**
- A reader on either product's pages sees that product only — its brand, its navigation, its repository —
  and can cross to the other product in one click.
- spek's pages are held to the same honesty as spekterm's: what it runs, what it connects to, and
  screenshots that show nothing of anyone's machine.

**Non-Goals:**
- Changing spek's repository, README, package metadata, or marketplace listings.
- Hosting spek's live demo on spekterm.com: it loads Google Fonts, which the site's origin check forbids;
  the site links to the demo on GitHub Pages.
- A shared "family" landing page at the root (the maintainer chose spekterm at the root, spek under
  `/spek/`).
- Separate search per product: one Pagefind index across both is intended — a result from the other
  product is a cross-link.

## Decisions

### D1. One Starlight site; the product comes from the path, in one shared module

A page belongs to spek when its path without the locale prefix starts with `/spek/`. That function and
each product's constants (landing path, name, logomark, tab icon, share image, home-screen icon,
repository, share-image alt key) live in `site/src/product.mjs` — plain JavaScript holding path strings
only (no image imports, so plain Node can load it) so that both the site
(Astro/TS imports it) and `site/scripts/check-content.mjs` use the same code instead of a mirror. Its
behavior is covered by check-content's self-test (paths `/`, `/docs/x/`, `/spek/`, `/zh-tw/spek/docs/x/`,
`/spekx/`, `404.html`), which runs in every build; no separate unit-test runner is added under `site/`.

*Alternatives:* two Starlight projects under one domain (two builds, two search indexes, two copies of the
gate, and the language switch and canonical rules would have to agree across them); the
`starlight-sidebar-topics` plugin (a dependency for what a short filter does, which the notices and origin
checks would then have to take in).

### D2. Header: the product's title, and a switch to the other product

Override Starlight's `SiteTitle`: it renders the current product's logomark and name linking to its landing
page in the page's locale, then a compact link to the other product's landing page (label from the site's
dictionary). Starlight's `.title-wrapper` clips what does not fit (`overflow: clip`), so "no horizontal
overflow" cannot show a missing switch; the phone check measures the switch's bounding box against the
wrapper and the viewport instead (task 6.4).

The `social` GitHub icon becomes per product by overriding `SocialIcons` (it links to the product's
repository from `product.mjs`), since the config's `social` list is site-wide.

### D3. Sidebar and previous / next: one config, filtered in the route middleware

`astro.config.mjs` lists spekterm's groups and spek's groups (spek's autogenerated from
`spek/docs/<group>`; autogenerate matches by directory prefix, so `docs/…` does not take in
`spek/docs/…`). The route middleware receives a deep copy of the route data and may change it: it drops
from `starlightRoute.sidebar` the top-level groups whose links are not under the current product, and
recomputes `starlightRoute.pagination` from the filtered sidebar's flattened links — Starlight's own
function for that is not exported. Frontmatter `prev` / `next` overrides are not honored by the
recomputation; no page uses them, and check-content fails if one ever does, so the omission cannot go
unnoticed.

### D4. Brand per product through the route middleware

The middleware chooses by product: spekterm keeps `/favicon.svg`, `/apple-touch-icon.png`,
`/og/en.png`, `/og/zh-tw.png`; spek gets `/spek-favicon.svg`, `/spek-apple-touch-icon.png`,
`/og/spek-en.png`, `/og/spek-zh-tw.png`. Starlight's tab-icon link is in `starlightRoute.head` (`rel=
"shortcut icon"`), so the middleware replaces its `href` rather than adding a second link; the
home-screen icon moves from the config's `head` into the middleware for the same reason. spek's marks are
copied from spek's `logo/` into `site/src/assets/spek/` (the commit recorded in `site/README.md`);
`scripts/make-brand-images.mjs` derives spek's tab icon, home-screen icon, and share images from them, as
it does spekterm's from `build/icon.svg`.

### D5. The other product-specific parts

- **Title suffix and `og:site_name`.** Starlight computes them from the config title before the middleware
  runs; the middleware rewrites the `<title>` entry's suffix and the `og:site_name` content on spek pages.
- **Share-image alt text.** Per product from the dictionary (`social.imageAlt`, `social.spekImageAlt`).
- **Hero.** The platform status under the download button is printed only on spekterm pages.
- **Footer.** The source and license links target the page's product's repository and license; the notices
  link is shared (one site, one notices file).
- **Disclaimer.** One statement on every page naming both projects.

### D6. Language-neutral screenshots live apart

spek's screenshots go to `site/src/assets/screenshots/neutral/`. `check-parity` compares `en/` and `zh-TW/`
only (unchanged); the manifest test walks every file under `screenshots/` recursively, so neutral ones are
covered. Captions and alt text are per language as usual.

*Alternative:* each spek screenshot twice under `en/` and `zh-TW/` — identical files that satisfy the check
while saying nothing, and every recapture must keep two copies equal.

### D7. spek screenshots: spek's own static builder, run against the fixture repository

The capture script gets a second loop for spek shots (the existing loop is language × spekterm shot and
writes per language; spek shots are written once, to `neutral/`). It:

1. Takes a spek checkout from `SPEK_DIR` (default `../spek`) and refuses one that has uncommitted changes
   or whose HEAD carries no release tag, naming the reason. A release tag is `v<major>.<minor>.<patch>`
   (`git tag --points-at HEAD --list 'v*'` filtered by `^v\d+\.\d+\.\d+$`): HEAD also carries
   `core-v…`, `ui-v…`, and the moving `v1`, and `git describe --exact-match` returns one of those. The tag is
   written to `site/src/assets/screenshots/neutral/SOURCE` — not into the manifest, whose every key the
   manifest test reads as an image path. It then rebuilds spek's core and ui in the checkout (`npm run
   build:core && npm run build:ui`; their `dist/` are git-ignored, so a clean tree says nothing about them,
   and the rebuild writes only there).
2. Runs spek's builder with the checkout's own `node_modules/.bin/tsx` (not `npx`, whose update notifier
   contacts the npm registry): `scripts/build-demo.ts --repo-dir <fixture> --output <tmp>/spek.html
   --title spek`, in the same allow-list environment as the spekterm shots (invented `HOME`,
   `OPENSPEC_TELEMETRY=0`, `DO_NOT_TRACK=1`) — the builder calls the `openspec` CLI three times, which
   would otherwise read the maintainer's global configuration and send usage statistics. The builder
   writes and removes a temporary `packages/web/dist-demo` inside the checkout; it leaves no change behind.
3. Opens the page in an Electron window under the virtual display at 1440×900 @2x, navigates with spek's
   hash routes (`#/`, `#/changes/add-rate-limiting`, …), and before each capture applies the hygiene
   read with a positive control taken from what that page shows: the static page's header reads "demo",
   not the repository name, so the control is fixture text the page renders (for example the auth spec's
   purpose sentence), chosen per shot.
4. Checks that the font loaded (`document.fonts.check('1em "Plus Jakarta Sans"')`) and aborts otherwise —
   offline, the page would silently fall back to another font. The capture lets the font request through:
   it is the maintainer's machine fetching a font at capture time, not something the site or the app does.

*Alternatives:* spek's committed screenshots (they show `/home/<maintainer>/git/spek`, and some are out of
date); spek's web app (two dev servers and a repository picker to drive, for the same pixels).

### D8. Content is checked against spek's code, not its README alone

The README is not fully current (it lists Fuse.js, which spek no longer uses; it says "no data leaves your
machine" while the web app loads Google Fonts). Every statement on spek's pages is taken from the code or
metadata at the recorded tag, and must also hold on spek's default branch, which the web app and the
Action's default run. The data and network page is written per form (web app, static pages / Action, VS
Code, JetBrains), since they differ.

### D9. Checks

`check-content`, each with a self-test fixture that violates it:

- product detection (D1) over the self-test paths;
- header product link and switch targets (D2); per-product repository links in header and footer (D5);
- sidebar links and `a[rel="prev"]` / `a[rel="next"]` within the product (D3); no frontmatter `prev` /
  `next` in content;
- exactly one tab-icon link, the product's; the header logo's source is the product's (built file names
  carry a hash, so by name prefix — spekterm's `logo.` and spek's `spek-logomark.`, neither a prefix of the
  other); share image and its file, its alt text, and the home-screen icon and its file (D4, D5); title
  suffix and `og:site_name` on spek pages; no platform-status string on spek pages;
- landing pages: links are collected from `<main>` excluding `.site-footer` (Starlight puts the footer
  inside `<main>`, and the header is outside it), and text likewise excludes `.site-footer` — so "names
  OpenSpec" and "links to the other product's landing page" cannot pass on the disclaimer or the header
  switch alone; this also fixes the existing spekterm landing check, which had the same blind spot;
- disclaimer names spekterm and spek as separate words (word boundaries; "spekterm" contains "spek");
- spek topics (from a `spek` block in `content-plan.json`) and spek's network keywords per language,
  matched in `<code>` elements or on word boundaries (a bare `git` substring matches `spekhq.github.io`).

`check-parity`: its self-test gains a neutral screenshot that must not be reported (green on the current
code too; its value is pinning the exemption's location).

### D10. The spekterm landing page links into spek's part of the site

The "Built on spek" section leads with a card to `/spek/`; the GitHub and demo cards move to spek's landing
page. Its sentence that implies every form aggregates worktrees is corrected (the JetBrains plugin does
not).

## Risks / Trade-offs

- **spek's web app API server is reachable beyond the machine.** While a reader runs `npm run dev`, any
  device on the network, or any web page they open, can list their directories and read OpenSpec content
  through it. → **Decided (maintainer):** spek is fixed first (a handoff to the spek repository: loopback
  bind, no cross-origin access, host check); the page states the fixed behavior, without a warning, and is
  worded from the spek session's report of what the fix does. Until that release is out the page describes
  spek's default branch ahead of its latest release.
- **spek facts drift with every spek release.** Nothing in this repository can see spek's code. →
  `site/README.md` gains a "when spek releases" step (re-read the release against spek's pages; recapture
  the spek screenshots); no version numbers on the pages.
- **The capture depends on spek's builder flags** (`--repo-dir`, `--output`, `--title`), a built clean
  checkout at a tag, and network access for the font. → Each failure stops the spek shots with its reason;
  nothing falls back to spek's committed screenshots or a fallback font.
- **spek screenshots carry relative times** ("7d") that depend on the capture date, like the spekterm shots'
  timestamps.
- **spek's marketplace listings and README still point at GitHub**, so few readers arrive at `/spek/` from
  spek itself until spek's metadata changes (out of scope).
