## Context

動機見 `proposal.md`。這裡只列出塑形了解法的既有事實：

- **注入的接縫只有一個**（`claude` 的 `--settings`），已有兩個貢獻者（狀態列、事件橋接），
  合成器是 `composeInjection()`，逐鍵 `Object.assign`（`src/main/agent-injection.ts:76-79`）。
- **收件匣的投遞落點明文是「供應用程式之外的 producer」使用，且其內容不受信任**
  （`agent-intake` 的第一條與「落盤的位置不得由它決定」）。routing 的判準因此分成「接收端可驗證」
  與「第三方逐字撰寫」兩類，而那個分類**落在型別上**。
- **`deliver(contents, adapter)` 是投遞的唯一入口**（`intake-service.ts:171`），`adapter` 由接收端
  供應、payload 自稱的一律不採信。
- **agent 是經由 pty 執行的，它本來就能寫任何位置的檔案**，且執行環境已經把使用者資料目錄的位置
  交給它了（`SPEKTERM_EVENT_DIR`、argv 上的 `--settings` 路徑）。終端的 cwd 邊界不是沙箱
  （CLAUDE.md），本 change 也不引入沙箱。
- 預填的時機以「等待狀態首次成為就緒」為閘（`intake-prefill.ts:68-99`），而那個狀態來自事件橋接。
- **共用落點的監看寫死 `depth: 0`**（`intake-source.ts:114`，註解明寫「落點是扁平的」）。

## Goals / Non-Goals

**Goals**
- agent 不必被使用者教就知道 spekterm 存在、知道可交接的對象、知道怎麼投遞。
- 交接的**來源**由接收端決定，不由投遞內容自稱。
- 交接的**目標**是一次查表，其定義域就是告訴 agent 的那份清單所取自的來源。
- 收件匣既有的驗證、去重、context 檔、預填、通知一律沿用，不複製第二份。

**Non-Goals**
- **不是安全邊界。** agent 有 shell，它能寫的位置不受本設計約束 —— **包含別的 session 的投遞
  落點**（根位置算得出來）。本設計約束的是**投遞內容不得自行決定它落在哪個 repo**，那保護的是
  收件匣型別分類的誠實性，不是防禦一個惡意的 agent。凡是倚賴「來源不可偽造」的設計都不成立，
  D7 因此必須是全域上限。
- 不做回程、不做 MCP、不規範交接文的內容格式。
- 不為 agent 提供投遞結果的回傳通道（見 Risks）。

## Decisions

### D0. 先實測「注入的內容真的進得了 agent 的脈絡」，再依賴它

**這是整個能力唯一一個不在我們掌控中的機制**，而它在本 repo 內**沒有任何既有證據**：
`additionalContext` / `hookSpecificOutput` 在整個版控中零命中（含 `archive/` 與 `docs/lessons/`）。
repo 既有的 hook 實測只有兩條，都與此無關：注入的 hooks 與使用者 `settings.json` 的 hooks 是
**合併**（`agent-injection.ts:22-24`）、`SessionStart` 的時序（`archive/2026-09-11-agent-intake-inbox`）。

因此 D1 的形式**尚未被證實**，它是一個假設。處置與 `agent-intake-inbox` 當初對預填時序的處置
相同：**排成第一個 task，以真實 agent 實測，結論與版本寫進 `docs/lessons/`**，再往下做。

> **已完成（2026-09-17、CLI 2.1.274）：D1 的形式成立。** 合法的 `hookSpecificOutput` JSON 進入
> 脈絡；**同一事件上的兩條命令其內容都進入脈絡**（事件橋接已佔用 `SessionStart`，這一條是本能力
> 可行的前提）；純文字與格式壞掉的 JSON **原樣**進入脈絡；非零碼結束的命令其 stdout 不進入脈絡
> 且 session 照常完成（降級方向正確）。完整記錄見 `docs/lessons/handoff.md`。
> **退路未被採用，但保留在下方供日後 CLI 行為改變時參考。**

**實測要回答三件事**：(1) `SessionStart` hook 的 stdout 是否真的進入脈絡、以什麼形式；
(2) 同一個事件上的**兩條**命令其 stdout 如何處置（本 repo 一定會有兩條 —— 事件橋接已經佔了
`SessionStart`）；(3) 失敗與非預期輸出時 agent 的行為。

**不成立時的退路**：改用 `--append-system-prompt`，文字經環境變數傳遞以避開命令列長度與引號
（D1 否決它的理由是「只反映 spawn 當下」，那個代價在此可接受 —— 清單變動不頻繁）。**退路存在
是本 change 可以開工的前提**，而不是一個補充說明。

### D1. 自我介紹走 `SessionStart` hook 的 `additionalContext`，內容由檔案供應

hook 命令是 `cat "$SPEKTERM_HANDOFF_INTRO"`，spekterm 在該檔案裡放一份完整的
`{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"…"}}`。**形式待 D0 確認。**

**為什麼內容不寫死在命令裡**：可交接的對象是 workspace 的 folder 清單，**它在 session 存活期間
會變**。`SessionStart` 於 `startup` / `resume` / `compact` / `clear` 都會重跑，讀檔於是每次都拿到
當下的清單；把文字烘進命令列則永遠是 spawn 當下的那一份。

**被否決的替代**：寫進使用者 repo 的 `CLAUDE.md` —— 那是使用者的檔案，且每個 repo 都要寫一次。
（`--append-system-prompt` 不是被否決，它是 D0 的退路。）

**降級方向**：檔案讀不到 ⇒ `cat` 失敗、stdout 為空 ⇒ 沒有自我介紹，session 照常運作。

**內容要寫明目標欄位可接受名稱或絕對路徑兩種形式** —— 顯示名稱取自路徑最後一段，同名是真實
可達的，而歧義對 agent 是一條死路（它收不到任何回饋，見 Risks）。

### D2. 合成器把 `hooks` 從 `settings` 裡拉出來，成為獨立欄位

`InjectionContribution` 改為 `{ settings, hooks?, env }`，合成時 `hooks` 由合成器**逐事件串接**。

**為什麼不是「對 `settings` 做深層合併」**：那是一條通用規則去解一個特定問題，而且它把「哪些 key
可以被多人貢獻」變成隱性知識。拉成獨立欄位之後，**「兩個貢獻者各寫一份 hooks 而後者蓋掉前者」
在型別上表達不出來** —— 與 repo 既有的「使不變式無法被違反的結構優於釘住格式的測試」同一條。

**但型別上的分開只涵蓋今天已知的那一項。** 第四個貢獻者與第三個若用同一個非 `hooks` 的 key，
覆蓋會再次靜默發生。因此 `composeInjection` 對 `settings` 的重複 key **直接視為不變式違反而
失敗**（一行），而不是只靠一道守衛擋「把 hooks 寫回 settings」。spec 據此收窄為
「已知會被多人貢獻的設定項在型別上分開 ＋ 其餘的重複貢獻為明確的失敗」。

配一道原始碼守衛：`settings` 內出現 `hooks` 這個 key 即失敗。

**貢獻者的註冊順序必須釘住。** 對照組（把合成改回覆蓋 ⇒ `probe:agent-view` 變紅）的鑑別力
取決於它 —— handoff 若排在事件橋接**之前**，覆蓋語意下事件橋接仍然勝出，**對照組不會紅**。

### D3. 投遞落點是 per-session 目錄，**目錄名決定來源，但那不是不可偽造的**

`<userData>/handoff/<sessionId>/`，經 `SPEKTERM_HANDOFF_DIR` 告訴 agent。

**它擋掉的是「payload 自稱來源」這一種**，於是收件匣的型別分類不被破壞：來源是接收端算出來的，
不是投遞內容講的。**它擋不掉「agent 直接寫進別人的落點」** —— 根位置算得出來（`SPEKTERM_EVENT_DIR`
已經把 userData 給了它），而它有完整寫入權。**spec 必須誠實寫出這一點**，否則下一個人會拿
「來源不可偽造」當前提去設計別的東西 —— D7 的第一版正是這樣錯的。

**sessionId → folderId 的解析要能撐過 session 結束。** 權威是 `TerminalService#sessions`，而
`kill()` 第一件事就是把它刪掉（`terminal.ts:630`）。處置是**落點的清除發生在其內容處理完之後**，
並在清除之前完成一次歸屬解析；「來源已結束」只影響呈現，不影響能不能建 session。

### D4. 已定址的投遞**不經共用的收件匣落點**，走行程內的 `deliver()`

`deliver(contents, adapter, { targetFolderId, sourceFolderId })` —— 解析出的目標由**參數**供應，
與 `adapter` 同一個姿態。

**這一條是承重的。** 若把 `targetFolderId` 做成投遞 JSON 的一個欄位，那麼**任何**丟進共用落點的
檔案都能繞過 routing 自選 folder —— 而那個落點明文是給應用程式之外的 producer 用的。
於是「已定址」必須是一個 payload 表達不出來的東西。

**代價要誠實記下**：Slack adapter 刻意寫檔給自己讀，為的是「日後搬到另一個行程時收件匣不必改」。
handoff **結構上拿不到那個性質**（來源身分來自它落在哪個目錄，只有主行程知道），所以那個繞路對它
沒有價值。但共用落點附帶的那些保護（檔案大小上限、`.json` 才採納、解析失敗不消費、暫時性拒絕
原封留著）**是本能力自己要重新提供的** —— 作法是把 `intake-source` 的「被監看的落點」一般化，
兩邊共用，而不是各寫一份。

**一般化要連 `depth` 一起參數化。** 共用落點是扁平的（`depth: 0` 寫死），handoff 的落點是巢狀的
（`<root>/<sessionId>/*.json`）。漏掉它的失效方式特別惡劣：**啟動掃描照常運作，只有 watcher 收
不到事件** ⇒ 症狀是「即時不進來、重啟才出現」，看起來完全像一個時序問題。

### D5. 目標解析：exact match，歧義以絕對路徑脫困

先比對 folder 的顯示名稱（不分大小寫、完整相等），再比對 folder 的絕對路徑。命中多於一個 ⇒ 拒絕
並列出候選；零命中 ⇒ 拒絕。**SHALL NOT 模糊比對** —— 這條路徑沒有人在看，一個「猜得很有把握」
的錯誤會讓 session 開在他沒有指名的 repo 裡。

顯示名稱是路徑的最後一段（`workspace-store.ts:70`），**同名是真實可達的**，因此絕對路徑那條是
歧義的脫困路徑，且必須寫進自我介紹 —— agent 收不到任何回饋，它不會自己想到換一種寫法。

**告知 agent 的清單是查表定義域的快照，不是恆等。** 兩者只在注入的那一刻相同；清單其後可能縮小，
於是**零命中是可達的正常結果**。任何「agent 只會送出解得開的目標」的推論都不成立。

**目標等於來源是合法的**（在同一個 repo 開一個乾淨的 session 接手），不特別處理。

### D6. 交接的識別碼由「來源 ＋ 內容摘要」推導

**不由檔名推導**（第一版的設計如此，是錯的）：檔名由 agent 挑選，於是「唯一性由 agent 負責」——
那正是我們用來否決「由投遞內容指定識別碼」的理由，它一字不改地適用於檔名。具體失效：同一個
session 兩次交接都叫 `handoff.json`，第二則成為重複 ⇒ 內容相同則靜默丟棄、內容不同則 `DUPLICATE`
拒絕且不建 session，**而 agent 已經回報它交接出去了**。

**也不於接收時隨機產生**：落點的「先建立監看、再掃描」會讓同一份投遞被讀兩次，隨機 id 使它成為
兩則交接、開出兩個 session，而既有去重完全看不見。

內容摘要同時滿足兩端：重送冪等、不同內容自然不同。摘要的輸出字母表是 hex，滿足識別碼的字元集
白名單與「落盤檔名由識別碼可逆編碼推導」那條。

### D7. 上限是**全域**的，超過即降級為待處理

第一版寫成 per 來源 session 的滾動窗口，**在本能力的威脅模型下沒有效力**：一個失控的 agent
輪流寫進不同 session 的落點（D3 —— 位置算得出來），每個計數器都不會累積，而那正是它唯一要擋
的情境。全域計數對這件事免疫。

狀態只存在記憶體中，重啟即歸零 —— 它要擋的是**一次執行內的洗版**，而那個 agent 與計數同生共死。

**降級是「退回需要接受」而不是「拒絕」** —— 拒絕會銷毀一件真實的工作交辦，而使用者確實可能在
短時間內連續交接三件事。

**上限與窗長要可注入**：`intake-service` 對 `maxPending` 已經是這個姿態（註解明寫「驗收要造出
『達到上限』這個前提，真實值造不起」）。不可注入 ⇒ 「超過上限」那條 scenario 造不出來。

### D8. 事件回報未啟用時，交接**不建立 session**

第一版寫「仍能建立 session，預填走到逾時那條可見的路徑」，那是錯的，且錯得比看起來嚴重：

- 它與既有條款正面衝突 —— 那條明寫「已知可事先偵測的成因 SHALL 於接受之前告知」，且其 scenario
  要求 session 總數不變。
- 更糟的是它讓一條迴圈成為主幹：建 session → 等 30 秒逾時 → 退回待處理 → 使用者再處理 → 又建
  一個 → 又逾時。**每處理一次多一個空的 session，沒有上界。**

處置：事件回報關閉時直接可見地拒絕。**並且獨立地**修掉那條迴圈本身 —— 一則回到可重新處理狀態
的 intake SHALL 保留它已建立的 session 的關聯，再次處理時對既有那一個重試預填，不建第二個
（那個缺口在手動 intake 上本來就在，只是自動化把它搬到了主幹上）。

### D8b. 交接**受**待處理總量上限約束

`deliver()` 的 `CAPACITY` 閘以待處理則數為判準，而交接「從不處於待處理」聽起來像是它不該
受約束。**裁決是受約束**，理由有二：

- 它**確實**會先成為一則待處理紀錄 —— 建立 session 的是 renderer，中間隔著一次 IPC 往返。
  「從不處於待處理」講的是**使用者看到的狀態**，不是紀錄的生命週期。
- 豁免它等於讓一個 producer 推開一道保護收件匣的閘，而那道閘的存在理由（投遞者控制數量）
  對交接**更**成立：它是自動建立 session 的那一條路徑。

代價要記下：達到上限時投遞檔**原封留在落點**（`consume: false`），而重掃只發生在
`IntakeSource.start()` 與 `endSession()`。使用者清掉收件匣之後，那則交接不會自己回來 ——
要等下次啟動或該 session 結束。**這是既有的行為，本 change 不改它**，但它現在多了一個
使用者看不見的觸發來源。

### D9. 一個偏好欄位，預設啟用，**沒有 Settings UI**

與狀態橋接、事件橋接並列，啟用狀態彼此獨立（既有合成條款）。

**照 `agentEvents` 的先例：只有偏好檔裡的欄位，不加對話框開關。** 加 UI 會動到
`terminal-preferences` —— 它以列舉方式規定對話框的內容，且每個開關各有一條 requirement，
於是那會是本 change 的 Capabilities **沒有宣告**的第五個 delta。spec 要求的是「提供一個
開關」，偏好欄位滿足它。

### D10. 通知的效果分流，是一次介面變更而非參數變更

`NotifyBackend.onActivate(handler: () => void)` **不帶任何識別**（`intake-notify.ts:44`）——
「聚焦這則交接建立的那個 session」在現行介面上**表達不出來**。這條要動到通知後端的介面，
三個實作（electron / stub / 測試替身）都要跟著改。

**合併的那一則通知只陳述數量**，可能同時涵蓋待處理項與已建立 session 的交接。裁決：
**批次中含任何待處理項 ⇒ 效果為打開收件匣。** 否則那些待處理項會從這條通道上消失，而使用者
無從得知這一則通知涵蓋了什麼。

## Risks / Trade-offs

- **D1 的機制在 repo 內零證據** → D0：先實測再依賴，且退路（`--append-system-prompt`）先寫下來。
  **這是本 change 最大的單點風險。**
- **agent 投遞之後收不到任何回饋** → 它不知道目標查無、格式錯、或被上限降級。這是寫檔投遞的固有
  代價，**本 change 不解決**：失敗對**使用者**是可見的（通知 ＋ 收件匣項目），對 agent 不可見。
  **也不得為此往來源 session 的終端寫東西** —— 那會弄亂使用者正在看的畫面。真正的解法是 MCP
  工具（參數驗證 ＋ 回傳值），列為後續。
- **handoff 的通知與其他 intake 的通知在畫面上長得一樣，點下去的效果卻不同** → 既有條款要求
  通知的系統文案不依 adapter 而異、且不含 folder 名稱或路徑，因此使用者沒有線索分辨。這是本
  change 明知並接受的取捨，記在此處而非假裝不存在。
- **自動開 session 會在使用者沒看著的時候改變 workspace 的狀態** → 不自動切焦點、發通知、rail 上
  看得見；且 prompt 不送出，所以不會有 agent 在背後跑起來。
- **`hooks` 的合成改動會動到事件橋接這條承重路徑** → 對照組：把合成改回覆蓋，`probe:agent-view`
  中「注入的 hook 真的被執行」那條必須變紅，**且貢獻者註冊順序要釘住**（見 D2）。
  **不驗這個對照組，就等於沒有修這個 bug。**
- **驗收環境目前驗不到「同一事件的兩條 hook 命令都被執行」** → `stub-agent.mjs` 只取
  `hooks[event][0].hooks[0].command` 且把 stdout 丟掉。要擴充替身，否則 D2 與 D1 的兩條
  requirement 在對照表上只能填「無載體」。
- **目標清單洩漏 workspace 的絕對路徑給 agent** → 它有 shell，那不是新增的暴露面。
- **這不是沙箱** → 已在 Non-Goals 寫明，spec 中亦不得宣稱。

無資料遷移。新目錄惰性建立，舊的 `sessions.json` / intake 落盤格式不變。
`deliver()` 的第三個參數為 optional，既有兩個呼叫端不受影響。
回退方式是關閉該偏好；`hooks` 合成的修正與「逾時退回後不建第二個 session」不隨偏好回退
（它們修的是既有缺陷）。
