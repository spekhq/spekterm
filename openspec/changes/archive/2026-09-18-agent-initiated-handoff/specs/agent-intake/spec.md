## MODIFIED Requirements

### Requirement: 欄位分為可驗證與第三方撰寫兩類，來源專屬的原始內容既不判斷也不交付

intake 的欄位 SHALL 分為三組：

1. **接收端可驗證的**（adapter、來源種類、來源座標的識別碼、**接收端已解析出的目標 folder**）
   —— 由接收 adapter 從自己已驗證的 metadata 填入。
2. **第三方逐字撰寫的**（標題、本文、發起者、來源座標的標籤）—— 投遞者完全控制。
3. **來源專屬的原始內容** —— 原封保存，供日後診斷。

**這個區分 SHALL 落在型別上。** 少了它，「以標題判斷要開在哪個 repo」會在介面上看起來與「以來源
channel 判斷」同樣可靠，而前者完全由投遞者決定。

**「接收端已解析出的目標 folder」SHALL 為可不存在的欄位**，且 SHALL NOT 能由投遞內容表達 ——
它由 adapter 以自己的依據解析而得（例如 `agent-handoff-source` 的查表），與 `adapter` 欄位同一個
姿態：**payload 自稱的一律不採信**。若它能被投遞內容表達，則放進共用投遞落點的任何一份檔案都能
繞過 routing 自行選擇 folder，而那道機制存在的理由正是「投遞者不得選擇他落在哪個工作目錄」。

第三組 SHALL NOT 出現在收件匣以內任何模組的型別中，SHALL NOT 被解讀為任何判斷依據，
**且 SHALL NOT 被交付給 agent** —— 交付一份使用者沒有看過的文字，等同讓投遞者在被審閱的內容
之外另開一條通道。

**來源座標 SHALL 為通用的形狀**（種類、識別碼、標籤），SHALL NOT 以任何單一來源的詞彙定義。

#### Scenario: 原始內容不出現在收件匣以內的型別中

- **WHEN** 檢視收件匣解析結果所使用的型別
- **THEN** 其中不存在來源專屬原始內容的欄位

#### Scenario: 原始內容不進入交給 agent 的檔案

- **WHEN** 一則 intake 的來源專屬原始內容中含有一段獨特的字串，而該字串不出現在本文中
- **AND** 該則 intake 被接受
- **THEN** 交給 agent 的檔案不含該字串

#### Scenario: 未知的來源種類仍可被處理

- **WHEN** 一則 intake 的來源種類是系統不認得的值，但其餘通用欄位齊備
- **THEN** 該則 intake 正常進入收件匣並可被接受

#### Scenario: 投遞內容無法表達已解析的目標 folder

- **WHEN** 一份放進共用投遞落點的 JSON 中含有指定目標 folder 的欄位
- **THEN** 該欄位被丟棄，該則 intake 的目標仍由 routing 規則決定

### Requirement: 使用者在接受之前看得到本文全文，且本文以純文字呈現

**待處理的** intake SHALL 在使用者接受它之前呈現**本文全文**。

**這是這條管線唯一的人類閘門能否成立的前提。** 少了它，使用者按下送出所依據的全部資訊是標題、
發起者與來源標籤，而**這三者皆為第三方逐字撰寫**：一則標題寫著「README 的錯字（小事）」、
本文夾帶指示的投遞，在介面上與一則真實的請求無法區分。

**該人類閘門的作用域即「本文為第三方逐字撰寫」。** 本文非第三方撰寫的投遞（由使用者自己 session
裡的 agent 撰寫、且由他當下的交辦觸發，見 `agent-handoff-source`）SHALL 得於到達時直接建立
session，**不停留於待處理狀態等待接受**。要使用者為一件他兩秒前才交辦的事再同意一次，是在問一個
可預測答案的高頻問題。

**放寬的僅有「等使用者按一下」這一件事。** 本文的長度上限、純文字呈現、攝入時的正規化、交付內容
與呈現內容逐字元相等、界線的 nonce —— **一律不放寬**，理由與第三方投遞完全相同：agent 撰寫的
本文仍可能被它讀過的內容塑形（它可能剛讀完一則 intake、一個 issue、一份不受信任的 repo 檔案）。
**被移除的是人類閘門，不是標示。**

**本文超過可呈現的長度時，該份投遞 SHALL 於投遞階段即被拒絕**，SHALL NOT 以截斷呈現。
截斷點由投遞者決定，於是他可以把指示放在被截掉的那一段；拒絕使「呈現的內容等於交付的內容」
成為一條**沒有例外**的性質。

**該長度上限 SHALL 訂在「一個人會實際讀完」的量級**，SHALL NOT 訂在某個技術極限 ——
它是這道人類閘門有效性的**唯一旋鈕**，而把它調大以「少拒絕一些」不會讓任何東西變紅。
呈現 SHALL 附上本文的長度，使「這則很長」本身是一個看得見的訊號。

**本文 SHALL 以純文字呈現**：SHALL NOT 套用任何標記語言的渲染、SHALL NOT 載入任何遠端資源、
SHALL NOT 產生可點選的連結。（不可列印字元的移除發生在**攝入**，見上一條 requirement ——
在呈現層做會使交付的那一份與它不同。）**本條涵蓋已接受的項目**：直接建立 session 的交接同樣
會被使用者讀到，其呈現不因為沒有經過接受而放寬。

這是本應用程式**第一次把第三方逐字撰寫的文字渲染進自己的介面** —— 既有那些「渲染不受信任
markdown」的紀律，其作用域是使用者自己 repo 裡的檔案，不涵蓋此處；而一個遠端圖片會讓投遞者
在使用者只是掃一眼收件匣的那一刻得到回條。

#### Scenario: 待處理的 intake 呈現本文全文

- **WHEN** 一則待處理的 intake 被檢視
- **THEN** 其本文的完整內容被呈現

#### Scenario: 本文中的標記語法以字面文字呈現

- **WHEN** 一則 intake 的本文含有標記語言的語法（例如圖片與連結的寫法）
- **THEN** 該語法以字面文字呈現，且畫面上不存在對應的圖片元素或可點選的連結

#### Scenario: 本文過長的投遞在投遞階段被拒絕

- **WHEN** 一份投遞的本文超過可呈現的長度上限
- **THEN** 該份投遞被拒絕，收件匣中不出現該則 intake

#### Scenario: 本文非第三方撰寫者不經接受即建立 session

- **WHEN** 一則本文非第三方撰寫的投遞到達，且其目標已由接收端解析出
- **THEN** 對應的 session 被建立，而使用者未執行任何接受動作

#### Scenario: 不經接受者其本文仍以純文字呈現且仍受長度上限約束

- **WHEN** 一則不經接受即建立 session 的交接，其本文含有標記語言的語法
- **THEN** 該語法以字面文字呈現，且畫面上不存在對應的圖片元素或可點選的連結
- **AND** 其本文超過長度上限時，該份投遞於投遞階段即被拒絕

### Requirement: 接受一則 intake 於解析出的 folder 建立 agent session

**建立一個由 intake 觸發的 session 時**（使用者接受一則待處理的 intake，或一則到達時即被接受的
項目），系統 SHALL 於 `intake-routing` 解析出的 folder 建立一個 **agent 目標**的 session，
且 SHALL 經與使用者手動建立時**相同的路徑**建立 —— 於是它一樣進入 session 清單、一樣被持久化、
一樣可被關閉與重建。系統 SHALL NOT 以繞過該路徑的方式建立 pty，亦 SHALL NOT 為此擴充該路徑所
接受的參數。

**本條的作用域以「session 由 intake 觸發」為準，不以「使用者按下接受」為準** —— 否則一條到達時
即接受的路徑會在字面上不受本條約束，而它建立 pty 的方式正是本條要管的事。

**系統 SHALL NOT 代使用者指定該 session 的名稱** —— 指定名稱在既有能力中被定義為「使用者永久
接管命名權」，此後 agent 依任務產生的終端標題將被靜默地不予呈現。由系統代為指定，等於替使用者
按下一個只有他能按的開關，而他不會知道要如何還原。

**由 intake 建立的 session，其啟動參數 SHALL 與同一個 folder 手動建立者等價**：除了對話識別碼
與系統注入設定的位置之外**逐項相同**，且參數的**個數相同**。系統注入的 agent 設定，其頂層欄位
**SHALL 恰為**既有注入所定義的那一組。

**兩處都刻意寫成等價／白名單而非「不得含某些值」**：後者是黑名單，只擋得住列舉得出來的東西，
而它在今日恆真（啟動路徑根本沒有能加旗標的參數）——**一條恆真的斷言撐不住任何東西**。

**本能力 SHALL NOT 宣稱它保證了 agent 的許可姿態。** 那由使用者自己的設定與**目標 repo 自己的
設定**決定，而目標 repo 是由 routing 選出的 —— 本能力保證的是「不降低它」，不是「它夠緊」。

#### Scenario: 於解析出的 folder 建立，而不是於選中的或第一個 folder

- **WHEN** workspace 中有三個 folder，rail 上選中的是第三個，routing 規則解析到第二個
- **THEN** 新的 agent session 建立於**第二個** folder，且出現在該 folder 的 session 清單中

#### Scenario: 由 intake 建立的 session 與手動建立者一同被重建

- **WHEN** 同一個 folder 中有一個由 intake 建立與一個手動建立的 agent session，應用程式重新啟動
- **THEN** 兩者都被重建

#### Scenario: session 的名稱未被系統指定

- **WHEN** 一則 intake 被接受並建立 session，其後 agent 宣告一個終端標題
- **THEN** 該標題最終呈現於該 session 的標籤上

#### Scenario: 啟動參數與手動建立者等價

- **WHEN** 於同一個 folder 各建立一個由 intake 觸發與一個手動觸發的 agent session
- **THEN** 兩者的啟動參數在去除對話識別碼與注入設定位置之後完全相同
- **AND** 兩者的參數個數相同

#### Scenario: 注入設定的頂層欄位未因本能力而增加

- **WHEN** 一則 intake 被接受並建立 session
- **THEN** 系統注入的 agent 設定，其頂層欄位集合與手動建立時相同

#### Scenario: 到達時即接受者其啟動參數同樣等價

- **WHEN** 一則到達時即被接受的交接建立了 session，同一個 folder 另有一個手動建立的 agent session
- **THEN** 兩者的啟動參數在去除對話識別碼與注入設定位置之後完全相同

### Requirement: 第一則 prompt 預先填入而不送出，且不早於 agent 就緒

系統 SHALL 將第一則 prompt 填入該 session 的 agent 輸入處，且 SHALL NOT 代為送出 ——
**送出由使用者為之**，那是這條管線唯一的人類閘門。

填入 SHALL NOT 早於該 session 的等待狀態**首次成為就緒**。在此之前寫入，內容會落進 agent 的
啟動畫面而非輸入處，**而畫面上不會有任何錯誤**。判定 SHALL 依 `agent-event-bridge` 的等待狀態，
SHALL NOT 以固定延遲、重試次數或終端畫面的內容為依據。

**填入 SHALL 由主行程執行。** prompt 含一個檔案系統位置，把它交給 renderer 再寫回去，等同把該
位置送過 IPC —— 那是本能力明文避免的事。

**單行 SHALL 為編碼路徑的性質，而非呼叫端的義務**：不附送出的編碼 SHALL 一併濾除換行。

**預填在一段有上限的時間內未能發生時，系統 SHALL 可見地說明，且該則 intake SHALL 回到可重新
處理的狀態。** 本條 SHALL 以**狀態**為判準而非以成因為判準 —— 等待狀態始終不到的成因不只一種
（事件回報未啟用、注入失敗、agent 啟動失敗、agent 版本改變）。已知可事先偵測的成因（例如事件
回報偏好已關閉）SHALL 於**建立 session 之前**告知並 SHALL NOT 建立 session，那是本條的快速
路徑，不是它的全部。

**該告知的時機寫成「建立 session 之前」而非「接受之前」**：到達時即被接受的項目沒有「接受之前」
這個時刻，而它同樣不該建立一個註定收不到 prompt 的 session。

**一則回到可重新處理狀態的 intake SHALL 保留它已經建立的 session 的關聯，其再次處理
SHALL NOT 建立第二個 session**，SHALL 改為對既有的那一個重新嘗試預填。

少了這一條，一次逾時會留下一個空的 session 在清單上，而再次處理又建一個 —— 每處理一次多一個，
**沒有上界**，且每一個看起來都正常。

#### Scenario: 就緒之後填入且未送出

- **WHEN** 一則 intake 被接受，其 session 的等待狀態成為就緒
- **THEN** 送往該 session 的內容含該 prompt
- **AND** 該 prompt 之後不含任何送出字元或換行

#### Scenario: 就緒之前不寫入

- **WHEN** 一則 intake 被接受，其 session 的 pty 已存在
- **AND** 該 session 的等待狀態尚未成為就緒
- **THEN** 在就緒發生之前的**整段期間**，送往該 session 的內容為空

#### Scenario: 就緒之後只填入一次

- **WHEN** 該 session 的等待狀態在就緒之後再次成為就緒
- **THEN** 該 prompt 未被再次填入

#### Scenario: 使用者送出後 agent 才收到

- **WHEN** 使用者於輸入處送出
- **THEN** 送往該 session 的內容出現送出字元
- **AND** 該 prompt 出現於 agent 的紀錄中

#### Scenario: 預填未能發生時說明並回到可重新處理

- **WHEN** 一則 intake 被接受，而其 session 的等待狀態在上限時間內未成為就緒
- **THEN** 系統可見地說明預填未能發生
- **AND** 該則 intake 回到待處理

#### Scenario: 事件回報已關閉時於接受之前告知

- **WHEN** 事件回報偏好已被關閉，使用者嘗試接受一則 intake
- **THEN** 系統於建立 session 之前告知預填不會發生
- **AND** session 的總數與嘗試之前相同，且該則 intake 仍為待處理

#### Scenario: 事件回報已關閉時到達的項目不建立 session

- **WHEN** 事件回報偏好已被關閉，一則本會於到達時即被接受的項目到達
- **THEN** session 的總數與到達之前相同
- **AND** 系統可見地說明預填不會發生

#### Scenario: 逾時之後再次處理不建立第二個 session

- **GIVEN** 一則 intake 已建立 session 但預填逾時，因而回到待處理
- **WHEN** 使用者再次處理它
- **THEN** session 的總數與再次處理之前相同

### Requirement: 新項目到達時發出作業系統通知，且合併與總量皆有界

一則 intake 成功進入收件匣時，系統 SHALL 發出一則作業系統原生通知。

同一時間窗之內到達的多則 SHALL 合併為一則。**該窗自第一則到達的時刻起算，SHALL NOT 因窗內
後續的到達而延後** —— 持續到達的情況下通知 SHALL 仍然週期性地發出。

通知在**比合併窗大一個量級的時間尺度上** SHALL 同樣有上界；逾越該上界時 SHALL 降級（延長窗、
改為僅陳述數量、或暫停），並 SHALL 以「使用者打開收件匣」為重置點。

通知 SHALL NOT 宣告為需要使用者手動關閉、或不會自行消失。

被拒絕的投遞 SHALL NOT 發出作業系統通知 —— 拒絕走收件匣之內的彙整呈現（見「投遞以檔案落點為
契約，且落點的內容是不受信任的」之「面向使用者的拒絕與警示 SHALL 有界」）。那是**同一條理由的
兩條獨立通道**：使用者的注意力有限，而投遞者控制數量。

**例外：來源為應用程式自身 agent session 的投遞，其拒絕 SHALL 發出通知。** 那條路徑上沒有任何
人在等著按下接受，而「使用者剛剛交辦、agent 回報已交出、實際上什麼都沒發生」與成功在畫面上
**完全相同**。上一段的理由在此不成立：投遞者不是第三方，而是使用者自己當下指使的 agent。
該例外 SHALL 與待處理項的通知**共用同一套合併與總量上界**。

**該例外 SHALL NOT 涵蓋尚未被消費的解析失敗。** 一份無法解析的投遞刻意不被消費（它可能只是
寫到一半），於是它會在每次補寫時再次被讀到 —— 逐次通知沒有上界，而合併只防批次、不防節奏。
這類失敗 SHALL 只走收件匣之內的彙整呈現。

**一則合併後的通知若其批次中含有任何待處理項，其效果 SHALL 為打開收件匣。** 合併的通知只陳述
數量，使用者無從得知它涵蓋了哪些項目；把他送去一個他沒有待辦動作的 session，會讓那些待處理項
從這條通道上消失。

> **「不因後續到達而延後」是合併那一半的重心。** 直覺的作法（每次到達都把計時器往後推）在持續
> 到達時**永遠不會到期**：越是有事情發生，越沒有通知。這個失效方向完全靜默。
>
> **總量的界是另一半，而合併擋不住它。** 合併只防批次、不防節奏：每數分鐘到達一則時，每個窗
> 結算的都是單則形式，於是這條通道可以無限期地每小時響十幾次。待處理總量上限也不是界 ——
> 使用者每清掉一則就釋放一格，**越認真清收件匣，這條通道越吵**。
>
> **覆蓋缺口：「通知真的出現在使用者的桌面上」沒有自動化載體。** 可驗的是決策發生了、合併與
> 上界成立、內容正確；通知實際送達與其視覺呈現（折行、截斷）由 dogfood 認定。
> **「應用程式在背景時通知仍然發出」同樣沒有載體** —— 驗收環境不涵蓋「視窗不可見時」的行為。

#### Scenario: 單一到達發出一則通知

- **WHEN** 一則 intake 進入收件匣
- **THEN** 恰發出一則作業系統通知

#### Scenario: 一次回補的多則合併為一則

- **WHEN** 十則 intake 於同一個時間窗之內進入收件匣
- **THEN** 恰發出一則作業系統通知

#### Scenario: 持續到達時通知不被無限延後

- **GIVEN** intake 以短於合併窗的間隔持續到達
- **WHEN** 經過數個合併窗的時間
- **THEN** 通知持續地發出，SHALL NOT 因後續的到達而停止發出

#### Scenario: 到達的節奏逾越總量上界時降級

- **GIVEN** intake 以每個合併窗一則的節奏持續到達，直到逾越總量上界
- **WHEN** 再有一則到達
- **THEN** 該則不再各自發出一則通知
- **AND** 使用者打開收件匣之後，上界重置

#### Scenario: 被拒絕的投遞不發出作業系統通知

- **WHEN** 一則投遞因識別碼不合法而被拒絕
- **THEN** 不發出任何作業系統通知
- **AND** 該拒絕仍呈現於收件匣之內

#### Scenario: 來源為自身 agent session 的拒絕發出通知

- **WHEN** 一則來源為自身 agent session 的投遞因其目標不存在而被拒絕
- **THEN** 發出一則作業系統通知
- **AND** 該拒絕亦呈現於收件匣之內

#### Scenario: 尚未被消費的解析失敗不發出通知

- **WHEN** 一份來源為自身 agent session 的投遞因內容不完整而解析失敗，且該項目未被消費
- **THEN** 不發出任何作業系統通知

#### Scenario: 批次中含待處理項的合併通知打開收件匣

- **GIVEN** 同一個合併窗內到達一則待處理項與一則到達時即被接受的交接
- **WHEN** 使用者觸發該合併後的通知
- **THEN** 收件匣被打開

### Requirement: 通知只有一種效果，且不得取用遠端資源

通知 SHALL NOT 取用任何遠端資源；其圖示 SHALL 為應用程式自身的本地資源。

通知 SHALL NOT 提供任何可對該 intake 直接採取行動的控制項（含動作按鈕與內嵌回覆）。
**其唯一效果 SHALL 為導覽** —— 把使用者帶到收件匣，或帶到該項目已經建立的 session
（見 `agent-handoff-source`）。**SHALL NOT 對該 intake 本身做任何處置。**

**「只有一種效果」規範的是種類而非目的地。** 它要擋的是「在通知上處置一則 intake」——
那會讓使用者在**沒有讀過本文**的情況下接受它。導覽到哪裡不影響這件事：兩個目的地都只是把
使用者帶到一個他能自己看清楚再動作的地方。

> **這兩條各擋一個看起來像改良的重構。** 「通知上放發話者的頭像」讓一則 intake 到達等於一個
> 遠端存取 —— 比收件匣那條更嚴重，因為它連「使用者掃一眼」都不需要。「通知上放一顆 Accept」
> 讓使用者在**沒有讀過本文**的情況下接受一則 intake，而「使用者在接受之前看得到本文全文」
> 是這條管線僅有的兩道人類防線之一。兩者都不會讓任何既有的斷言變紅。

#### Scenario: 通知不產生任何遠端存取

- **WHEN** 一則 intake 觸發一則作業系統通知
- **THEN** 不發生任何對外的網路存取

#### Scenario: 通知不提供處置該 intake 的控制項

- **WHEN** 一則 intake 觸發一則作業系統通知
- **THEN** 該通知上不存在任何可接受或忽略該 intake 的控制項

#### Scenario: 導覽到 session 的通知同樣不提供處置控制項

- **WHEN** 一則到達時即建立了 session 的交接觸發一則作業系統通知
- **THEN** 該通知上不存在任何可接受或忽略它的控制項

### Requirement: 觸發通知把視窗帶到前景並打開收件匣

使用者觸發該通知時，系統 SHALL 把主視窗帶到前景（**包含自最小化狀態還原**），並 SHALL 打開
收件匣。

**本條的作用域為待處理的項目。** 一則到達時即被接受並建立了 session 的項目，其通知的效果 SHALL
為聚焦該 session（見 `agent-handoff-source`）—— 它在收件匣中沒有任何待辦動作，把使用者送去收件匣
等於要他再點一次才到得了他真正要去的地方。**失敗的項目仍是待處理，適用本條；合併後涵蓋待處理項
的通知亦適用本條。**

收件匣已經開啟時，觸發通知 SHALL 為無操作 —— **SHALL NOT 重設它當前的分頁、輸入中的內容或
焦點位置**。

由通知開啟的收件匣關閉之後，焦點 SHALL 回到活動列的收件匣入口（與使用者自行點擊開啟時相同）。

主視窗由 `workspace-app-shell` 持有；本條是唯一一個不由使用者直接操作該視窗而改變其前景狀態
的來源。

> **覆蓋缺口，分兩層：**
>
> 「把視窗帶到前景」這組操作本身**是可驗的** —— 在帶有 window manager 的環境下，
> 「只呼叫聚焦」與「還原、顯示、再聚焦」兩種實作可分辨（前者對最小化的視窗無效）。
> 本輪**不建置**該驗收環境（它會改變所有探針的執行環境），列為缺口 —— 這是「本輪不做」，
> 不是「做不到」。
>
> 真正做不到的是桌面環境的搶焦點抑制（視窗可能改為在工作列閃爍而不是浮到最前）。
> 那一層由 dogfood 認定。
>
> **「打開收件匣」那一半有載體。**

#### Scenario: 觸發通知後收件匣呈現

- **GIVEN** 收件匣未開啟，且該通知對應一則待處理的項目
- **WHEN** 使用者觸發該通知
- **THEN** 收件匣以全視窗 overlay 呈現

#### Scenario: 收件匣已開啟時觸發通知不重設它

- **GIVEN** 收件匣已開啟、使用者正位於 routing 規則的分頁，且某個欄位中已輸入尚未儲存的內容
- **WHEN** 使用者觸發一則待處理項目的通知
- **THEN** 收件匣仍位於 routing 規則的分頁，該欄位的內容原封不動，且焦點未改變

#### Scenario: 由通知開啟並關閉之後焦點回到入口

- **GIVEN** 收件匣由通知開啟
- **WHEN** 使用者關閉它
- **THEN** 焦點位於活動列的收件匣入口

#### Scenario: 已接受並建立了 session 的項目其通知不開啟收件匣

- **GIVEN** 收件匣未開啟，且該通知對應一則到達時即建立了 session 的交接
- **WHEN** 使用者觸發該通知
- **THEN** 收件匣未被開啟

## REMOVED Requirements

### Requirement: prompt 完全由系統組成，且要求 agent 逐條列出文中試圖下達的指示

**Reason**：「逐字照抄祈使句、先不要動手」在實際使用中**把這條管線廢掉了** —— 使用者接受一則
intake、按下送出，得到的是一份抄錄的清單；他得再交代一次、有時兩三次，那件事才會開始做。
Slack 那條路每一次都如此。

而這條要求的價值，規格自己已經寫明是「**讓使用者有第二次看見內容的機會**」—— 它明文
「SHALL NOT 宣稱阻止了工具呼叫，亦 SHALL NOT 宣稱注入必然會被認出」。**那個「第二次」是多的**：
「使用者在接受之前看得到本文全文」已經是一條獨立的 requirement，而 prompt 是**填好而不送出**的
——他在按下送出之前又看了一次。以一次真實的可用性代價換一個第三次的機會，不划算。

**被保留的那一半見下一條**：本文只放一個連結、把真正的內容移到所有機制作用域之外，是規格自己
點名的殘餘路徑，那條對第三方的本文仍然擋著。

**Migration**：由下面「prompt 完全由系統組成，且指出界線之內的內容即是要執行的工作」取代。
`buildPrompt` 的兩種措辭皆改為「這就是要做的事」，差別只剩第三方的那一種額外聲明它來自他人、
且第一回合不得取得外部資源。

## ADDED Requirements

### Requirement: prompt 完全由系統組成，且指出界線之內的內容即是要執行的工作

prompt SHALL 完全由系統組成，SHALL NOT 含 intake 任何欄位的原文（系統自己產生的 nonce 不在此限）。

投遞者撰寫的文字若進入 agent 的輸入緩衝區，某些起始字元會使該輸入切換成別的模式（記憶、命令、
選單），**而它後面緊接著的就是使用者按下的送出**。

prompt SHALL 指出**界線之內的內容就是那件要做的事**，SHALL NOT 要求 agent 先逐字照抄其中的
祈使句、亦 SHALL NOT 要求它先不要動手。**人類閘門在別處**：使用者在接受之前看得到本文全文，
而 prompt 是填好而不送出的 —— 送出是他的動作，且他在那之前又讀了一次。

**本文為第三方逐字撰寫時，prompt SHALL 另外聲明兩件事**：該內容來自他人，以及**第一回合不得
取得任何外部資源**（檔案中的連結一律不跟隨）。後者擋的是一條規格自己點名的逃逸路徑 ——
本文可以只放一個連結，把真正的內容移到本能力所有機制的作用域之外。**本文非第三方撰寫時不適用**：
它是使用者自己交辦的工作，而工作本來就可能要求去看某個東西。

**「本文是否為第三方撰寫」SHALL 是接收端可驗證的欄位，SHALL NOT 能由投遞內容表達** ——
否則任何放進共用投遞落點的檔案都能為自己要到比較寬鬆的那一種措辭。

**界線與 nonce 在兩種情形下都保留。** 非第三方的本文仍可能被來源 agent 讀過的東西塑形，
標示不會因此失去意義；被換掉的只有「要不要動手」。

**本能力 SHALL NOT 宣稱 prompt 阻止了任何事。** 它不約束模型的行為，也不及於使用者送出之後的
回合。**唯一真正的人類閘門是「使用者讀過本文之後按下送出」** —— 那條由「接受之前看得到本文
全文」與「prompt 填入而不送出」兩條共同構成，而這一條不是它們的替代品。

**系統 SHALL NOT 以任何方式使 agent 存取該檔案時的許可提示更不顯眼。** 該提示與注入內容要突破
的是同一個提示；讓它看起來理所當然，等同訓練使用者對它放行。需要降低摩擦時，作法是讓它**更
可辨識**（固定且使用者認得的位置），不是讓它更不引人注意。

#### Scenario: prompt 不含 intake 的欄位原文

- **WHEN** 一則標題與本文皆含特殊起始字元的 intake 被接受
- **THEN** 填入輸入處的 prompt 不含該標題與本文的任何片段

#### Scenario: prompt 指出那就是要做的事

- **WHEN** 一則 intake 被接受
- **THEN** 填入的 prompt 指出界線之內的內容即是要執行的工作
- **AND** 該 prompt 不要求 agent 先逐字照抄其中的祈使句

#### Scenario: 第三方的本文另外聲明來源與不取得外部資源

- **WHEN** 一則本文為第三方逐字撰寫的 intake 被接受
- **THEN** 填入的 prompt 聲明該內容來自他人
- **AND** 該 prompt 明示第一回合不得取得任何外部資源

#### Scenario: 投遞內容無法為自己要到比較寬鬆的措辭

- **WHEN** 一份放進共用投遞落點的 JSON 中含有宣稱本文非第三方撰寫的欄位
- **THEN** 該欄位被丟棄，該則 intake 仍得到第三方的那一種 prompt
