## Why

第十一次 dogfooding 的回饋：**「我在 vscode 習慣按 `Ctrl+P` 找檔案開啟，但現在沒辦法這樣做了。」**

側欄的 Files 身分只有一棵**逐層展開**的檔案樹 —— 那是 `file-explorer` 刻意的設計（「目錄於展開時
才載入其內容」，避免在一個旁邊有 agent 一直在寫檔的 app 裡預先掃描整棵樹）。代價是：要開一個
**已知路徑**的檔案，使用者得從根目錄一層一層點下去，而那是滑鼠的工作。

這個 app 的價值命題是「不必另外開 IDE 就能一邊駕駛 agent、一邊看著上下文」。**而「跳到一個我知道
名字的檔案」是讀程式碼最基本的動作** —— 它目前的成本高到讓人寧可切回 IDE，那正好打在價值命題上。

## What Changes

- **新增 quick open 入口**：側欄持有焦點時按 `Ctrl+P`，開啟一個以鍵盤操作的檔案搜尋入口 ——
  輸入片段即時模糊比對、`↑↓` 選擇、`Enter` 開啟、`Esc` 關閉。
- **搜尋範圍為當前側欄座標**：來源 repo ＋ 工作目錄所指的那棵樹（＝ Files 樹當下的根）。
  這不引入任何新的範圍概念 —— 觸發條件是「人在側欄裡」，範圍是「側欄當下看的那棵樹」，語意一致。
- **選中後開在側欄的 Files 檢視**：複用既有的跨身分開檔路徑（`MainStage.openFileFromOpenSpec`），
  它已經會解析目標所屬的工作目錄、切換身分、展開側欄。**開檔那一半不需要新的路徑。**
- **主行程新增受邊界約束的遞迴列舉**：既有的 `listDir` 是單層的，quick open 需要整棵樹的清單。
  新的能力受**與 `listDir` 完全相同**的邊界約束（folder 識別碼定址、不回傳絕對路徑、不跟隨
  越界 symlink），並排除版控忽略的內容。
- **終端持有焦點時 `Ctrl+P` 讓路給 pty**，這是**明確的行為而非未完成的缺口**：實測 `claude`
  自己以 `Ctrl+P` 顯示 previous history（zsh 綁 `up-line-or-history`、bash 綁 `previous-history`，
  且使用者的 GNOME Terminal 未綁它 —— 沒有 `Ctrl+T` 當年那個「你早就沒有它了」的豁免）。
  agent 是這個 app 的主場，**這顆鍵在終端裡不拿**。

### 本 change 不做

- **不做 command palette**（只做檔案）。`Ctrl+P` 在 VS Code 裡與 `Ctrl+Shift+P` 是同一個介面的
  兩種前綴，但命令面板需要一份「有哪些命令」的清冊，那是獨立的論證。
- **不做跨 repo 搜尋**。範圍是側欄座標；要找別的 repo 的檔案，先切側欄來源（既有能力）。
- **不做內容搜尋**（grep）。這條是「跳到一個檔案」，不是「找一段文字」。
- **不新增「把焦點移到側欄」的快捷鍵**。使用者已知情裁決只做焦點判定版（見下）。

### 一個知情下的裁決，必須被記錄

**觸發條件要求焦點在側欄，而「終端幾乎永遠持有焦點」是這個 app 的核心前提**（`keyboard-navigation`
的 Purpose 明文寫著它）。於是這顆快捷鍵在使用者於終端中打字時**不生效** —— 要用它得先讓側欄取得
焦點，而目前唯一的方法是用滑鼠點過去。

實作時曾提議補一顆無條件生效的鍵（`Ctrl+Shift+P`，`Ctrl+Shift+<字母>` 在終端協定裡編碼不出來、
代價確定為零）作為主力，`Ctrl+P` 僅在側欄內生效。**使用者裁決不採用，只做焦點判定版。**

記錄它是為了讓日後讀到的人知道：那個限制是**被選擇的**，不是漏做的。退路（無條件的第二顆鍵）
成本為零且隨時可加 —— 屆時只動一個判斷、spec 與 probe，沒有任何資料格式綁在鍵位上。

## Capabilities

### New Capabilities

- `quick-open`: 側欄的鍵盤檔案搜尋入口 —— 觸發條件與作用域、搜尋範圍取自側欄座標、模糊比對與
  結果排序、鍵盤操作模型（選擇／開啟／關閉）、開啟目標的行為、清單的取得與時效、以及空結果與
  大型樹的處理。

### Modified Capabilities

- `keyboard-navigation`: 本能力此前只涵蓋**導航**與**排序**兩組快捷鍵，而它們的通則是「終端持有
  焦點時**仍然生效**」。quick open 是**第三組**，其作用域與前兩組相反（終端裡讓路、側欄裡生效，
  且該按鍵**必須**抵達 pty）。既有措辭的作用域已寫明是「導航與排序」，因此**並不存在字面上的
  矛盾** —— 要修的是**誤讀的風險**：這份規格反覆以「導航 vs 排序」的兩組對照解釋各種焦點情形，
  而那個形式會被讀成一份窮舉表。兩條 requirement 因此明文寫出第三組落在哪一邊，並要求日後新增
  快捷鍵時回到該處交代。**Purpose 不改** —— 它描述的是本能力自己的兩組快捷鍵，而 quick open
  隸屬於另一個能力。
- `filesystem-access`: **一條 ADDED 與一條 MODIFIED。** 新增遞迴列舉的邊界要求；而既有的「檔案
  系統能力僅暴露已為其定義邊界要求的操作」，其 scenario 是一份**逐一列舉 method 名稱**的清單 ——
  不同時修改它，`listFiles` 進了 preload 之後主 spec 就會與實作、與 `probe:shell` 的白名單守衛
  三方分岔（而那道守衛存在的理由正是「你加了東西卻沒告訴它」）。

## Impact

- **主行程**：`fs-service` 新增遞迴列舉；`ipc/fs` 與 preload 白名單各增一個進入點。
- **renderer**：新的 quick open 元件（overlay 形態，含 `role="dialog"` —— 於是它自動被既有的
  「對話框開啟時導航快捷鍵不生效」尊重）；`KeyboardNavigation` 新增第三組的判定分支。
- **既有邊界不變**：`fs.*` 的定址詞彙（folder 識別碼 ＋ folder-relative 路徑）一個字都不改，
  新能力只是換一種列舉粒度。
- **i18n**：新文案入 `src/shared/i18n/en.json`（受既有三道守衛約束）。
- **驗收**：`probe:shell`（白名單）、`probe:keyboard`（觸發與讓路的兩個方向，**兩者都要有對照組**
  —— 只驗「側欄裡開得起來」的話，一個無條件攔截的錯誤實作照樣通過）、`probe:files`（開檔與範圍）。
- **效能**：遞迴列舉的成本與時效策略見 design。實測基準：本 repo 412 檔／10ms，一個 4493 檔的
  repo／34ms（Node `readdirSync` 遞迴，含忽略清單）。
